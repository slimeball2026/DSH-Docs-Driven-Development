# M2.2 施工记录：项目根没有自动来源

> **日期**：2026-11-13 ｜ 环境：DSH desktop `0.2.2-rc.2`（commit `a6b1b85`）｜ GUI `http://127.0.0.1:59258`
> **前置**：`M2.2-施工记录-真因与修复.md`（cordis Proxy 陷阱，`apply()` 第一行就抛）

---

## 1. 现象

面板终于出现了（M2-1 通过），但主栏显示：

```
当前项目没有启用 DDD
没有探测到项目根。
```

我先按"这是 bug"查，结论是：**这不是 bug，是必然。** 而且背后的原因比 bug 更值得记。

---

## 2. 真因：cwd 在 client 侧**没有自动来源**

### 2.1 旧实现的三处取值，三处都错

`sessionInfoOf()` 是从 SPEC 的设想写出来的，**从没在真宿主上验过**：

| 原写法 | 宿主真实情况（用 `cordis_inspect_query` 核过） |
|---|---|
| `ctx.workingDirectory.get()` | **host 侧**服务；签名是 `get(session: Session)`，需要 `Session` 对象。浏览器里没有 `Session` 实例 |
| `ctx.layout.panelInfo()` | `layout` **确实有** `panelInfo`，但 `PanelInfo` 只有一个字段：`{ activePanelId: MainPanelId \| null }` —— **不含 sessionId** |
| `ctx.sessions.active()` | `sessions` **没有 `active()` 方法**。它有 `retain / using / retainInfo / refreshProjections / search / fork / scope / binding` |

三处全部返回 `undefined` → `cwdOf()` 永远返回空串 → 面板不知道查哪个项目。

### 2.2 更根本的一条：宿主**设计上**不给这个席位会话

`dsh-client-ui-layout/src/client/index.ts` 第 71-75 行，原文：

```ts
/**
 * Central panel selected by sidebar entry id. The reserved `conversation`
 * key hosts the Conversation; **other keys receive no Session binding**.
 */
'main': { kind: 'keyed'; scope: 'root' }
```

我们的 `ddd-construction-board` 正是"other keys"。

### 2.3 client 侧也没有"当前选中会话"

我把 client Service 目录全查了：

| 服务 | 有没有"当前会话"？ |
|---|---|
| `layout` | ❌ 只有 `activePanelId`（哪个**主栏面板**被选，不是哪个会话） |
| `sessions` | ❌ 有 `list`（全部会话）、`binding(id)`（按 id 取），**没有"当前"** |
| `uiWorkspace` | ❌ 全是"打开/切换"动作，不暴露当前选中 |
| `workspace` 系列 | ❌ 同上 |

`grep 'selectedSession\|currentSession\|activeSession'` 在 `app.asar` 全量里**零命中**。

> ⇒ **"用户当前选中哪个会话"是 UI 内部状态，没有服务暴露它。**
> client 侧**不可能**自己知道该查哪个项目。

### 2.4 为什么"猜一个"是错的

`grep -c services.list`：`~/.dsh/sessions/` 下有 **12 个不同的工作区目录**（`dogfood`、`_m1-drill`、`_m15-live2`、`_review/proj-a`、`coach-test-workspace`…）。

猜错的后果不是"显示得不好看"，而是**显示另一个项目的门禁读数** ——
这正是本项目从 M2 起就在防的事：

> **UI 如果显示了错的数据，比没有 UI 更糟 —— 它会把错误的信任可视化。**

所以按铁律：**不猜，让用户显式选。**

---

## 3. 修法：host 出候选 + 用户显式选

### 3.1 新增 host 路由 `GET /api/ddd/projects`

`server/routes.ts` 里加第 5 条路由，返回：

```jsonc
{
  "ok": true, "version": 1,
  "projects": [
    { "cwd": "C:\\...\\dogfood", "projectRoot": "C:\\...\\dogfood", "isDdd": true },
    { "cwd": "C:\\...\\_m1-drill", "projectRoot": "", "isDdd": false }
  ]
}
```

`isDdd` **由 host 判定** —— client 没有文件系统，判断不了有没有 `docs/`。

`index.js` 里的实现要点：

1. 从 `sessions` 服务收集所有会话的 `cwd`（`values()` / `list()` / 数组，三种形状都试，**不假定一种**）；
2. 逐个用 `prober.ensure()`（**读盘**）而不是 `peek()`（只读缓存）——
   从没被会话打开过的目录在缓存里没有记录，`peek` 会误报"不是 DDD 项目"；
3. **只标，不丢**：不是 DDD 项目的目录也留在列表里（用户可能正准备把它变成 DDD 项目）；
4. DDD 项目排前面，其余按路径字母序（稳定排序，不抖动）。

### 3.2 client 侧：`ProjectPicker` 下拉

- 候选来自 `/api/ddd/projects`；
- `●` = 已启用 DDD，`○` = 尚未启用（**都可选**）；
- 切换项目会**真的重新取数**（不是只改标题）——
  否则会显示"上一个项目的数据 + 新项目的标题"，正是本项目最怕的症状；
- 没选时显示**明确提示**：

  ```
  请先选择项目根
  宿主不会告诉面板"当前是哪个项目"，所以需要你在上面的下拉里选一个。
  ```

  ⚠️ 这句与"当前项目没有启用 DDD"**必须区分**：前者是"我不知道查谁"，
  后者是"查过了，没启用"。混为一谈会让用户以为自己的项目坏了
  —— 这正是本轮实机撞到的误解。

### 3.3 `sessionInfoOf` 的语义收口

```ts
sessionInfoOf(ctx, chosenCwd)   // 现在第二个参数是 cwd 的**唯一真源**
```

- `cwdOf()` 只返回 `chosenCwd`，**不再读任何服务**（三个来源全是错的）；
- `sessionIdOf()` 只在**恰好一个会话**时返回它的 id，多个则留空（不猜）——
  `gate.read` 是会话级的，猜错会话会让门禁显示成别人的读数。

## 5. 这一轮的方法论收获

| # | 教训 |
|---|---|
| 1 | **`cordis_inspect_query` 是查 API 形状的最快路** —— 我靠它一次否掉了 `sessions.active()` / `layout.panelInfo().sessionId` 两个不存在的 API |
| 2 | **`?.` 拦不住 Proxy 抛错**（上一轮），**`getSnapshot()` 也不等于"当前状态"**（这一轮）—— 都要落到真源码 |
| 3 | **"显示了错的数据"比"什么都没显示"更危险**。所以宁可多一步用户操作，也不自动猜 |
| 4 | **区分"我不知道"与"我查过了"**。两种情况看起来都像"没有数据"，但用户的处置完全不同 |
