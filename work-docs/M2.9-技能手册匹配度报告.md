它把这条列为**拖累最大的一项** —— 不是 token 成本，是"两个权威同时说话该信谁"。

## 3. 用实测裁决的那条冲突（最重要）

手册 §4.1.1 说「改完内容文档 → 写交接 → 标绿」，
而 `doc_new` 的提示说「**第 3 步（重排阅读顺序）在第 2 步（标绿）之后**」。

**两条对 `read-order` 该在哪一步改，给出了相反的答案。** 我没有猜，而是实测。

### 3.1 探针：`_m28/probe-order-conflict.mjs`

用**真实 `apply()` 装配**（不是假注册表 —— 交接 §4.1 的纪律），两种顺序各跑一遍：

| 顺序 | 做法 | H-6 |
|---|---|---|
| **A**（手册） | 先改 `read-order` → 写交接 → 标绿 | **0 条** |
| **B**（提示） | 写交接 → 标绿 → 再改 `read-order` | **1 条** |
| C（对照） | 写交接 → 标绿，完全不碰 `read-order` | 0 条 |

B 的实际报错：

```
`handover-1` 标成 authoritative 之后，这些文档改过：
- `read-order`：标绿时 9537a6，现在 ce3576
```

### 3.2 结论

**H-6 的定义就是"标绿之后改过的文档"。** 所以"标绿之后再改 `read-order`"**必然**触发它 ——
`doc_new` 那句提示把因果说反了，它把 **H-6 的成因**说成了 **H-6 的解药**。

而且它与**同一段里自己上面的 ⓪ 前置**（先把要引用的东西全定稿）直接矛盾。

### 3.3 已修

- `tools/doc-new.js`：改成「第 3 步在第 2 步**之前**」，并说明这和 ⓪ 是同一条规矩；
- `test/tools.test.js`：原来那条断言**钉住了错误行为**（`第 3 步在第 2 步之后`），
  改成断言正确方向 + 反向断言（不许再出现"之后"）；
- 新增变异 `step-order-backwards`，已 CAUGHT。

> ⚠️ **这条测试是"测试钉住错误行为"的实例**：
> 测试红了不代表代码错，也可能是**测试本身在守一个已被证伪的假设**。
> 改它之前必须先有实测，否则就是"改测试让它变绿"。

## 5. 还没解决的一条（UNKNOWN）

**手册 §2 没有提到 `pwsh` 这个已知漏洞。**

门禁按路径判，而 `pwsh` 的参数是任意字符串，插件拦不住 `pwsh -Command "> docs/x.md"`。
这是 SPEC §7.2 / R1 明确登记的**已知限制**（"写进 README 已知限制，不假装堵住了"），
但**手册里没写**，于是 AI 不知道这条路存在。

为什么判 UNKNOWN 而不是 STALE：这属于"手册可以补一条"，不是"手册说错了"。
**要不要补**需要你决定 —— 补了等于告诉 AI 一条绕过门禁的路，不补则它永远不知道边界在哪。

### 7.2 每条都带反例

只写"照手册做能成功"会得到**永远绿**的检查 —— 插件坏成什么样它都过。
所以每条同时断言：

- **正例**：手册说能做的，真能做；
- **反例**：手册说不能/不会发生的，真的不发生。

例：`_artifacts` 放行是正例；**`docs/` 下未读必须被拦**是反例 ——
没有这个反例，"`_artifacts` 放行"可能只是因为门禁根本没工作。

### 7.3 它自带反向验证（**这一条最重要**）

跑完所有检查后，脚本会把 `core/gate.js` 里「必读未读完」那条判据短路掉，
**重跑自己**，必须变红；红不了就自报 `❌ 自检失败` 并非零退出。

理由：**全绿本身就是可疑的**。本项目吃过三次"假绿"：
假注册表（`m28-fixes`）、假绿变异（锚点失效）、以及本检查器自己前面那 6 处误判。

### 7.4 我写这个检查器时误判了 6 次（**全部是我的错，不是手册的错**）

| # | 我以为是手册错 | 真相 |
|---|---|---|
| 1 | `doc_mark` 合法改动也失败 | 我拿 `scope` 当反例，而 `doc_mark` **不认** `scope`（那是 `doc_new` 的参数） |
| 2 | 「改完即变未读」不成立 | 那是 **M2.8 的 `selfWritten` 有意豁免**；手册没写边界（这条**确实是手册的缺口**，已补） |
| 3 | 七段缺两段不报 error | 我查 `issues`，而它返回 `errors` / `warnings`（`doc_health` 才是 `issues`） |
| 4 | H4 没报 | 同上，H4 在 `warnings` 里 |
| 5 | 顺序检查炸了 ENOENT | `boot({docs})` 只在 docs 为空时才自动建 `read-order`，我传了 docs 又去读它 |
| 6 | 外部改动不被发现 | **必须重跑 `step()`** 才会重扫注册表；光 `setTimeout` 不刷新缓存 |

⇒ **6 条里只有 1 条是手册真错。** 判据写错比没判据更危险 ——
它会让下一个人去改一份本来正确的手册。**每次误判我都先做最小复现再改。**
