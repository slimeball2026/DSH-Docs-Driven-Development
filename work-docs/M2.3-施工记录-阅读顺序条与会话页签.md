## 1. 需求 2：AI 阅读顺序条

### 1.1 做了什么

面板底部一条横向 chip 列表，显示**门禁强制 AI 要读的那批文档**及其已读状态。

| 项 | 落点 |
|---|---|
| 纯逻辑（可被单测 import） | `ddd-bundle/src/client/read-order.ts` |
| 组件 | `ddd-bundle/src/client/read-order-bar.tsx` |
| 挂载点 | `index.tsx` 的 `BodyWith` 新增 `footer` 入参，`BoardPage` / `BoardPanel` 各传一份 |
| 单测 | `ddd-bundle/test/client-read-order.test.js`（15 条） |
| 变异 | `_m23/mutate-read-order.mjs`（6 个变异，全 CAUGHT） |

### 1.2 三个设计决定（都有理由，别随手改）

**① 数据源是 `required`，不是 `all`**（用户 W3 拍板）。
`required` 就是「AI **被强制**要读的」，语义最准也最短。测试里钉了
`readOrderOf(snapshot.required)` 且 `doesNotMatch(readOrderOf(snapshot.all))`。

**② client 绝不重排顺序**。
顺序的真源在 host：`core/index.js` 的 `buildIndex()` 已经按 `order` 升序、同 order 按 id 字典序排好。
client 再排一次就会造出**第二套顺序** —— 条上的"第 3 篇"与索引块里的"第 3 篇"就不是同一篇。
变异 `reorder-by-order` 专门钉这条（改坏了必红）。

**③ 条挂在 `BodyWith` 的 footer，不是 `BoardPage` 里平铺**。
因为只有 `BodyWith` 知道"快照到底有没有到手"。挂在外面会在「还没选项目根」时
显示一个**假的 0/0 进度** —— 那正是本项目最怕的症状。

### 1.3 一处差点写进去的错

第一版我在 `BoardPage` 里这样传：

```ts
onOpenDoc: (item) => openDoc(controller, snapshot, { ...item, title: '', fingerprint: '', order: null, verifiedAt: null } as SnapshotDoc)
```

那是**伪造一个 `SnapshotDoc`**：把"我手上没有这些字段"伪装成"这些字段是空的"。
已改成拿 `id` 回快照里查（`snapshot.required.find(...)`），查不到就不开。
这条写进了 `read-order-bar.tsx` 的注释与测试说明里。

### 1.4 用户指出的视觉歧义：**一个 chip 上有两个圆**（2026-11-14，已修）
用户原话：

> 「截图里绿点指的应该是高置信度，右侧空着的白点才应该是 ai 读过的标识。」

**完全正确，而且这不止是文案问题。** 旧版每个 chip 长这样：

```
1 🟢 read-order ○
  ↑              ↑
  置信度           已读标识
```

- **`🟢` = 置信度**（`statusMarkOf(status)`，`authoritative` 就是绿）；
- **后面的圆点 = AI 读没读**。

三个错叠在一起：

| # | 错 | 后果 |
|---|---|---|
| 1 | 文案写「绿点 = AI 读过」 | 把**置信度**说成了**已读** |
| 2 | 已读画成**实心绿点** | 已读的 chip 变成 `🟢 … 🟢` **两个绿圆**，分不清 |
| 3 | 置信度徽标没有 `title` | 悬停也问不出"这个绿是什么" |

**修法（只改文案不够，三件事一起做）**：

| 改什么 | 改成 |
|---|---|
| 已读标记 | **`✓`**（形状，语义直白），**不再用绿色** |
| 未读标记 | **空心圆**（只有轮廓，无填充无颜色） |
| 文案 | `🟢 置信度 ｜ ✓ = AI 读过（你点开不算）` —— **明确分开说两者** |
| 置信度徽标 | 补 `title="置信度：<status>"` |

> **原则**：绿色**从此专属于置信度**。已读状态改用形状表达，
> 两者不占用同一个视觉通道 —— 色盲用户与灰度截图也分得清。

对应测试 2 条（`client-read-order.test.js`）+ 变异 2 条
（`read-mark-uses-green` / `old-legend-text`，均 CAUGHT）。

### 2.2 注册契约（**这一节是给下一个人省 1 天的**）

官方 `dsh-client-ui-sidebar-documentpreview` 是完整范例，照抄它的两段式：

```js
// 阶段①：类型（ctx.sidebarRightTabs 由 ui-sidebar-right 用 reflect.provide 提供）
ctx.sidebarRightTabs.register({
  id: '@local/ddd',            // 这个实现的唯一身份
  kind: 'ddd-board',           // 类型判别符（openTab 用它）
  priority: 'extension',       // 外部类型档（最高）
  // ⚠️ 不声明 patterns：我们是页面类型，由 kind 打开，不认领任何文件地址
  title: (address) => '文档驱动开发',   // ← 签名是 (address) => string，**不是 thunk**
  guide: [{ id, order, title: () => '…', description: () => '…' }],  // ← 这里才是 thunk
})

// 阶段②：正文 + ③：标题（keyed，键 = 上面那个 id）
ctx.slots.inject('sidebar.right.pane.tab', () => ctx.slots.register({
  name: 'sidebar.right.pane.tab', key: '@local/ddd', inject: (sessionId) => ({...}),
}, SessionTab))
ctx.slots.inject('sidebar.right.pane.tab.title', () => ctx.slots.register({
  name: 'sidebar.right.pane.tab.title', key: '@local/ddd',
}, DddTabTitle))
```

**三处键必须逐字一致**。不一致的症状是「点开页签一片空白」，而且**不报错**
（宿主判据：没有类型认领这个 kind → 渲染 owner 的 "nothing can view this" 提示）。

### 2.3 `sessionId` 与 cwd 从哪来（**交接文档说要摸 1–2 小时，实际已坐实**）

用活体 Slot 检查（`cordis_inspect_query` 的 client `Slots.listSubTree`，root = `sidebar.right.pane.tab`）
确认了该席位的 **standard props 里直接有**：

```
sessionId: SessionId
useSessions: SnapshotSelectorHook<WorkspaceSnapshot>
useResource / usePanelInfo / useChat / useSession / …
```

所以：

| 要什么 | 怎么拿 | 出处 |
|---|---|---|
| `sessionId` | 注册回调第一参 | 框架注入的 standard prop |
| cwd（首选） | `useSessions(state => state.byId[sessionId])?.cwd` | 框架绑定到当前会话的 hook |
| cwd（兜底） | `sessions.list.getSnapshot().byId[sessionId]?.cwd` | 官方 `ui-reference` L65/L168 的用法 |

两条都走一遍：hook 优先，根服务兜底。**两条都拿不到就返回空串**，由 UI 明说
"拿不到这个会话的项目目录"，**绝不猜目录**（猜错会显示别的项目的门禁读数）。

### 2.4 一个必须记住的取舍：**不声明 `patterns`**

我们是 `priority: 'extension'`（最高档）。若声明了 `dsh-resource://file/**` 之类的 glob，
就会把**所有文件预览**从 `documentpreview` 手里抢走 —— 那是严重回归。
测试与变异各钉一次（`patterns-steal-files` 变异必红）。

### 2.5 页签为什么一开始不出现（**已解决，保留供参考**）

第一轮用户刷新后**看不到页签**。当时排除了代码问题：

- 产物级验证 26/26 全过：`apply()` 不抛、双注册成对、页签类型/正文/标题三处注册齐全且键一致；
- 构建产物 `lib/client.js` 90 529 B，`inject: ["slots","sidebarRight","sidebarRightTabs"]`。

原因：`inject` 变更需要**重启 DSH** 才生效 —— 与 `M2-施工记录-宿主重载真相.md` 的结论一致：
`include:hmr` 只做模块级热替换，插件 fiber 不重建，`apply()` 不会重跑。

> **重启后页签出现，但随即暴露了一个更严重的问题**：切到新会话时右栏被整个炸空。

#### 5.2.1 关于 `defaultSeed()` 与"只剩一个胶囊"（**用户 2026-11-14 提出，已结案**）

用户原话：

> 「这个我没法确认，因为我没办法让它只剩一个胶囊，官方默认的『工作区文件』总要留着吧？」

**用户完全正确，而且这比"无法验证"更强 —— 这个风险在结构上不可能发生。**

源码判据（`dsh-client-ui-sidebar-right/src/client/contract/seed.ts` L26-33）：

```js
export function defaultSeed(tabs) {
  const [only, ...others] = tabs.guide()
  const single = only !== undefined && others.length === 0
  const kind = single ? only.kind : GUIDE_KIND   // ← 只有"恰好一个"才切换
  ...
}
```

也就是说：**`guide()` 返回 0 个或多个时，默认页恒为 `guide`**（指南页）。只有**恰好 1 个**胶囊时才换成那个胶囊。

而官方自带至少两张**常驻**胶囊（都在 `guide:` 数组里，无条件注册）：

| 包 | 胶囊 id | order |
|---|---|---|
| `dsh-client-ui-sidebar-files` | `workspace`（工作区文件） | 10 |
| `dsh-client-ui-sidebar-terminal` | `new`（新建终端） | 20 |
| **本插件 `@local/ddd`** | `construction-board` | 60 |

⇒ 胶囊总数**最少是 2**（files + terminal 是 profile 常驻），所以 `others.length === 0` **永不成立**，
`single` 恒为 `false`，默认页**恒为 `guide`**。

> **结论**：我们加胶囊**不可能**改变用户的右栏默认页。这条从"待验"改为"**已由源码证明**"。
>
> ⚠️ 反过来说：如果哪天用户把 files 或 terminal 从 profile 里禁用，只剩我们一个胶囊，
> 那时默认页会变成 DDD 看板。但那种情况下用户是有意精简右栏的，
> 而且 `defaultSeed` 是官方行为、不是我们的选择 —— 记在这里备查即可。

## 9. 最后一句

需求 2 是**第一次**把"AI 的阅读顺序"真正摆到人眼前 —— 那正是这个项目最初想让人看见的东西。
需求 3 的价值不在"多一个入口"，而在于**把插件放回了它本该在的位置**：有会话、有 cwd、能预览。

但这一轮也再次证明了同一条老教训：

> **测试全绿不等于功能可用。**
> 需求 2 的 8 项肉眼验收里有 2 项（可点手势、主题跟随）是**单测永远测不出来**的；
> 需求 3 则连撞两道 —— 先是"代码全对但 inject 没生效"（只能靠真机重启发现），
> 再是"页签出现了但把整个右栏炸空"（只能靠用户真点一下发现）。
>
> 而这两个问题**我的测试都没抓到**。测试抓不到它们不是测试写得差，
> 是**它们的失败模式在渲染期**，而我的断言都在源码与数据层。
> 唯一能补的是：**每加一块 UI，就让真人点一遍**。
