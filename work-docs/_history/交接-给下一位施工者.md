## 1. 我的意图（为什么做成现在这样）

### 1.1 为什么先做"约束器"而不是先做 UI

用户最初的设想是一个**可视化**的文档驱动工具（右栏树状图 + 交付网格 + 坟场散落窗口）。
评审后拍板 **Q1 = B：先做施工约束器**，理由有三条：

1. **可视化解决的是"看得见"，解决不了"AI 会不会照做"**。而后者才是这个插件的价值所在。
2. **UI 是换技术栈，不是加功能**。教练模式是纯 host 插件（只有 `index.js`，零构建）；一旦要右栏面板，就必须 host + client 双半侧，需要 `dsh.client` 声明、`lib/client.js` 构建产物、`PLATFORM_MODULES` 白名单、React 运行时。
3. **最核心的假设还没被验证**："结构化索引 + 强制读取"能不能让 AI 真的按文档施工？这条不成立，UI 做得再漂亮也是白做。

**所以 M0 一个 UI 都不做。** 这不是偷懒，是把不确定性最大的东西先测掉。

### 1.1b 为什么是"全局插件"而不是"新模式"（**S1，这条推翻了 v1.0**）

一开始我照抄了教练模式的形态——做成一个 preset。**这是错的，已改。**

- **插件管的对象是"项目"，不是"会话模式"**。一个仓库有没有 `docs/`、必读清单是什么，跟你在用标准模式还是别的模式**没关系**。
- 做成 preset 的后果就是**覆盖变小**：标准模式下干活时它不存在。
- 更糟的是：**preset 形态的门禁可以被绕过**——切回标准模式就没了。**能靠换模式逃掉的约束，本质上还是提示词。**

**所以 S1 = 全局插件（profile 级 bundle）。** 装载是全局的，**生效是项目级的**（靠激活标记，§1.1c）。

这也顺带解释了为什么全局挂载的代价可以接受：**M0 一个新增工具都不加**（Q13 = A）。
工具 schema 是每轮请求的固定 token 开销，是全局挂载的主要成本。零工具 = 没有 schema 开销。

### 1.1c 全局挂载的两个必要条件

**激活标记**（否则会误伤）：光有 `docs/` 目录不算 DDD 项目——一个普通代码仓库里刚好有个 `docs/`（没有 frontmatter），模型去改它就会被拦，这是不可接受的误伤。所以必须有标记：

- T1：`docs/` 下至少有一份**能解析出 `id`/`role`/`status`** 的 `.md`
- T2：`AGENTS.md` 里有 `<!-- ddd:index` 标记

**没有标记 → 整个插件对该项目 no-op。**

**子代理排除**（S2，否则会硬故障）：全局挂载会让 subagent 也生效。子代理通常只做一次局部任务，不需要"必读文档"纪律，而且**门禁会拦住它的正常写入，让它没法干活**——这是硬故障，不是体验问题。判据用 `session.header.origin`。


### 1.2 为什么门禁要"按路径拦"而不是"加个新工具"

这是评审里被推翻得最彻底的一处，**别再退回去**：

- 曾经的想法是加 `doc_update` 工具替代 `write`/`edit`。**这个想法是错的**，三个原因：
  1. **歧义**：两个工具都能改文件，模型会按习惯选。教练模式的实机日志里，模型在专用工具 `coach_research` 和通用 `web_search` 之间选了后者。
  2. **门禁会被静默绕过**：如果你把门禁建在 `doc_update` 上，模型用 `write` 改，**你不报错、只会发现文档没更新**。这比没有门禁更糟。
  3. **重复实现**：`write`/`edit` 已经做了定位、替换、原子写、diff 元数据、沙箱提权。
- **删掉 `write`/`edit` 也不可行**：`read` 不能关（要读代码），而 `read` 在、`write` 不在，模型会转向 `pwsh` 写文件——`guard` 拦不住"这条命令会不会写文件"。
- **正确做法**：保留 `write`/`edit`，用 `ctx.tools.guard()` 按**目标路径**拦。模型看到的工具目录**与标准模式完全一致**，零歧义。

### 1.3 为什么索引要拆成两条通道

- **慢变量**（必读清单、禁止清单、术语）→ `<项目>/AGENTS.md`，由 `dsh-agent-instructions` 自动注入。
- **快变量**（当前切片、进度、已读集合）→ `systemPrompt.context()`。

**关键机制事实**：`AGENTS.md` 的注入是"持久 user 消息 + digest 变化才追加替换"。**索引一变就多一条历史消息，旧的在压缩前一直留着。** 所以快变量放进去 = 每轮都在累积垃圾。

这是 **R3**，有验收用例 **M0-5** 专门盯它：连续 10 轮后，会话历史里只能有**一条**索引消息。

**`ctx.fs.watch()` 的已知行为**（`_ref\asar\...\dsh-fs\README.zh.md:38`）：

## 4. 坑（不要重犯）

### 4.1 环境类

| # | 坑 | 现象 / 处置 |
|---|---|---|
| 1 | **`node --test test/` 不可用** | Node 24 把目录当单个入口模块 → `ERR_UNSUPPORTED_DIR_IMPORT`。用 `--test --test-isolation=none` |

### 4.2 机制类

| # | 坑 | 事实 |

## 8. 最后一句

这个项目最容易犯的错，**不是"功能没做完"，而是"为了把清单打勾，造出一个模型走不出去的状态"**。

你的 M0 没有状态机，所以没有"卡死"的风险——这是好事，**别急着加**。

但你有另一个更容易犯的错：**为了让门禁"更严格"，去拦本来不该拦的东西**。
M0-3（未读就改 `src/` 必须放行）就是专门防这个的。**门禁漏一次只是少管一次，误伤一次会让模型没法干活。**
