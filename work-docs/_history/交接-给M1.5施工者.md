## 0. 这个项目是什么（**先读这一节，否则你不知道自己在改什么**）

> **三次三个人——所以这不是笔误，是模板缺一段**（见 `M1-评审报告.md` §十 的 N8，§三 有登记条目）。

### 0.1 一句话

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；「读没读」由插件记账并强制，不是靠提示词嘱咐。**

这是一个 **DSH 插件**，名字叫「文档驱动开发」（DDD，Document-Driven Development）。

> ⚠️ **DDD 在这里不是「领域驱动设计」**，是本插件名。这个缩写在本项目里**只有这一个意思**。

### 0.2 用户的原始设想（`Downloads\文档驱动开发架构设想.md`，25 行）

用户最初想要一个**可视化**工具：在 DSH 右栏画三个分区——

| 分区 | 设想中的样子 |
|---|---|
| **工作区** | 从左往右的树状图，文件按「阅读顺序文档」标定的顺序排列 |
| **交付成品** | 工作区下方的网格，只放 AI 的交付物 |
| **坟场** | 工作区上方散落的窗口，放已弃置的文档，**AI 平时不读** |

配套两个属性：**阅读顺序**与**文档置信度**（标绿/黄/红 + 原因）。

核心流程：**AI 不直接开工** → 先问清需求 → 做规划 → 产出文档 → **按文档施工** → 交接时更新阅读顺序与置信度。

> **用户原话里最有价值的一句**：「更建议写交接文档交给下一个会话」。
> 这不是一个功能，是**对「AI 会话是有限资源」的承认**——整份设计的动机都在这里。

### 0.3 评审之后，项目变成了什么

架构评审（`文档驱动开发-架构评审与补充设计-v1.md`，**以它为准**）做了三处根本性修正：

| 原设想 | 修正后 | 为什么 |
|---|---|---|
| 先做可视化 | **先做约束器，M0/M1/M1.5 零 UI** | UI 解决"看得见"，解决不了"AI 会不会照做"。后者才是价值 |
| 置信度写在散文里 | **frontmatter 元数据是真源，图是渲染** | 手写散文索引必然漂移 |
| 插件做成 preset | **全局插件，按项目激活**（S1） | 做成 preset 会让标准模式看不到它，**且门禁能被"切个模式"绕过** |

## 1. 我的意图

**M1.5 不是"再做一个切片"，是"把 M1 留下的坑填平"。**

我评审 M1 时发现：**14 条判据全部成立**（交接这条核心假设被证实了），
但**工程可用性上有 9 条独立缺陷**——**1 条阻塞**（N1，含 N1b）、**1 条架构级**（N9）、**4 条高**（N1b / N2 / N3 / N8），
其余 4 条中低（N4 / N5 / N6 / N7）。而且**它们全都不在 A4 的 14 条里**。

所以我的意图是：**先修能让用户项目"变成只读"的死锁，再谈交接排序**。
理由很直接——**一个把用户 docs/ 锁死的插件，交接排第几都没意义。**

我坚持的一条原则：**能证伪的修，不能证伪的不修。**
这条直接导致我否掉了两件事：D2 降级（"模型会跳过"不可证伪）、M1-14 不修（根因判断与我的实测矛盾）。

### 3.1 先修 N1（阻塞）：`docs/` 下无 frontmatter 的 md 被永久锁死

**改哪里**：`ddd-bundle/core/gate.js` 的 `id === undefined` 分支（第 116-131 行）。

**现在的问题**：`knownOf(path) === true` 时一律拒绝，理由是「先补上 id / role / status 等字段，再改它」——
**但补字段只能用 `edit`/`write`，而这两个被同一句话拒掉**。死锁。

**怎么改**：把 `unmanaged`（完全没有 `---` 开头）与 `broken`（有 `---` 但解析失败 / 字段非法）分开：

```js
// core/gate.js 第 116 行附近
if (id === undefined) {
  const known = typeof opts.knownOf === 'function' ? opts.knownOf(path) : true
  if (known !== true) return allow
  // ★ 新增：完全没有 frontmatter 的普通 md → 放行（它不参与索引，写它不破坏任何判据）
  if (opts.unmanagedOf?.(path) === true) return allow
  return { decision: GATE_DENY, reason: '...' }
}
```

> #### `unmanagedOf` 的数据从哪来（**别在这里卡住**）
>
> 一个常见的误解是"unmanaged 的文件不进任何清单，所以注册表里没有它，拿不到 `unmanaged` 标志"。
> **不是这样。** 我核过 `adapters/registry.js`：
>
> - **L53 的注释**：`/** 所有条目（含 unmanaged 与坏文档）。 */`
> - 也就是说 `entries` **包含** unmanaged 条目，只是 `core/index.js:54-57` 的 `buildIndex`
>   把它们从 `required` / `forbidden` / `anomalies` 三份清单里**排除**。
>
> 所以 `unmanagedOf` 的实现就是：
>
> ```js
> unmanagedOf: (path) => {
>   const abs = resolvePath(path, session)
>   return reg.entryByPath(abs)?.unmanaged === true
> }
> ```
>
> **它和现有的 `knownOf`（`gate.js:123` 已经在用 `reg.entryByPath`）是同一个数据源**，不用新开接口。

### 3.4 修 N5（中）：`minOrder` 只该在 handover 里取最小

### 3.5 修 D1 + D9（一起修，不能分开）

>

- 建两份交接，第二份不传 `order` → 它的 order **小于**第一份；

> 修法已由用户拍板：**索引块【项目】行为主 + §1 内容判据为辅，不加第 8 段**。
> 理由是**不加第 8 段**：H1 判"七段全部命中"，加第 8 段会让**所有现存交接一次性全挂**（dogfood / `_m1-drill` / `_m1-probe` / 交接给 M1 的那份），代价与收益不成比例。

#### 3.8.1 主修法：索引块加一行 `【项目】`

**改哪里**：`core/render.js` 的 `renderIndexBlock`（第 132 行 `const sections = []` 附近）。

**加什么**：

```js
// 【项目】行（N8）。**pinned：永不裁**，理由同【预算】——
// 它是"新会话知不知道自己在改什么"的唯一保证，被裁掉就等于没做。
const projectLine = typeof opts.projectLine === 'string' ? opts.projectLine : ''
if (projectLine !== '') sections.push({ key: 'project', text: projectLine, pinned: true })
```

**`projectLine` 从哪来**（`index.js` 里算，然后传给 render）：

```js
// 取法：项目里 role: index 的文档的 summary（它天然是"入口索引"）
// 拿不到就退到 role: spec 的第一份，再拿不到就不显示（不要瞎编）
function projectLineOf(registry) {
  const idx = (registry?.entries ?? []).find((e) => e?.meta?.role === 'index' && e?.meta?.summary)
  const spec = (registry?.entries ?? []).find((e) => e?.meta?.role === 'spec' && e?.meta?.summary)
  const pick = idx ?? spec
  if (pick === undefined) return ''
  return `【项目】${pick.meta.summary}`
}
```

**三条硬约束**：

1. **必须是慢变量性质但走 `context()` 通道**——按 R3 红线，**绝不能进 `AGENTS.md`**（那里一变更就多一条历史消息，M0-5 在盯这个）。索引块**就是** `context()`，所以合规。
2. **`pinned: true`**，不允许被 `fitBudget` 裁掉。
3. **拿不到就整行不显示**，`不要`写"（未知项目）"这类占位——那会变成永久噪声。

**验收**：新会话第一轮（`seq` 最小那条）的索引块里出现 `【项目】...`，且内容等于项目里 `role: index` 文档的 `summary`。

### 3.9 修 N9（**高，架构性**）：子代理只干工程活，`docs/` 只有主 agent 能改

#### 3.9.1 为什么必须改（**实测证据，不是推断**）

|---|---|
| `docs\subagent-probe.md` | **`Created file`，零拒绝** |
| `src\subagent-probe.txt` | `Created file`，零拒绝 |

**而且它不在索引里、不报异常**（我用真实 `parseFrontmatter` + `buildIndex` 复算：`unmanaged: true` → 不进 required、不进 anomalies）。

**所以：子代理能在 `docs/` 里造一份"主 agent 永远改不了、索引里也看不见"的文件。**

#### 3.9.2 改哪里

**主改动**：`adapters/guard.js` 第 39-47 行（现在 `if (!activated) return undefined` 一刀切放行）。

**改成**：

```js
// 子代理：S2 仍然不注入索引、不记 readSet，但**不许写 docs/**
// config.excludeSubagents 是**现有**配置项（默认 true）：它表示"S2 生效"。
// 也就是说：excludeSubagents === true → 子代理走下面这条分支；=== false → 维持旧行为（完全放行）。
if (isSubagentSession(session) && config.excludeSubagents !== false) {

```

> ⚠️ **命名提醒**：`excludeSubagents` 是**现有的**（`config.js:35`，语义 = "子代理不加载"），**不要新建**。
> 我在 §3 的新标识符表里提过一个 `subagentDocWriteMode`——**那是"可选的新开关"，可以不做**。
> **最简做法：直接用现有的 `excludeSubagents` 当开关**，不新增配置项。
> 只有当你需要"能单独关掉文档写拦截"时才加 `subagentDocWriteMode`（默认 true）。
> **两个名字别混用**——否则语义会打架（`excludeSubagents=false` 是"不排除"，`subagentDocWriteMode=false` 是"不拦截"，方向相反）。

**`decideSubagentWrite` 的判据**：

```
写类工具（write / edit / str_replace_editor / apply_patch）

其余（读、以及 src/ deliverables/ _artifacts/ 下的写）
  → 返回 undefined（放行）
```

**拒绝文案（照抄，含出路）**：

```
docs/ 下的文档只能由主 agent 改（S2：子代理不参与文档施工）。
你改的是文档，不是代码。请把「要改什么、为什么改」交回父会话，

#### 3.9.3 **三个实现难点**（别以为很简单）

| # | 难点 | 必须怎么处理 |
|---|---|---|
| **1** | **子代理的 `probe` 是 no-op**（S2 第一句返回 `hasMarker:false`） | `classify(path, session)` **拿不到项目根**，判不出路径是不是 `docs/` |
