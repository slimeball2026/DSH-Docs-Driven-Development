## 0. 这个项目是什么（**先读这一节**）

> 这一节被漏过三次（三个不同作者），所以由系统强制：索引块的 `【项目】` 行 + **H9** 判据。

**一句话**：

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；「读没读」由插件记账并强制，不是靠提示词嘱咐。**

这是一个 **DSH 插件**，名字叫「文档驱动开发」（DDD，**不是**领域驱动设计）。

### 0.1 它具体怎么工作

不是"提醒模型去读文档"，而是四件事拼起来的一个**约束器**：

| # | 环节 | 落点 | 一句话 |
|---|---|---|---|
| 1 | **激活判定** | `adapters/probe.js` | 向上探 `AGENTS.md`（含 `<!-- ddd:index`）或 `docs/` 下合法 frontmatter。**探不到 → 整个插件对该项目 no-op**，绝不误伤普通仓库 |
| 2 | **扫描建注册表** | `docs/scan.js` + `adapters/registry.js` | 把 `docs/**.md` 读成条目（meta / 指纹 / 是否有 error）。**坟场永不进索引** |
| 3 | **索引注入** | `adapters/inject.js`（走 `systemPrompt.context()`） | 每轮往模型上下文里塞一段清单：`【门禁】`/`【预算】`/`【项目】`/`【施工】`/`【已读】`/`【未读】`/`【禁止执行】`/`【文档异常】` |
| 4 | **门禁** | `adapters/guard.js`（`ctx.tools.guard()`） | 模型调 `write`/`edit` 打 `docs/` 时，**按路径**判：要改的那份读过没？role 允许写吗？**没读过就拒绝** |

**关键在 3 与 4 的分工**：3 只是"让人看见清单"，**4 才是那个 `if`**。
只有 3 就是提示词嘱咐（教练模式已证明会失效），只有 4 就是莫名其妙被拒。

### 0.2 用户的原始设想

用户最初想要一个**可视化**工具：DSH 右栏三个分区（工作区树状图 / 交付成品网格 / 坟场），
配「阅读顺序」与「文档置信度」（绿/黄/红 + 原因）。

核心流程：**AI 不直接开工** → 问清需求 → 规划 → 产出文档 → **按文档施工** → 交接时更新阅读顺序与置信度。

> 最有价值的一句：「**更建议写交接文档交给下一个会话**」。
> 这不是功能，是**对「AI 会话是有限资源」的承认**。

### 0.3 评审之后，项目变成了什么

架构评审（`文档驱动开发-架构评审与补充设计-v1.md`）做了三处根本修正：

| 原设想 | 修正后 | 为什么 |
|---|---|---|
| 先做可视化 | **先做约束器**，M0/M1/M1.5 零 UI | UI 解决"看得见"，解决不了"AI 会不会照做"。后者才是价值 |
| 置信度写在散文里 | **frontmatter 元数据是真源**，图是渲染 | 手写散文索引必然漂移 |
| 插件做成 preset | **全局插件，按项目激活**（S1） | preset 会让标准模式看不到它，**且门禁能被"切个模式"绕过** |

> **M2 是第一次让"外部观察者"能看见这个插件的内部状态。**
> 所以 M2 的 UI 如果显示了**错的数据**，比没有 UI 更糟 —— 它会把"错误的信任"可视化。

### 0.4 三条铁律

| # | 铁律 | 破坏了会怎样 |
|---|---|---|
| 1 | **门禁必须是代码里的 `if`，不是提示词嘱咐** | 退化成软约束（教练模式已证明会失效） |
| 2 | **全局挂载，项目级生效**（S1，不做 preset） | preset = 标准模式看不到 + 门禁能被切模式绕过 |
| 3 | **Q1–Q13 / R1–R5 / M1-Q1–M1-Q9 / P1–P14 / M2-Q1–M2-Q6 已冻结** | 改冻结决策必须有用户授权记录 |

### 0.5 术语

| 词 | 含义 |
|---|---|
| **DDD** | 本插件名。**不是**领域驱动设计 |
| **受管文档** | `docs/` 下带合法 frontmatter 的 `.md` |
| **unmanaged** | `docs/` 下完全没有 frontmatter 的 md。不进索引、不报异常，但可写 |
| **激活标记** | T1: 合法 frontmatter；T2: `AGENTS.md` 含 `<!-- ddd:index`。**没有标记 → 插件 no-op** |
| **坟场** | `docs/_graveyard/`，只读、不进索引、**平铺**（不递归） |
| **M0-5 红线** | 索引块**不得含快变量**（时间戳 / 轮次 / 百分比）。内容一变宿主就 append 一条新历史消息 |
| **双注册** | Q7 = C：`sidebar.panellist`（右栏入口行）+ `main`（主栏整页）。**少一个就白做** |

## 3. 三个待做需求（**用户要求先评估，他来决定**）

### 3.1 需求 1：修复"点文档打不开"

**结论：这不是 bug，是设计边界。已改成"明说"。**

#### 证据（源码级）

`dsh-client-ui-sidebar-right/src/client/service.ts` L854-864：

```js
private require() {
  const sessionId = this.mounted.getSnapshot()      // ← 屏幕上的会话
  const actions = sessionId === undefined ? undefined : this.actionsFor(sessionId)
  if (sessionId === undefined || actions === undefined) {
    throw new Error('sidebarRight: no session surface is mounted')
  }
  return { sessionId, actions }
}
```

右栏的所有席位（`sidebar.right.pane.tab` / `sidebar.right.tab.menu.item` …）都是 **`scope: 'session'`**
（`contract/slots.ts` L45/61/75/86/95/105）。

而 DDD 主栏是 **`main` 席位 = `scope: 'root'`**（`dsh-client-ui-layout` L75，
注释原文：「other keys receive no Session binding」）。

⇒ **root 面板上没有会话挂载 → 右栏不存在 → `openResource` 必抛。**

#### 已做的处理（**本轮已完成**）

1. 选择器下方**常驻**一行：
   `预览只能在会话页打开：本面板没有会话上下文（右栏是会话作用域的）。`
2. 文档行**不再显示可点击手势**（`cursor: default`，`opacity` 略降），
   `title` 改为「…（预览需在会话页打开）」
3. `openDoc` 仍保留完整逻辑（地址可解析性检查 + 失败留痕），供需求 3 复用

> 这符合铁律：**不让"看起来能点"和"点了会怎样"不一致。**

#### 顺带修掉的两个真问题（对需求 3 有用）

| 问题 | 修法 |
|---|---|
| `ctx.get('sidebarRight')` **恒定返回 undefined**（它是 `ctx.reflect.provide` 出来的，不在 Service 目录里） | 写进**插件级 `inject`**，用 `ctx.sidebarRight`（官方 `ui-reference`/`ui-chat`/`ui-plan` 都这么做） |
| `sessionId` 为空时地址**必然解析失败**（`parseFileAddress` 里 `id === ''` 直接返回 undefined） | 退回 **`absolute` scope**（`dsh-resource://file/absolute/<路径>`，不带会话） |

#### 工作量

**已完成，0 剩余。** 但"真的能打开"要等需求 3。

### 3.2 需求 2：底部横向"AI 阅读顺序"条（可收起到右下角）

#### 数据：**已有，零后端工作**

`GET /api/ddd/index` 的 `required` 数组**就是 AI 的阅读顺序**：

```jsonc
"required": [
  { "id": "read-order", "role": "index", "order": 0, "status": "authoritative", "read": false, ... },
  ...
]
```

- 顺序由 `order` 决定（host 侧 `core/index.js` 已排好）
- `read: boolean` 就是"读没读"（来自会话级 readSet）
- `gate: { read, required, ready }` 是汇总

⚠️ **一个需要你拍板的设计问题**：条上显示哪一批？

| 选项 | 含义 | 我的倾向 |
|---|---|---|
| `required` | 门禁必读的那批（AI **被强制**要读的） | ✅ **推荐**——它就是"AI 会进行的阅读顺序" |
| `all` 按 order | 全部受管文档 | 太长，且包含 AI 不需要读的 |

#### 工作量

| 项 | 估计 |
|---|---|
| 组件（横向 chip 条 + 收起按钮） | 1–2 小时 |
| 收起状态持久化（`localStorage`） | 15 分钟 |
| 单测（顺序正确、read 状态、收起/展开） | 30 分钟 |
| **合计** | **约 2 小时** |

#### 风险：**低**

纯新增 UI，不动数据层、不动门禁、不碰 host。

#### 实现要点

- 位置：`BoardPage` / `BoardPanel` 的**底部**，`position: sticky; bottom: 0`
- 每个 chip：`序号 · id · 状态点 · 已读/未读`
- 点 chip：走 `openDoc`（在 root 面板里**同样打不开**，所以要么复用"禁用点击"、要么等需求 3）
- 收起：缩成右下角圆形按钮（`position: fixed; right: 16px; bottom: 16px`）
- 样式：**必须用 `--dsw-alias-*` token**（见 §5 坑 #7）

### 3.3 需求 3：在会话页右侧栏也能看到这个页面

#### 为什么这个需求价值**远超**"多一个入口"

会话右侧栏是 **`session` scope**，那里：

1. **有 `sessionId`** → 预览能用 `session` scope 地址（更可靠）
2. **有 `cwd`**（`sessions.list.getSnapshot().byId[sessionId].cwd`）→
   **不需要再让用户手选项目根**！这是目前最别扭的设计
3. **有右栏** → `openResource` 能用 → **M2-3 判据自动通过**
4. `gate.read` 是会话级的 → 在会话页看才是**真正正确的读数**

> 换句话说：**需求 3 不只是加个入口，它把这个插件放回了它本该在的位置。**

#### 技术路径（已核实）

| 步骤 | 要点 |
|---|---|
| ① 注册 tab 类型 | `ctx.sidebarRightTabs`（`dsh-client-ui-sidebar-right` L182 `reflect.provide('sidebarRightTabs', tabs)`） |
| ② 注册 tab 正文 | keyed slot **`sidebar.right.pane.tab`**，键为 tab 类型 id（`contract/slots.ts` L42-45，`scope: 'session'`） |
| ③ 拿会话上下文 | 在 session scope 的注册回调里，框架**注入 `sessionId` 标准 prop**（`ScopeStandardProps`） |
| ④ 拿 cwd | `sessions.list.getSnapshot().byId[sessionId]?.cwd`（官方 `ui-reference` L68 就这么用） |
| ⑤ 复用 UI | 现有 `BoardPage` / `MainPage` / `Dashboard` 全部可复用，只需换数据源 |

**参考实现**：`@deepseek-ai/dsh-client-ui-sidebar-documentpreview` 是最完整的"tab 类型 + 正文"范例，
`dsh-client-ui-sidebar-right/src/client/index.ts` 的注释说它「is the live proof」。

#### 工作量

| 项 | 估计 |
|---|---|
| 摸清 `sidebarRightTabs` 注册契约（读 documentpreview 源码） | 1–2 小时 |
| 实现 tab 类型 + 正文注册 | 2–3 小时 |
| 会话上下文接线（sessionId → cwd → snapshot） | 1–2 小时 |
| 复用现有组件 + 去掉"手选项目根"分支 | 1–2 小时 |
| 单测 + 实机验证（**要重启**） | 2 小时 |
| **合计** | **约 1 天（7–9 小时）** |

#### 风险：**中**

| 风险 | 说明 | 缓解 |
|---|---|---|
| 注册契约不熟 | `sidebarRightTabs` 的 API 我**没读过**，只是从 `reflect.provide` 推断 | **先读 `documentpreview` 的完整实现**（它是官方范例） |
| 需要重启 | 新增 tab 类型要改 client bundle，刷新即可；但如果改 `inject` 就要重启 | 单变量 + 备份 |
| 双入口重复 | 左栏 root 面板 + 会话右栏，两份 UI 状态 | 抽出共享组件，数据源不同 |
| **可能推翻需求 1 的结论** | 如果右栏能用，root 面板的"禁用点击"要不要保留？ | **保留**——root 面板仍然没有会话，事实没变 |

#### 建议顺序

**先做需求 2（2 小时、零风险、立刻有用），再做需求 3（1 天、价值最大）。**

需求 3 做完后，**需求 1 的"打不开"会自然消失**（在会话页能开），
但 root 面板的禁用提示**仍应保留**（那里确实没有会话）。

## 4. 坑（**本轮新踩的，按代价排序**）

| # | 坑 | 代价 | 怎么避免 |
|---|---|---|---|
| 1 | **用错版本的源码解读日志** | 对着 rc.2 分析 rc.1，浪费大量推理 | **先确认版本再读栈**。crash log 里有 `app:` 行 |
| 2 | **`?.` 拦不住 cordis Proxy 抛错** | 读未声明服务**直接抛**，不是返回 undefined | 可选服务一律 `ctx.get(...)`；**硬依赖写进 `inject`** |
| 3 | **`ctx.get` 对 `reflect.provide` 的服务无效** | `sidebarRight` 恒为 undefined，预览永远降级 | 这类服务只能写进 `inject` 再 `ctx.xxx`。**用 `Service.listService` 查不到 ≠ 不存在** |
| 4 | **右栏是 session scope，root 面板没有** | "点了没反应"查了很久 | 先查**目标席位的 scope** 再决定能不能用 |
| 5 | **`notify()` 埋在异步函数里** | 受控组件不重渲染 | 要在同一次同步流程里通知 |
| 6 | **组件各自读 controller 却不订阅** | `ProjectPicker` 与 `BodyWith` 是两个订阅者，只改一个等于没改 | 每个读 controller 的组件都要 `useControllerState` |
| 7 | **主题 token 全写错（`--dsh-*` 是瞎编的）** | 一直用 fallback 硬编码色，主题切换不跟随 | 真实 token 是 **`--dsw-alias-*`**（用 client `Theme.listTokens` 查） |
| 8 | **`ctx.fs` 默认按会话 workspace 执行沙箱** | 写别的目录 `file access denied` | 必须传 `sandboxPolicyFor(projectRoot)` |
| 9 | **Windows `realpath` 返回 8.3 短名** | `SLIMEB~1` vs 长名，前缀比较误判越界 | 逐级找**最近存在的祖先**再比 |
| 10 | **空数组上的断言恒真** | `dogfood` 的 deliverables 是 0 条，"每条都有 presented"永远绿 | 先用夹具造真数据，再加一条「夹具真的读到数据」 |

## 9. 破了一条纪律（**已获用户授权，有记录**）

**边界**（`test/decoupling.test.js` 钉着）：

- 只允许 `server/mkdir-bridge.ts` 一个文件 import `node:`；
- 只允许 `node:fs/promises` + `node:path`；
- 必须有 `realpath` + `isInside` + 越界拒绝分支；
- 白名单文件若不再 import node:，测试会红（提示删白名单）。
