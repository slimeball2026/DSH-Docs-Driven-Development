## 0. 这个项目是什么（**先读这一节**）

> ⚠️ **这一节被漏过三次**（三个不同作者），所以它现在由系统强制：索引块的 `【项目】` 行 + **H9** 判据。
> **我不是靠记得。**

### 0.1 一句话

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；「读没读」由插件记账并强制，不是靠提示词嘱咐。**

这是一个 **DSH 插件**，名字叫「文档驱动开发」（DDD，Document Driven Development）。

> ⚠️ **DDD 在这里不是「领域驱动设计」**，是本插件名。这个缩写在本项目里**只有这一个意思**。

### 0.2 用户的原始设想

用户最初想要一个**可视化**工具：DSH 右栏三个分区（工作区树状图 / 交付成品网格 / 坟场），
配「阅读顺序」与「文档置信度」（绿/黄/红 + 原因）。

核心流程：**AI 不直接开工** → 问清需求 → 规划 → 产出文档 → **按文档施工** → 交接时更新阅读顺序与置信度。

> 最有价值的一句：「**更建议写交接文档交给下一个会话**」。
> 这不是功能，是**对「AI 会话是有限资源」的承认**。

### 0.3 评审之后，项目变成了什么

架构评审（`文档驱动开发-架构评审与补充设计-v1.md`）做了三处根本修正：

| 原设想 | 修正后 | 为什么 |
|---|---|---|
| 先做可视化 | **先做约束器**，M0/M1/M1.5 零 UI | UI 解决"看得见"，解决不了"AI 会不会照做"。后者才是价值 |
| 置信度写在散文里 | **frontmatter 元数据是真源**，图是渲染 | 手写散文索引必然漂移 |
| 插件做成 preset | **全局插件，按项目激活**（S1） | preset 会让标准模式看不到它，**且门禁能被"切个模式"绕过** |

### 0.6 现场事实（**这一轮更新了，与原文档不同**）

1. **工作区根 `DDD插件施工\` 不是 DDD 项目** —— 没有 `docs/`、没有 `AGENTS.md`。
   只有 `dogfood/`、`_m1-probe/`、`_m1-drill/`、`_review/proj-a/`、`_m15/live-proj/`、`_m15-live2/` 是。
   **改 `ddd-bundle\` 时插件对你是 no-op** —— 没有护栏，也没人挡你。
2. **改 `apply()` **必须重启** DSH —— 这条被实测确认过三次**。
   `plugin_manager` 的停用/启用**不会重跑 `apply()`**（删掉探针文件 → 停用 → 启用 → 文件没被重建）。
   **但**：改 `core/*.js` 这类**被 import 的模块**，HMR 会热替换，**立即生效**。
   区分标准：**`inject` 声明、`ctx.effect` 的注册、模块顶层的闭包捕获 —— 要重启；纯函数改逻辑 —— 不用。**
3. **`dsh.client` 是"全有或全无"的开关**（新增，代价最大的一条）：
   宿主 `clientModules` 服务的构造函数里，
   ```js
   const failures = [];
   this.flush((err) => failures.push(err));
   if (failures.length > 0) throw new ClientPackageCompositionError(failures);
   ```
   组合失败一次 → 这个**服务整体不存在** → 声明它的 entry 全部 `failed` → **宿主起不来**。
   这就是 SPEC §11 R-11 说的事，也是 **M2 这次事故的直接原因**。
4. **外部 HTTP 探测无法区分"路由在"与"路由不在"**：宿主认证发生在**路由匹配之前**，两者都返回 401。
   唯一判据是「重启后拿到 200」或「插件自己写探针」。

## 1. 我的意图

**本项目**是「文档驱动开发」插件（DDD）——一个让 AI 在改文档前必须先读过文档的约束器。

**M2 这一轮我要做两件事，第二件比第一件重要**：

1. 把七项 UI 做出来（A 看板 / B 预览 / C 图谱 / D 交付网格 / E 归档 / F 占用提醒 / G 预算出路）；
2. **换一次技术栈**：纯 `.js` host → **host + client 双半侧 + TypeScript**。

**为什么第二件更重要**：M0/M1/M1.5 已经把约束器做完了（门禁会拦、交接能校验、健康度能自检），
但**人看不见它在干什么**——用户只能问 AI「我现在能改哪份文档？」，然后祈祷 AI 说的是对的。

> **M2 是第一次让"外部观察者"能看见这个插件的内部状态。**
> 所以 M2 的 UI 如果显示了**错的数据**，比没有 UI 更糟——
> 它会把"错误的信任"可视化。这正是 M2-Q1 要求先把 M1.5 三个条件修完的原因。

**我这一轮做完了什么、没做完什么**，下一节说。但我的意图里有一条贯穿始终、值得你继承的：

> **每一条数据都要能追到它的真源。追不到就留空——留空比显示一个猜的数字好。**

这条在 M2 里被我执行成了三处具体决定：
`nextStep`/`basisDoc` 取不到就**不显示**；`presented` 拿不到会话事件就**标 `presentedKnown: false`**；
`slice` 为空就**整行不出现**（不写「（未知）」）。

### 4.1 `dsh-cuigengji-plugin` 的处理**值得参考**（**这一条很有用，别跳过**）

我原以为 `skill-explorer` 是最佳参考（它也是 `panellist` + `main` 双注册）。
但 **`dsh-cuigengji-plugin` 更值得看**，因为**它就是在侧边栏直接显示、UI 量很大的插件**：

```
~/.dsh/profiles/desktop/node_modules/dsh-cuigengji-plugin/
├── package.json          ← dsh.client 的完整写法（6 个 inject）
├── lib/client.js         ← 真实的 __ModuleLoader__ 产物（101 KB 级）
└── runtime/index.js      ← host 入口
```

**它一次帮我排掉了两个错误怀疑**：

| 我一度怀疑 | 它的反证 |
|---|---|
| "`dsh.client.inject` 里写 `@deepseek-ai/dsh-client-ui-sidebar` 不存在于 profile，会失败" | 它注入的正是 `ui-sidebar` + `ui-sidebar-right`（`dsh-context` 也注入 `ui-sidebar-right`） |
| "我的 bundle 外壳形态不对" | 它的头尾与我的**逐字同形**：`window.__ModuleLoader__.load({id:"…",factory:(require)=>{var module={exports:{}};var exports=module.exports; … return module.exports;}})` |

**为什么它比 `skill-explorer` 更适合当模板**：
`skill-explorer` 是**第三方包**（`@linxin666/*`），它的写法可能带着自己的约定；
`cuigengji` 是**同类本地插件**（自己写 host + 自己构建 client + 直接显示在侧边栏），
而且它的 `package.json` 里连 `scripts` 都写清了构建方式（`node scripts/build.mjs`）。

> ⚠️ **它是 `enabled: false` 状态**（不在 profile 的 `bundles` 里），所以**不能直接跑起来看**。
> 但它的**文件就是最好的样板**：`package.json` 的 `dsh` 段、`lib/client.js` 的头尾、
> 以及它注入的 6 个包名（那 6 个名字证明了"注入 sidebar 包是合法的"）。

**用法**：攻 client 侧之前，先
```powershell
Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\dsh-cuigengji-plugin\package.json" -Raw
Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\dsh-cuigengji-plugin\lib\client.js" -TotalCount 3
```
拿它和你自己的产物**逐字对照**。**比"看起来对不对"可靠得多。**

**我选择挂起，而不是再赌一次让你的宿主起不来。**

> **SPEC §11 R-11 已经写了处置方案——「在 `cordis.patch.yml` 里先不声明 `dsh.client`（分两轮上）」。**
