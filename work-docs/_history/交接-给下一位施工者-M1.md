## 0. 这个项目是什么（**先读这一节，否则你不知道自己在写什么**）

> 上一版交接漏了这一节，是评审指出的缺口。**如果你只读一节，读这节。**

### 0.1 一句话

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；「读没读」由插件记账并强制，不是靠提示词嘱咐。**

这是一个 **DSH 插件**，名字叫「文档驱动开发」（DDD，Document-Driven Development）。
**注意：DDD 在这里不是「领域驱动设计」**，是本插件名。

### 0.2 用户的原始设想

用户想做的其实是一个**可视化**工具：在 DSH 右栏画三个分区——

| 分区 | 设想中的样子 |
|---|---|
| **工作区** | 从左往右的树状图，文件按「阅读顺序文档」标定的顺序排列 |
| **交付成品** | 工作区下方的网格，只放 AI 的交付物 |
| **坟场** | 工作区上方散落的窗口，放已弃置的文档，**AI 平时不读** |

配套两个属性：**阅读顺序**（AI 初次工作按什么顺序读）和**文档置信度**（每份标绿/黄/红 + 原因）。

核心流程：**AI 不直接开工** → 先问清需求 → 做规划 → 产出文档 → **按文档施工** → 交接时更新阅读顺序与置信度。

> **用户原话里最有价值的一句**：「更建议写交接文档交给下一个会话」。
> 这不是一个功能，是**对「AI 会话是有限资源」的承认**——整份设计的动机都在这里。
> **你正在读的这份交接文档，就是那个需求的实物。**

### 0.3 评审之后，项目变成了什么

架构评审对原始设想做了几处**根本性修正**，最重要的三条：

| 原设想 | 修正后 | 为什么 |
|---|---|---|
| 先做可视化（右栏三区） | **先做约束器，M0/M1 零 UI** | UI 解决"看得见"，解决不了"AI 会不会照做"。而后者才是价值所在 |
| 置信度写在"树状图文档"的散文里 | **frontmatter 元数据是真源，图是渲染** | 手写散文索引必然漂移 |
| 插件做成 preset | **全局插件，按项目激活**（S1） | 插件管的对象是**项目**，不是**会话模式**。做成 preset 会让标准模式的会话看不到它，**且门禁能被"切个模式"绕过** |

### 0.4 三个切片

| 切片 | 内容 | 状态 |
|---|---|---|
| **M0** | 索引（必读清单进上下文）+ 门禁（没读完不许改 `docs/`） | ✅ **已实现、已评审、已修复** |
| **M1** | 交接（模板/校验/演练）、`doc_health`、冷启动预算、4 个工具 | ⬜ **你要做的这一刀** |

**为什么是切片而不是一次做完**：因为最核心的假设还没被验证完——
「结构化索引 + 强制读取」能不能让 AI 真的按文档施工？M0 证明了「会先读」，**M1 要证明「交接接得住」**。

### 0.5 术语表（读 SPEC 前先扫一眼）

| 词 | 含义 |
|---|---|
| **DDD** | 本插件名（Document-Driven Development）。**不是**领域驱动设计 |
| **切片 M0/M1/M2** | 分批交付的梯度。**不是**"阶段" |
| **项目根** | 带激活标记的目录，里面有 `docs/` / `deliverables/` / `_artifacts/` |
| **受管文档** | `docs/` 下带合法 frontmatter 的 `.md` |
| **激活标记** | 判定"这是不是 DDD 项目"的依据（T1: 合法 frontmatter；T2: `AGENTS.md` 里有 `<!-- ddd:index`）。**没有标记 → 插件 no-op** |
| **索引块（L0）** | 每轮注入模型上下文的清单：已读/未读/禁止执行/文档异常 |
| **慢变量 / 快变量** | 慢的写 `AGENTS.md`（必读清单）；快的走 `systemPrompt.context()`（已读集合） |
| **门禁（gate）** | `ctx.tools.guard()` 里按**路径**拦截：`docs/` 下的文档没读过，改它就被拒 |
| **坟场** | `docs/_graveyard/`，只读，不进索引，`glob`/`grep` 结果里会被剔除 |
| **role / status** | 文档的两种封闭枚举：role 决定写权限，status 决定能不能当依据 |
| **sealed** | 「原地封存」：内容有诱惑力但已被推翻，**没有替代品** |
| **superseded** | 有明确替代品，可以直接跳过。**与 sealed 不是一回事** |
| **S1 / S2** | S1 = 全局插件不做 preset；S2 = 排除子代理会话 |
| **Q / R** | Q1–Q13 = 产品级决策；R1–R5 = 落地细节。**全部已拍板，冻结，不许重开** |
| **M1-Q1–M1-Q9** | M1 新增的 9 条决策，见 SPEC §2.1 |

## 2. 我的意图（为什么 M1 是这样设计的）

### 2.1 为什么 M1 只有五个目标

因为**M0 的成功经验是「克制」**：6 个目标、0 个新工具、0 行 UI → 14 条验收全过、298 单测。

M1 如果把「交接 + 健康度 + 预算 + 工具 + 跨会话状态」全塞进来，就会变成「什么都做了一点，没有一个能验收」。

所以 SPEC §1.1 只列了五条，且**每条都有一个能被拒绝的判据**（M1-C 那条「交接失败会被拒绝」是刻意的）。

### 2.2 为什么我推翻了原交接对工具数量的倾向

上一任交接 §4.2 P2 说「**加 `doc_new` + `doc_mark`，`doc_health` / `doc_handover_check` 看情况，M1 最多用 2 个**」。

**我改成 4 个全加**（SPEC §2.2）。最关键的理由是第三条：

> **`doc_handover_check` 必须是工具，因为它要「拒绝」。**
> 一条 shell 命令拒绝不了模型——只有工具返回错误、或 `guard` 返回字符串，才能。

这一条如果错，M1-C（「交接失败会被拒绝」）就没法验收。**而这个目标是 M1 存在的理由之一。**

### 2.3 为什么 `readSet` 跨会话用「旁路文件」而不是「日志折叠」

上一任交接 §4.2 P1 和我自己的直觉都是「从会话日志折叠」。**但那个 API 现在不能用了。**

`dsh-session` 的 README 原文 `[实测]`：

> `eventAt()`、`snapshotEvents()` 和 `ownEvents()` **已弃用**：现有逻辑可以暂不迁移，但**禁止新增生产调用**。

替代品 `ctx.sessionQuery.readSession(id)` 有两个问题：
1. **它可能没挂载**（headless / SDK 组合就没有）；
2. **它回放整个日志并校验**——在 434 步的会话上每次调用都要付完整检查。

而交接**必须在任何部署形态下都能工作**。所以 SPEC §3.4 选了旁路文件（`_artifacts/ddd/read-state/`）。

> ⚠️ **这是本 SPEC 里我最不确定的一处**。它引入了「插件往项目里写文件」的新行为。
> 我在 SPEC §3.4 留了降级方案：**如果评审认为风险太大，可以砍掉整个跨会话 readSet**——
> 代价是交接的痛点只解决一半，但**不影响其它四个目标**。
> **你开工前先确认这一条**，别默默实现。

### 2.4 为什么 `doc_health` 只留 5 项，且 H-5 是我加的

架构评审 §3.6 列了 9 项。我砍到 5 项，砍掉的两项理由：

- **「冷启动预算超限」**→ 它不是「健康度」是「成本」，挪到索引块（M1-E）；
- **「文档内部数字是否一致」+「关键数字多处不一致」**→ **不可靠**。文本里的数字一致性判断必然误报，**没有可证伪的判据**。

**H-5（`basis: 未验证` 但 `status: authoritative`）是我新增的**，也是我认为 M1 最该有的一条：

> M0 的 `basis` 字段**只被解析、从未被使用**。一个填了却没人看的字段，等于没填。

### 2.5 我坚持的三条边界

1. **零 UI**。M1 一个像素都不做。UI 是 M2，且那是换技术栈。
2. **慢变量不许加速变量**。M1 新增的交接状态、健康度、预算**一律不进 `AGENTS.md`**（M1-Q4）。
   理由：`dsh-agent-instructions` 的注入是持久追加，一变就多一条历史消息——**这正是 M0-5 在盯的东西**。
3. **每个工具都要能被拒绝**。只测成功路径等于没测门禁（架构评审 §5 的原话）。

### 2.6 我刻意没做的事

| 没做 | 为什么 |
|---|---|
| **没写一行 M1 实现代码** | 我是评审者。SPEC 由「马上要写代码的人」来写，他会不自觉地写出自己好实现的东西 |
| **没做 `amends` 字段** | 附录 B1 里有，但**没有任何验收能证伪它**。加进来只是字段膨胀 |
| **没做自动交接触发** | Q6 = C 已冻结。且自动触发需要判断「什么时候该交接」，那个判断本身不可靠 |
| **没把 `doc_health` 做成 UI 红点** | M2 |
| **没做「批量改状态」** | `doc_mark` 一次一份。批量会让「改状态要读过」这条约束失效 |
| **没实现「交接模板自动生成」** | 模型照着 SPEC §4.2 的七段结构写就行。自动生成模板会把「写什么」变成「填空」，反而降低质量 |
| **没改 `M0-验收报告.md` 的 A1** | 那是被评审对象。A1（M0-11 的「附带更强证据」论证不成立）应由你或用户决定怎么处理 |
| **没修 R1**（索引块 `【已读】` 重复） | 不阻塞 M1。但它在 `render.js` 里，你改【预算】行时会看到它——**顺手修掉也行，但记得加反向断言**（`assert.equal(text.split('【已读】').length - 1, 1)`） |

## 5. 坑（**不要重犯**）

### 5.1 机制类（我替你验过的，别再花时间重新论证）

| # | 事实 | 出处 |
|---|---|---|
| 1 | **`snapshotEvents()` / `eventAt()` / `ownEvents()` 已弃用**，禁止新增生产调用 | `[实测]` dsh-session README |
| 2 | 替代品 `ctx.sessionQuery.readSession` **可能没挂载**，且**回放整个日志** | `[实测]` dsh-session-query README |
| 3 | **`register(def, { when })` 的 `when` 抛错 = `TOOL_ACTIVATION_FAILED`，中止步骤准备** | `[实测]` dsh-tools README |
| 4 | 宿主对工具 schema 做**无损 JSON 快照**，有 `undefined` 就整轮失败 | `[实测]` coach-mode v0.3.4 事故 |
| 5 | **不能用 `defineTool`**（要 import `@deepseek-ai/dsh-tools`），必须自己写 | M0 的 `decoupling.test.js` 强制 |
| 6 | 原始 `ToolDefinition` = `{ name, description, parameters, output:{schema, render}, execute }` | `[实测]` coach-mode `define-tool.js` |

### 5.2 项目惯例（M0 期间形成的，**别破坏**）

### 5.3 M1 特有的坑

| # | 坑 | 表现 |
|---|---|---|
| 13 | **`when` 条件里读盘** | 条件必须同步。读盘会让每个步骤都付 IO 成本，而且抛错会中止步骤 |

## 7. 三个最容易犯的错（**SPEC §14 的展开**）

1. **为了「更完整」加第 5 个工具**。Q13 的上限是 4，M1 已用满。想加时先问：
   「`guard` 拦不住吗？现有 4 个表达不了吗？」两个都「否」就别加。
2. **把交接状态塞进 `AGENTS.md`**。慢变量只放清单。塞进去会让它每次交接都变，
   而 `dsh-agent-instructions` 是持久追加——**一变就多一条历史消息**。这正是 M0-5 在盯的。
3. **`when` 条件里读盘或抛错**。每步骤求值一次，抛错中止步骤准备（M1-L8）。

## 8. 对抗性审查：用子 agent 当「第二双眼睛」

> **这一节是用户拍板的用法。** 子 agent **不参与写实现**，只用来挑错。

### 8.1 为什么这么做

本机可用子 agent 的模型**和你我同一个**（`beichenapi/deepseek-v4.1-flash`），
所以子 agent **不会比你更聪明**。它唯一的价值是：**不共享你的盲点**。

M0 那次评审证明了这件事：评审者独立复核，抓出了实现者自己没发现的 3 个缺陷（D1/D2/D3）。
而**写 SPEC 的我本人**也在 H3 判据上栽过一次——自己写的判据自己验，验的是"我以为的"而不是"实际的"。

### 8.2 什么时候派（**每个模块写完、跑绿之后**）

| 时机 | 派给它的输入 | 要它回答 |
|---|---|---|
| `core/handover.js` 写完 + 测试绿 | SPEC §4.2–§4.3 全文 + 你的实现 + 测试文件 | 「举出 3 份**能通过你的校验但不该通过**的 handover」 |
| `core/health.js` 写完 + 测试绿 | SPEC §6 全文 + 你的实现 | 「H-1–H-5 哪一条会误报？举反例」 |
| 4 个工具写完 + 冒烟绿 | SPEC §5 全文 + 你的工具定义 | 「哪个参数组合能让它写坏文件 / 绕过门禁？」 |
| **全部完成后**（最重要） | `M0-评审报告.md` + 你的 M1 验收报告 | 「按 M0 那次评审的标准，这份验收报告哪里站不住？」 |

### 8.3 怎么派（**任务说明必须自带全部上下文**）

子 agent **不继承你的对话**（除非用 `subagent_fork`）。所以任务说明要写成自包含的：

```
【背景】你在审查一个 DSH 插件「文档驱动开发」的 M1 实现。它的目的是让 AI
改项目文档前必须先读过该读的文档。M1 做的是「交接」——一份 handover 文档
必须通过校验才算合格。

【你的任务】不是写代码，是挑错。读下面三段材料，然后回答一个问题：
  「举出 3 份**能通过这套校验、但不应该通过**的 handover 文档。」

【材料 1】SPEC §4.2 七段结构（贴全文）
【材料 2】core/handover.js 实现（贴全文）
【材料 3】test/handover.test.js 测试（贴全文）

【输出格式】
  反例 1：<文档全文> → 为什么它能通过 → 为什么它不该通过
  反例 2：...
  反例 3：...

【判据】如果你举不出 3 个，直接说「举不出」，不要凑数。
```

> ⚠️ **两个坑**：
> 1. **别让它改文件**。任务说明里明写「只读、不写」。两个 agent 同时改文件会互相覆盖。
> 2. **别问「这个实现好不好」**。那种问题会得到「总体不错，建议加强测试」这类空话。
>    要问**具体的、可证伪的**问题（「举反例」比「评估质量」有用一个数量级）。

### 8.4 拿到反例之后

**别急着改代码**。先判断：

| 反例的类型 | 怎么办 |
|---|---|
| **确实能通过但不该通过** | 改判据（优先）或加测试把它钉住 |
| **能通过且通过是合理的** | 在 SPEC/README 里记下「这是已知的宽松处」，**别假装它不宽松** |
| **反例本身不成立** | 记一句「审查者误判」，**别为了迎合它改坏设计** |

> 最后一条很重要：**审查者也会错**。它的价值是「提出你没想过的问题」，不是「它的结论一定对」。
> M0 的评审里也有过这种情况——我在 M0-12 的归因上就留了「有歧义」而没有硬下结论。

### 8.5 递归深度

本机 `maxDepth: 2`（用户设的），意味着**你的子 agent 还能再派一层**。
**不建议用第二层**——审查者再派审查者，收益递减且协调成本陡增。一层足够。

## 9. 最后一句

M0 之所以能验收得干净（14/14、307 单测），是因为它的范围**只有 6 个目标、0 个新工具、0 行 UI**。

M1 的范围比 M0 大：**5 个目标、4 个工具、1 个新的写入路径（旁路文件）**。
这是不可避免的——交接本来就需要工具。**但「大」不等于「可以松」**。

> **判断标准始终是同一条**：**每条验收都要能证伪。**
> M0-5 的教训就在这——一个不可达的判据等于没有判据；
> 而 M1 最容易犯的同类错误是**「看起来严格但永远通过」的校验**（比如只查七段标题在不在）。

**所以：写完 `doc_handover_check` 的第一件事，是造一份「七段齐全但 §3 全是空话」的 handover，看它会不会被拒。**
如果它通过了，那这个工具就没有存在的意义。
