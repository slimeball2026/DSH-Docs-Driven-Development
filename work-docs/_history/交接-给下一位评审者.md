## 0. 这个项目是什么（**先读这一节，否则你不知道自己在评审什么**）

### 0.1 一句话

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；"读没读"由插件记账并强制，不是靠提示词嘱咐。**

这是一个 **DSH 插件**，名字叫「文档驱动开发」（DDD，Document-Driven Development）。

### 0.2 用户的原始设想（`Downloads\文档驱动开发架构设想.md`，25 行）

用户想做的其实是一个**可视化**工具：在 DSH 右栏画三个分区——

| 分区 | 设想中的样子 |
|---|---|
| **工作区** | 从左往右的树状图，文件按"阅读顺序文档"标定的顺序排列，点开看全文 |
| **交付成品** | 工作区下方的网格，只放 AI 的交付物 |
| **坟场** | 工作区上方散落的窗口，放已弃置的文档，**AI 平时不读** |

配套两个属性：**阅读顺序**（AI 初次工作按什么顺序读）和**文档置信度**（每份文档标绿/黄/红 + 原因）。

核心流程是：**AI 不直接开工** → 先问清需求 → 做规划 → 产出这几类文档（阅读顺序 / 规格 / 工程记录）→ **按文档施工** → 交接时更新阅读顺序与置信度，把过时的扔进坟场。

> **用户原话里最有价值的一句**：「更建议写交接文档交给下一个会话」。
> 这不是一个功能，是**对"AI 会话是有限资源"的承认**——整份设计的动机都在这里。

### 0.3 评审之后，这个项目变成了什么

架构评审（`文档驱动开发-架构评审与补充设计-v1.md`）对原始设想做了几处**根本性修正**，其中最重要的三条：

| 原设想 | 修正后 | 为什么 |
|---|---|---|
| 先做可视化（右栏三区） | **先做约束器，M0/M1 零 UI** | UI 解决"看得见"，解决不了"AI 会不会照做"。而后者才是价值所在。且 UI 是**换技术栈**（host + client 双半侧），不是加功能 |
| 置信度写在"树状图文档"的散文里 | **frontmatter 元数据是真源，图是渲染** | 手写散文索引必然漂移（示例文档里"共 11 份"vs 实际 15 个文件） |
| 插件做成 preset（像教练模式） | **全局插件，按项目激活**（S1） | 插件管的对象是**项目**，不是**会话模式**。做成 preset 会让标准模式的会话看不到它，**且门禁能被"切个模式"绕过** |

**所以现在这个项目分三个切片**：

| 切片 | 内容 | 状态 |
|---|---|---|
| **M0** | 索引（必读清单进上下文）+ 门禁（没读完不许改 docs/） | ✅ **已实现、已实机验收（14 条），待你评审** |
| **M1** | 交接（模板/校验/演练）、`doc_health` 自检、冷启动预算、少量工具 | ⬜ **你要写它的 SPEC** |
| **M2** | 全部 UI（右栏看板、图谱、交付网格、坟场归档、占用提醒） | ⬜ 未开始 |

### 0.4 为什么是"切片"而不是"一次做完"

因为**最核心的假设还没被验证**：

> 「结构化索引 + 强制读取」能不能让 AI 真的按文档施工？

如果这条不成立，后面所有 UI 都白做。**所以 M0 一个 UI 都不做、一个新增工具都不加**（Q13 = A），只验证这一条。

M0 的成绩（14 条全过、298 单测）说明这条**基本成立**——但它的验收质量要你复核。

### 0.5 参考项目：教练模式

同一个用户上一个插件叫「教练模式」（`@local/coach-mode`，v0.4.4，171 单测）。

DDD 的**方法论**几乎全是从它继承的：

| 教练模式的做法 | DDD 的对应 |
|---|---|
| 状态从会话日志折叠 | 文档状态从 frontmatter + `tools/result` 记账 |
| `coach_verify` 四条前置条件（代码里的 if，不是提示词） | `core/gate.js` 七条裁决 |
| 每轮状态块（`systemPrompt.context()`） | 索引块（同一机制） |
| 验收以日志为准（会话 id + `seq`） | 同 |
| **"能写进代码 if 的，不写进提示词"** | 同 |

**但它有两点 DDD 刻意不学**：
1. **它是 preset** —— DDD 是全局插件（S1）
2. **它的状态块每轮都变**（含"已完成 1/11 → 2/11"）—— DDD 的索引块**只由文档状态决定**，这正是 M0-5 判据修订的由来

### 0.6 术语表（读后面几节前先扫一眼）

| 词 | 含义 |
|---|---|
| **DDD** | 本插件名（Document-Driven Development）。**不是**领域驱动设计 |
| **切片 M0/M1/M2** | 分批交付的梯度。**不是**"阶段"（示例项目里的另一种划分） |
| **项目根** | 带激活标记的目录，里面有 `docs/` / `deliverables/` / `_artifacts/` |
| **受管文档** | `docs/` 下带合法 frontmatter 的 `.md` |
| **激活标记** | 判定"这是不是 DDD 项目"的依据（T1: 合法 frontmatter；T2: `AGENTS.md` 里的 `<!-- ddd:index` 标记）。**没有标记 → 插件 no-op** |
| **索引块（L0）** | 每轮注入模型上下文的清单：已读/未读/禁止执行/文档异常 |
| **慢变量 / 快变量** | 慢的写 `AGENTS.md`（如必读清单）；快的走 `systemPrompt.context()`（如已读集合） |
| **门禁（gate）** | `ctx.tools.guard()` 里按**路径**拦截：`docs/` 下的文档没读过，改它就被拒 |
| **坟场** | `docs/_graveyard/`，只读，不进索引，`glob`/`grep` 结果里会被剔除 |
| **role / status** | 文档的两种封闭枚举：role 决定写权限，status 决定能不能当依据 |
| **sealed** | 「原地封存」：内容有诱惑力但已被推翻，**没有替代品**。09/10/11 就是典型 |
| **superseded** | 有明确替代品，可以直接跳过。**与 sealed 不是一回事** |
| **S1 / S2** | S1 = 全局插件不做 preset；S2 = 排除子代理会话 |
| **Q / R** | Q1–Q13 = 产品级决策；R1–R5 = 落地细节。**全部已拍板，冻结，不许重开** |

### 0.7 三条绝对不能动的（**评审时也必须守**）

> 这三条不是"实现细节"，是**这个项目之所以成立的前提**。你可以质疑实现，不能质疑它们——除非用户重新拍板。

| # | 铁律 | 破坏了会怎样 |

| 3 | **Q1–Q13 / R1–R5 / S1–S2 已冻结** | 每开一次会重新讨论一遍，等于没有决策台账 |

| **P3** | **交接触发与"交接质量"怎么验收？** | 架构评审 §2.3(c) 列了 6 条判据，其中"冷启动演练"最硬但最难自动化 | **冷启动演练必须做**。判据：新会话第一轮能复述"目标 + 下一步 + 依据文档 id" |

| **P5** | **`doc_health` 的检查项** | 架构评审 §3.6 列了 9 项（索引指向不存在的文件、孤儿文档、循环 supersedes、超 TTL 未复核……）。**注意：TTL 已被 Q5 否决，那一项要去掉** | 从 9 项里挑 5–6 项，**每条都要有真实案例**（示例文档里有现成的：05 的索引列了个不存在的文件） |

| **P7** | **M1 的验收编号** | R5 定了 `M0-1` 起。M1 用 `M1-1` 起？还是延续 `M0-15`？ | **`M1-1` 起**，与切片对齐 |

### 4.3 写 M1 SPEC 时该守的三条

1. **M1 不是"把剩下的都做完"**。对照架构评审 §5 的 M0/M1/M2 划分，**M1 只做交接与验收**，UI 全部推 M2。
2. **别为了"更完整"加工具**。Q13 = A 的上限是 4 个，M0 用了 0 个，M1 **最多用 2 个**。
3. **每条验收都要能证伪**。M0 的 M0-5 教训就在这——一个不可达的判据等于没有判据。

## 8. 最后一句

这一轮的核心不是"再验一遍 M0 能不能跑"，而是**判断"通过"这个结论本身可不可信**。

M0 的实现质量看起来不错（298 单测、6 个真 bug 被自己抓到、4 处订正都写了理由）。**但这正是最需要警惕的地方**：

> **一个诚实的实现者，也可能在"判据达不到"的时候选择"改判据"，而不是"改实现"。**
> 他在 README 里把这个过程写得很清楚——**这是加分项，不是免检项。**

你的价值不在于说"通过"，而在于说清楚：**哪一处我信了，哪一处我要求补证据，哪一处我认为该打回。**

然后，写 M1 SPEC 时记住 M0 的成功经验：**克制**。
M0 之所以能验收得这么干净（14 条全过、单测 298），是因为它的范围只有 6 个目标、0 个新工具、0 行 UI。
**M1 要保持同样的克制。**
