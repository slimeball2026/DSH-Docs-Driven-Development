# SPEC · 文档驱动开发插件 v1（M1 切片：交接与验收）

> **项目是什么**（只读本文件的人也必须知道）：这是一个 **DSH 插件**，叫「文档驱动开发」（DDD，**不是**领域驱动设计）。
> 它让 **AI 在改项目文档之前必须先读过该读的文档**，「读没读」由插件记账并在 `guard` 里用 `if` 强制，不是靠提示词。
> 插件**全局挂载**（profile 级 bundle，不做 preset），但**只在带激活标记的项目里生效**——没有标记 → 整个插件 no-op。
> 用户原始设想是个可视化工具（右栏三区：工作区树 / 交付网格 / 坟场），**评审把它改成「先做约束器、UI 推到最后」**：
> UI 解决"看得见"，解决不了"AI 会不会照做"。切片：**M0 = 索引+门禁（已完成）｜M1 = 交接（本文件）｜M2 = UI**。
> **完整的项目背景、术语表、三条铁律**见 `交接-给下一位施工者-M1.md` §0。

> **状态**：**v1.0**，2026-11-11。**决策已全部拍板**（M1-Q1–M1-Q9），本文件是 M1 的施工图。
> **上游输入**：`文档驱动开发-架构评审与补充设计-v1.md`（v7）§5 的 M1 划分 + 附录 B2/B3；`SPEC-M0-文档驱动开发插件.md` v1.1；`M0-评审报告.md`。
> **前置**：**M0 已通过评审**（`M0-评审报告.md` §九），D1/D2/D3 已修复，307 单测全绿。
> **切片边界**：M1 = 交接 + 自检 + 预算 + 4 个新工具。**仍然零 UI**（全部推 M2）。
> **基线（本机实测，2026-11-11）**：DSH **`0.2.2-rc.1`**；Node **`24.21.0`**；`@local/ddd@0.1.0` 已装、`application: applied`。

## 0. 一句话

> **让「交接」从「写一份文档」变成「一份能通过校验、能被冷启动复述、失败会被拒绝的产物」。**

M0 证明了「AI 会先读文档」。M1 要证明的是**下一件事**：

> **上一个会话丢掉的东西，能不能被下一个会话无损接住。**

M0 结束时的状态是：索引会注入、门禁会拦、慢变量会更新。但**交接仍是人肉**——写一份 handover、改一下 `AGENTS.md`、祈祷下个会话读得懂。
M1 要把这条链路变成**可校验的数据结构 + 一个能被拒绝的验收**。

## 1. 目标与非目标

### 1.1 目标（五条，多一条都不要做）

| # | 目标 | 一句话验收 |
|---|---|---|
| **M1-A** | **交接文档可校验** | handover 文档的七个必填段落缺一段 → `doc_handover_check` 报 error，交接被拒 |
| **M1-B** | **冷启动可复述** | 新会话只靠索引 + handover，**第一轮**就能复述「目标 + 下一步 + 依据文档 id」，不需要追问 |
| **M1-C** | **交接失败会被拒绝** | 只测成功路径等于没测门禁——必须有一条「交接不达标 → 明确拒绝」的用例 |
| **M1-D** | **文档健康度可自检** | `doc_health` 能查出 5 类真实问题（每条都有 dogfood 里的真实案例） |
| **M1-E** | **冷启动预算可见** | 索引块显示「必读总计 ≈ Nk tokens」，超预算报警 |

### 1.2 非目标（明确不做）

| 推迟项 | 归属 | 原因 |
|---|---|---|
| **任何 UI**（右栏看板、图谱、交付网格、坟场归档） | M2 | Q1 = B；M2 是换技术栈 |
| 交接触发的**自动阈值**（占用 40%/55% 提醒） | M2 | Q6 = C，纯客户端 |
| 坟场**归档动作**（勾选/移动/还原） | M2 | Q12 = C，需要 UI |
| **`doc_health` 的 UI 红点** | M2 | 本切片只出工具输出 |
| 跨会话 `readSet` 的**完整恢复** | **M1 只做「读过的指纹」**，不做「读过的正文」 | 见 M1-Q1 |
| 段落级 `sections` 的**批量编辑 UI** | M2 | `doc_mark` 只做单次结构化写入 |
| git 快照 / 回滚 | 后续 | Q8 = A，但 M1 不依赖它 |
| `amends` 字段 | 不做 | 附录 B1 里有，但**没有任何验收能证伪它**，加进来只是字段膨胀 |

### 1.3 判断标准

> 任何一条实现如果**不在上面五个目标里**，就属于范围蔓延，退回。
> **M0 的克制必须保持**：M0 用了 0 个新工具，M1 最多用 **2 个**。

## 2. 决策台账（**冻结，不要重开**）

### 2.1 M1 新增决策（M1-Q1–M1-Q9）

> 这些是**交接文档里 P1–P7 那七个问题**的裁决。每条都给了理由，理由比结论重要。

| # | 问题 | 拍板 | 理由 |
|---|---|---|---|
| **M1-Q1** | **`readSet` 要不要跨会话恢复？** | **恢复「已读指纹」，不恢复「已读正文」** | 交接的核心痛点是「新会话不知道上个会话读过什么」。但恢复正文会让内存占用随会话线性增长，且正文随时可能过期——恢复指纹就够：门禁只需判断「你读的那一版还在不在」。**具体机制见 §3.4** |
| **M1-Q2** | **`doc_new` / `doc_mark` 该不该加？** | **只加这两个**，`doc_health` / `doc_handover_check` **也加**（共 4 个，用满 Q13 上限） | 原交接倾向「只加两个、其余做成普通命令」。**不采纳**，理由见 §2.2 |
| **M1-Q3** | **交接触发与「交接质量」怎么验收？** | **交接只能由用户发起**；质量验收 = 七段校验 + 冷启动演练**两条都要** | Q6 = C 已定「不由 AI 发起」。冷启动演练是**最硬的判据**，但必须写成可复现的协议（§7.3） |
| **M1-Q4** | **`AGENTS.md` 的写回时机** | **保持「慢变量才写」**；M1 新增的交接/健康度状态**一律不进慢变量** | D1 修复后写入通道已经通了。M1 如果往里塞快变量，等于把 M0 刚修好的东西再弄坏 |
| **M1-Q5** | **`doc_health` 的检查项** | **5 项**，从架构评审 §3.6 的 9 项里挑 | 挑的标准：**每条都要有真实案例，且能用现有数据结构判定**。见 §6 |
| **M1-Q6** | **段落级 `sections` 的写入格式** | **`doc_mark` 用结构化参数写**，不让模型手写流式 JSON | M0 的 `sections: [{"anchor":"#7",...}]` 人能写但很丑，且**手写 JSON 是错误来源**。工具收 `{id, anchor, status, reason}`，内部序列化 |
| **M1-Q7** | **M1 的验收编号** | **`M1-1` 起**（与切片对齐，不从 `M0-15` 续） | R5 定了 `M0-1` 起。切片对齐比连续编号更重要——`M1-1` 一眼能看出属于哪个切片 |
| **M1-Q8** | **4 个工具怎么注册？** | **必须用 `register(def, { when })` 条件注册** | SPEC-M0 §2.3 末尾的连带要求。全局挂载下，无条件注册会让工具出现在**所有人的所有会话**里。`when` 条件抛错会 `TOOL_ACTIVATION_FAILED` 中止步骤准备——所以条件里**只能读同步缓存，不能抛** |
| **M1-Q9** | **交接的「下一步」怎么变成可校验的？** | **只校验「含 ≥1 条具体路径或工具名」**，不校验语义正确性 | 语义正确性不可自动化。宁可弱一点但**可证伪**，也不要一个「看起来严格但永远通过」的检查 |

### 2.2 为什么 M1-Q2 推翻了原交接的倾向

交接文档 §4.2 P2 的倾向是「**加 `doc_new` + `doc_mark`，`doc_health` / `doc_handover_check` 看情况**」，并说「M1 最多用 2 个」。

**我改成 4 个全加**，三条理由：

1. **Q13 的上限就是 4 个，且已经点名了这四个**。架构评审 §2.5 第三层的原话是「上限 4 个：`doc_new` / `doc_mark` / `doc_handover_check` / `doc_health`」。**少用不等于克制，等于把已经论证过的设计打折**。
2. **「用普通命令实现」在这个架构里是错的**。`doc_health` 要读全部受管文档、跑 V1–V10 校验、跨文档比对 supersedes 图——这些能力**已经在注册表里了**。让模型用 `pwsh` 去实现，等于把结构化数据降级成文本解析，而且**必然与插件内部的判定不一致**（两份真源）。
3. **`doc_handover_check` 必须是工具**，因为它要**拒绝**。拒绝是 `guard` 或工具返回错误才能做的事，一条 shell 命令拒绝不了模型。

> **代价**：4 个工具 = 4 份 schema = 每轮固定 token 开销。**对冲手段**：`when` 条件注册（M1-Q8），只在探测到项目根且非子代理时可见。
> 这是 SPEC-M0 §2.3 早就写好的要求，M1 只是**第一次真正用上它**。

## 3. 已核实的机制事实（**不要重新论证**）

> 全部在本机 `app.asar` 提取的 README 或实跑中确认。**M1 的整个设计建立在这几条上。**

### 3.1 工具注册

| 事实 | 落法 | 出处 |
|---|---|---|
| `ctx.tools.register(definition, { when })` | `when` **每步骤计算一次**，返回 false 从描述/PTC/执行集合中排除 | `[实测]` dsh-tools README |
| **`when` 条件抛错 = `TOOL_ACTIVATION_FAILED`，中止步骤准备** | 条件里**只能读同步缓存**，且**必须自己 try/catch** | `[实测]` 同上 |
| `when` 收到 `{ agent, modelSelection, signal }` | 从 `agent.session` 拿会话，判 S1/S2 | `[实测]` 同上 |
| 原始 `ToolDefinition` 形状：`{ name, description, parameters, output: { schema, render }, execute }` | **不需要 `defineTool`**，直接给原始 JSON Schema | `[实测]` coach-mode `tools/define-tool.js` |
| 宿主对工具 schema 做**无损 JSON 快照** | 对象里**不许有 `undefined`**（漏写 `description` → 整轮 `request/header` 写盘失败） | `[实测]` coach-mode `test/tool-shape.test.js` 的 v0.3.4 事故记录 |
| 注册由 effect 持有 | 用 `ctx.effect()` 包住注册 | `[实测]` dsh-tools README |

> ⚠️ **M0 的一条硬约束在 M1 变成真的风险**：`decoupling.test.js` 禁止 import `@deepseek-ai/*`，所以**不能用 `defineTool`**。
> M1 必须**自己写一个极小的 `defineTool` 等价物**（编译「属性表 → 原始 JSON Schema」），或直接手写 schema。
> **建议照抄 coach-mode 的 `tools/define-tool.js` 思路**（约 150 行，零依赖，且它是被 171 个单测验过的）。

### 3.2 会话日志读取（**M1 最重要的机制发现**）

| 事实 | 影响 |
|---|---|
| **`session.snapshotEvents()` / `eventAt()` / `ownEvents()` 已弃用** | 「现有逻辑可以暂不迁移，但**禁止新增生产调用**」——`[实测]` dsh-session README 原文 |
| 替代品是 `ctx.sessionQuery.readSession(id)` / `filterEvents(id, filters)` | 需要 `inject` 里加 `sessionQuery`，且**它可能没挂载**（headless/SDK 组合） |
| `readSession` **回放整个日志并校验**，大历史每次都要付完整检查 | 不能在 `pre-step` 里每轮调 |
| `session.seq` 拿长度是**允许的**（未弃用） | 只读长度的场景用它 |
| `filterEvents` 返回**语义事件文档**，不是原始 JSON | 折叠 `readSet` 用它最合适 |

> **这条推翻了一个隐含假设**：M0 SPEC §9.2 写「M1 可考虑从会话日志 `snapshotEvents()` 折叠出 readSet」。
> **那个 API 现在不能用于新代码。** M1 必须走 `ctx.sessionQuery`，且**必须有「拿不到 sessionQuery」的降级路径**。

### 3.3 可用的既有机制（**不要重造**）

| 机制 | M1 怎么用 | 不要做什么 |
|---|---|---|
| `dsh-agent-instructions` | 继续承载慢变量 | 不要自己往上下文里塞必读清单 |
| `dsh-tool-present` + `deliverables/presented` | 交接产物用 `present` 声明 | 不要自建交付物模型 |
| `ctx.sessionProjections` | 交接状态可以做成投影供 M2 的 UI 读 | 本切片**不注册投影**（M2 才需要） |
| `dsh-goal` | **不要**用它表达交接 | goal 是「长期目标」，交接是「一次性的状态转移」 |

### 3.4 `readSet` 跨会话恢复的正确形态（M1-Q1 的落地）

**不做的事**：不读日志、不扫磁盘、不猜。

**做的事**：**把「已读指纹」写进 frontmatter 旁边的一个旁路文件**——但**不是** frontmatter（Q3 要求 frontmatter 是真源，但「谁读过」不是文档属性，是会话事实）。

```
<项目>/_artifacts/ddd/read-state/<sessionId>.json
  {
    "sessionId": "...",
    "at": "2026-11-11T21:00:00Z",
    "reads": { "spec-tier2": "8c6246", "read-order": "a371b0" }
  }
```

**为什么是旁路文件而不是日志折叠**：
1. 日志折叠依赖 `ctx.sessionQuery`，它**可能没挂载**（§3.2）——而交接必须在任何部署形态下都能工作；
2. `readSession` **回放整个日志**，在 434 步的会话上代价不可接受；
3. 旁路文件在 `_artifacts/` 里，**R4 规定永不自动删**，正好。

**恢复语义**：
- 新会话启动时，若找到 `<项目>/_artifacts/ddd/read-state/` 下的**最近一份**（按 mtime），把它折进 `readSet`；
- **指纹过期即失效**：折进来的记录若与当前指纹不符，视为未读（与 §9.3 的 M0 语义一致）；
- **不跨项目**：路径按项目根隔离；
- **写入时机**：`tools/result` 记账后**节流写**（同 `AGENTS.md` 的节流思路，默认 5s 合并）。

> **⚠️ 这条要在 M1 开工时重新评估**：它引入了「插件往项目里写文件」的新行为。
> 如果评审认为风险太大，**降级方案是「M1 不做跨会话 readSet」**——但那会让交接的痛点只解决一半。
> **本 SPEC 选择做，但把「写旁路文件」限制在 `_artifacts/`（过程产物目录）里，且失败只 warn。**

## 4. 交接的数据模型

### 4.1 交接文档是什么

**一份 `role: handover` 的 `docs/**.md`**，`order` 最小（永远排第一），`status: authoritative`。

> **不新建目录、不新建存储**。交接就是一份文档——这是 Q3（frontmatter 是真源）的直接推论。

### 4.2 七段结构（B2 模板的落地版）

**必须存在的二级标题**（按顺序，但允许中间插别的小节）：

| # | 标题关键词（正则） | 必须非空 | 判据 |
|---|---|---|---|
| §1 | `我的意图` / `为什么` | ✅ | 至少 1 个段落，且不是「无」 |
| §2 | `现在到哪了` / `现状` | ✅ | 至少 1 个**表格行**或列表项 |
| §3 | `下一刀` / `下一步` / `接下来` | ✅ | **≥1 条含具体路径 / 工具名 / 命令**（见下，M1-Q9） |
| §4 | `坑` / `不要重犯` | ✅ | 至少 1 个表格行 |
| §5 | `验收` | ✅ | 每条都要有**证据形式**（会话 id + seq / 哈希 / 测试输出） |
| §6 | `刻意没做` / `负向范围` | ✅ | 至少 1 个列表项 |
| §7 | `仍未决` / `需要拍板` | ⚠️ 可为空，但**必须显式写「无」** | 区分「忘了写」与「确实没有」 |

**为什么 §1「意图」排第一**（架构评审 B2 的原话）：现状可以从代码和日志重建，**意图不能**。

#### §3 的判据细节（**我预演过，第一版漏了一种情况**）

「具体」= 满足**任一**：

| 形态 | 正则 | 例子 |
|---|---|---|
| 路径 | `/[\\/]/` 或 `/\.\w{1,5}\b/` | `core/render.js`、`ddd-bundle/test/` |
| 工具名 | 白名单 `\b(write\|edit\|read\|pwsh\|bash\|glob\|grep\|present\|doc_new\|doc_mark\|doc_health\|doc_handover_check)\b` | 「用 `doc_new` 建一份 spec」 |
| **命令** | 反引号包住且含空格或 `--`：/`` `[^`]*\s[^`]*` ``/ | **`` `node --test --test-isolation=none` ``** |

> **第三行是自查时补的**：第一版只有「路径」和「工具名」两种，
> 结果「跑 `node --test --test-isolation=none`」这条**合法且非常具体的下一步会被误拒**。
> 我写了 11 条样例跑了一遍（7 条该拒、4 条该过），这条是唯一失手的。
> **执行者请照抄这三条，并把这 11 条样例做成 `handover.test.js` 的用例。**

### 4.3 校验规则（`doc_handover_check`）

| # | 规则 | 级别 |
|---|---|---|
| H1 | 七个段落标题都能匹配到 | **error** |
| H2 | §1/§2/§4/§6 段落非空（去掉标题后正文非空白） | **error** |
| H3 | §3 至少 1 条含具体路径（`\` 或 `/`）**或**工具名（`write`/`edit`/`read`/`pwsh`…） | **error** |
| H4 | §5 每条验收都有证据形式（含 `seq` / `session-` / `哈希` / `测试` 等关键词） | **error** |
| H5 | §7 若为空，正文里必须出现「无」 | **warn** |
| H6 | 存在**多份** `role: handover` 且都是 `authoritative` | **warn**（建议把旧的标 `superseded`） |
| H7 | handover 的 `order` 不是当前最小 | **warn** |

> **H3 与 H4 是 M1 唯一「语义」判据**，也是最容易被写成「永远通过」的两条。
> **反例测试必须包含**：§3 写「继续做下一步」（无路径无工具名）→ **必须被拒**。

### 4.4 交接的完整流程

```
用户说「交接」/ 点了 M2 的按钮
        ↓
模型调用 doc_handover_check（只读，不改任何东西）
        ↓
   ┌─ error 存在 → 返回错误清单，**拒绝交接**（模型必须去补）
   └─ 通过 → 返回「可以交接」
        ↓
模型写 handover 文档（用 write 新建，或 edit 已有 draft）
        ↓
模型调用 doc_mark 把新 handover 的 status 设为 authoritative、order 设为 0
        ↓
（慢变量通道）rescan → onIndexChanged → AGENTS.md 重写（D1 已修，自动生效）
        ↓
新会话冷启动 → 索引块里有 handover → 模型先读它 → 能复述目标/下一步/依据
```

> **注意「交接不是写文档就完」**：`doc_handover_check` **在写之前**跑，`doc_mark` **在写之后**跑。
> 这个顺序是刻意的——**先证明能达标，再允许落盘**。反过来（先写再检查）会让「不合格的交接」短暂存在于索引里。

## 5. 四个工具

### 5.0 共同约定

- **全部用 `register(def, { when })` 条件注册**（M1-Q8）；
- `when` 条件：`hasMarker && hasProjectRoot && !isSubagent && requireMarker`，**内部 try/catch，绝不抛**；
- 全部返回**结构化 JSON**（`output.schema`），文本由 `render` 生成；
- 全部**不加 `description` 里没有的东西**（v0.3.4 事故：`undefined` 会让整轮失败）；
- **`doc_health` / `doc_handover_check` 是只读的**；`doc_new` / `doc_mark` 会写文件。

### 5.1 `doc_new` —— 新建一份带合法 frontmatter 的文档

**为什么必须是工具**：`write` 表达不了「生成一个 id 唯一、字段齐全、order 自动插值的 frontmatter」。
让模型手写 frontmatter，等于让它每次重新发明 schema——而 schema 错了会进 `anomalies`。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `role` | enum（8 个） | ✅ | |
| `title` | string | ✅ | |
| `summary` | string ≤80 | ✅ | |
| `id` | string | ❌ | 不填则从 title 派生 kebab-case + 去重 |
| `order` | number | ❌ | 不填则取当前最大 order + 10 |
| `status` | enum | ❌ | 默认 `draft` |
| `basis` | enum | ❌ | 默认 `未验证` |
| `scope` | string[] | ❌ | `status: partial` 时必填 |
| `body` | string | ❌ | 正文初始内容 |

**行为**：
1. 校验 `role` / `status` / `basis` 枚举；
2. `id` 冲突 → 返回错误（**不自动改 id**，因为 id 永不变）；
3. 写入 `docs/<id>.md`（**走 `ctx.fs`，不走 guard**——它是插件自己的写）；
4. **创建项目目录**（`docs/` `deliverables/` `_artifacts/`）——**补 M0-A 没做的一半**（评审 §五 补充发现）；
5. 触发 `rescan()`。

> **`doc_new` 必须触发 rescan**——否则会踩 M0 的 D2（新建文档永不被发现）。

### 5.2 `doc_mark` —— 结构化改状态

**为什么必须是工具**：`edit` 做字面替换改 `status` 太脆（M0 的 `roles.js` 甚至禁止 `evidence`/`handover` 被 edit）。
而且 `sections` 是流式 JSON，**手写必然出错**（M1-Q6）。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | 目标文档 |
| `status` | enum（6 个） | ❌ | 文档级状态 |
| `anchor` | string | ❌ | 段落级状态的目标锚点（`#7`） |
| `sectionStatus` | enum | ❌ | 段落级状态 |
| `reason` | string | ❌ | **改 `sealed` / `void` 时必填**（Q12：AI 必须给理由） |
| `supersededBy` | string[] | ❌ | `status: superseded` 时必填 |

**行为**：
1. 至少要给 `status` 或（`anchor` + `sectionStatus`）之一；
2. **改 `sealed` / `void` 必须带 `reason`**，且 reason 会被写进文档正文的一个 `<!-- ddd:mark ... -->` 标记块（可追溯）；
3. **只改 frontmatter，不动正文**（除了那个标记块）；
4. 触发 `rescan()`。

> **`doc_mark` 不能绕过门禁**：它仍然要求目标文档**已被读过**（与 `write`/`edit` 同一条规则）。
> 理由：改状态就是改文档的语义，没读过就改等于凭想象改。

### 5.3 `doc_handover_check` —— 交接校验（只读）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ❌ | 指定哪份 handover；不填则取 `order` 最小的那份 |

**返回**：`{ ok: boolean, errors: [...], warnings: [...], sections: {...} }`

**行为**：跑 §4.3 的 H1–H7。**不写任何文件。**

### 5.4 `doc_health` —— 健康度自检（只读）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `scope` | enum | ❌ | `all`（默认）/ `errors`（只看 error） |

**返回**：`{ ok, issues: [{ rule, level, docId, message }], stats: {...} }`

**检查项见 §6。**

## 6. `doc_health` 的 5 项检查（M1-Q5）

> 从架构评审 §3.6 的 9 项里挑。**挑的标准：每条都有真实案例，且能用现有数据结构判定。**
> **明确排除的两项**：
> - 原第 9 项「冷启动预算是否超限」→ **挪到索引块**（M1-E），它不是「健康度」而是「成本」；
> - 原第 3 项「同一份文档内部数字是否一致」与第 8 项「关键数字多处不一致」→ **不可靠**。文本里的数字一致性判断必然误报，且**没有可证伪的判据**。

| # | 检查项 | 判据 | dogfood 里的真实案例 |
|---|---|---|---|
| **H-1** | **`supersededBy` 未反填** | `A.supersededBy` 含 B，但 `B.supersedes` 不含 A | **5 条**（V8 warn 已有，`doc_health` 把它提升为一等公民） |
| **H-2** | **`superseded` 链断掉 / 循环** | 顺着 `supersededBy` 走，走不到一个非 `superseded` 的文档；或回到起点 | 需检查（dogfood 的 12→13 是单向的，正常） |
| **H-3** | **孤儿文档**（`authoritative` 但不在必读清单） | 排除 `_graveyard/`、`draft`、`void` | 需检查 |
| **H-4** | **`authoritative` 但 `verifiedDsh` 与当前环境不符** | V9 已有，这里**汇总**成一条 | dogfood 里 `spec-tier1` 冻结在旧版本 |
| **H-5** | **`basis` 与 `status` 自相矛盾** | `basis: 未验证` 但 `status: authoritative` | **M0 完全没检查这个**——而它是最有价值的一条：**没验证过的结论不该被当成权威** |

**输出排序**：error 优先，同级按 `docId` 字典序（保证输出稳定，便于 diff）。

> **H-5 是本 SPEC 唯一新增的检查项**，也是我认为 M1 最该有的一条。
> 理由：M0 的 `basis` 字段**只被解析、从未被使用**。一个填了却没人看的字段，等于没填。

## 7. 冷启动预算与演练

### 7.1 预算（M1-E）

**索引块新增一行**（只在这一行变的时候才变，符合 R3）：

```
【预算】必读 7 份 ≈ 28.4k tokens（上限 30k）
```

**`tokens` 从哪来**：
1. frontmatter 里显式写了 `tokens` → 用它；
2. 没写 → **估算**：`Math.ceil(正文字符数 × 0.75)`（中文按 1 字 ≈ 0.75 token，保守取整）；
3. **不写回 frontmatter**（写回会让每次读都改文件）。

**超预算**：`≈ Nk` 后加 `⚠️ 超出上限`，并在 `AGENTS.md` 里保持原样（**慢变量不放动态数字**）。

> ⚠️ **预算行的稳定性**：它只由「必读集合 + 各文档 tokens」决定。
> **不许**把「已读了几份」这种快变量混进来——那是 M0-5 的红线。

### 7.2 冷启动演练协议（M1-B / M1-C 的核心）

**这不是自动化测试，是一份可复现的协议**。理由：它要验证的是「模型能不能复述」，只能靠真实会话。

```
准备：
  1. 一个 DDD 项目，有 handover、有必读清单
  2. 一个**全新会话**（不是 fork），cwd 指向该项目

执行：
  3. 第一轮只发一句：「这个项目现在到哪了？下一步做什么？依据是哪几份文档？」

判据（三条全中才算通过）：
  a. 复述出**目标**（与 handover §1 的意图一致）
  b. 说出**下一步**（与 handover §3 一致，且不是「我先看看」这类空话）
  c. 引用**至少 2 个具体的文档 id**（来自必读清单）

失败模式（必须记录）：
  - 追问「你指哪个项目」→ 索引没进上下文（S1 失效）
  - 说「我先读一下文档」→ 索引里没给清单，模型只能自己找
  - 复述与 handover 不一致 → 交接文档本身有问题
```

### 7.3 交接失败必须被拒（M1-C）

**只测成功路径等于没测门禁**（架构评审 §5 的原话，来自示例 A3/A4/A14-d 的教训）。

必须有的反向用例：

| # | 造什么 | 判据 |
|---|---|---|
| **M1-9** | 一份缺 §3 的 handover | `doc_handover_check` **拒绝**，指出缺哪段 |
| **M1-10** | 一份 §3 只有「继续做下一步」的 handover | **拒绝**，指出「没有具体路径或工具名」 |
| **M1-11** | 一份 §5 没有证据形式的 handover | **拒绝** |
| **M1-12** | 两份都是 `authoritative` 的 handover | **warn**（不拒绝，但要点名） |

### 10.5 对抗性审查（用户拍板的用法，**不是可选项**）

> 本机可用子 agent 的模型**与执行者同一个**（`beichenapi/deepseek-v4.1-flash`），
> 所以子 agent **不会更聪明**。它唯一的价值是**不共享执行者的盲点**。
> M0 的评审证明了这件事（独立复核抓出 3 个实现者自己没发现的缺陷）。

**四道审查，每道都在对应模块跑绿之后：**

| # | 时机 | 要它回答的问题 | 产物 |
|---|---|---|---|
| **A1** | `core/handover.js` + 测试绿 | 「举出 3 份**能通过校验但不该通过**的 handover」 | 反例清单 |
| **A2** | `core/health.js` + 测试绿 | 「H-1–H-5 哪一条会误报？举反例」 | 反例清单 |
| **A3** | 4 个工具 + 冒烟绿 | 「哪个参数组合能让它写坏文件 / 绕过门禁？」 | 反例清单 |
| **A4** | **全部完成后（最重要）** | 「按 `M0-评审报告.md` 的标准，这份 M1 验收报告哪里站不住？」 | 评审意见 |

**拿到反例后的处置（必须记录，三选一）：**

| 反例类型 | 处置 |
|---|---|
| 确实能通过但不该通过 | **改判据**（优先）或加测试钉住 |
| 能通过且通过是合理的 | 在 README 记「这是已知的宽松处」，**不假装它不宽松** |
| 反例本身不成立 | 记一句「审查者误判」，**不为了迎合它改坏设计** |

> ⚠️ **两个约束**：
> 1. **子 agent 只读不写**——两个 agent 同时改文件会互相覆盖。
> 2. **不许问「这个实现好不好」**——那种问题会得到空话。要问**可证伪的具体问题**。
>
> **递归深度**：本机 `maxDepth: 2`，但**不建议用第二层**（审查者再派审查者，收益递减）。

## 11. 风险与已知限制（**要写进 README**）

| # | 限制 | 影响 / 处置 |
|---|---|---|
| **M1-L1** | **`doc_handover_check` 只校验结构，不校验语义** | 七段齐全 + §3 有路径，不代表交接内容对。**不假装它证明了正确性** |
| **M1-L2** | **冷启动演练不能自动化** | 它是一份协议，靠人工/半自动执行。§7.2 给了判据与失败模式 |
| **M1-L3** | **跨会话 `readSet` 是「旁路文件」，不是日志真源** | 删了它就退化回 M0 行为（需重读），**不影响正确性** |
| **M1-L4** | **`doc_new` 会创建目录** | 它可能覆盖用户已有的同名目录结构？**不会**——只用 `mkdir -p` 语义 |
| **M1-L5** | **`doc_mark` 仍然要求先读过** | 这是刻意的（改状态就是改语义）。代价是「批量改 20 份文档的状态」要读 20 份 |
| **M1-L6** | **`doc_health` 的 H-5 可能误报** | `basis: 未验证` + `authoritative` 有时是合理的（比如用户明确授权）。所以它是 **warn 不是 error** |
| **M1-L7** | **4 个工具 = 4 份 schema 的固定 token 开销** | 用 `when` 条件注册对冲；但**探测不到项目根的会话仍然要付 `when` 的求值成本**（同步、无 IO，可忽略） |
| **M1-L8** | **`when` 条件抛错会中止整个步骤准备** | 所有 `when` 都必须自己 try/catch 并返回 false。**这是 M1 最危险的一处** |
| **M1-L9** | **交接质量的上限是「可复述」** | 复述对了也可能做错。M1 只保证「信息没丢」，不保证「决策正确」 |

## 13. 开工顺序（建议）

1. **先跑 M0 的基线**（307 单测 + 冒烟 + `verify-d1d2d3.mjs`），确认地基是绿的；
2. **`tools/define-tool.js` + 单测**——这是 M1 的地基，且它最容易踩「`undefined` 让整轮失败」的坑；
3. **`core/frontmatterEdit.js` + 单测**——`doc_mark` 依赖它，且「正文一个字节都不变」很容易写错；
4. **`core/handover.js` + 单测**——H1–H7 是纯函数，迭代最快；
5. **`core/health.js` + `core/budget.js` + 单测**；
6. **4 个工具 + `when` 条件注册**——**先把 `when` 的 try/catch 写好**（M1-L8）；
7. **`adapters/readstate.js`**——最后做，因为它是唯一「可砍掉」的部分（M1-L3）；
8. **扩展冒烟 → 重启 → 跑 M1-1 ~ M1-14**；
9. **冷启动演练**（M1-13）——**放在最后，因为前面的都过了它才有意义**。

> **第 2 步和第 6 步是刻意的**：`define-tool.js` 决定「工具能不能被宿主无损序列化」，
> `when` 决定「工具会不会在所有会话里冒出来」。这两件事错了，后面全白做，而且**症状都很奇怪**
> （前者是 `request/header` 写盘失败，后者是步骤准备被中止）。

## 14. 三条最容易犯的错（M1 版）

1. **为了「更完整」加第 5 个工具**。Q13 的上限是 4 个，M1 已经用满。想加工具时先问：
   「这个能力 `guard` 拦不住吗？现有 4 个工具表达不了吗？」两个答案都是「否」就别加。
2. **把交接状态塞进 `AGENTS.md`**。M1-Q4 已经定了：慢变量只放清单。塞进去会让 `AGENTS.md`
   每次交接都变，而 `dsh-agent-instructions` 的注入是**持久追加**——一变就多一条历史消息。
   **这正是 M0-5 在盯的东西。**
3. **`when` 条件里读盘或抛错**。`when` 每步骤求值一次，抛错会 `TOOL_ACTIVATION_FAILED`
   中止整个步骤准备（M1-L8）。条件里**只能读同步缓存**，且**必须 try/catch 返回 false**。
