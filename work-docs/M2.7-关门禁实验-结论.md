> **日期**：2026-11-15 ｜ **作者**：M2.7 施工者
> **实验**：把「让 AI 反复返工」的五道判定全部关掉，看那些复杂门禁到底有没有用。
> **结论**：**门禁不是成本来源。关掉它，成本反而上升。**
> **状态**：已恢复门禁（`git checkout master` @ `752eec1`）。
> **可重跑**：`node _m27/m27-analyze-21.mjs`

## 0. 一句话

> **关掉门禁后，错误从 1 降到 0，但步数从 28 涨到 34、字符从 11 332 涨到 16 335。**
> 那些步数不是"被门禁挡下后重来"，而是**它本来就会做的事**。
> **门禁从来不是成本来源，它只是刹车。**

## 2. 这个结果为什么重要（推翻了我们之前的假设）

### 2.1 原来的假设

摩擦台账算出的结论是：

> 31 次失败里 22 次来自同一条门禁，为它烧掉 **32% 的工具调用**。
> 那条限制防的，主要是「AI 改了自己刚改的文件」——它自己的合法行为。

**隐含推理**：如果门禁挡的是 AI 的合法行为，那关掉它就该省下这些步数。

### 2.2 实测推翻了它

关掉之后：
- 错误确实降到 **0**（说明门禁确实挡住了全部那类操作）；
- **但步数涨了 6 步，字符涨了 5 003。**

⇒ **那 22 次"失败之后的恢复步数"，并不是门禁制造的多余动作。**
AI 在没有门禁时**依然会**读 9 次、跑 7 次 `doc_health`。
门禁只是把其中一部分**显式标记成"失败"**，让我们看见了它们；
关掉之后它们还在，只是**不再显示为错误**。

> **这是本次实验最大的收获：我们把"可见的成本"误当成了"门禁造成的成本"。**

### 2.3 为什么关掉后反而更慢（机制）

门禁被拒时，AI 得到的是一个**明确信号**："你读的是旧版，重读"。
没有门禁时，它**失去了这个信号**，于是只能靠**反复自检**来确认自己对不对：

```
doc_health：4 次 → 7 次   （"确认没事"的仪式，涨了 75%）
doc_handover_check：3 次 → 4 次
重读：7 次 → 9 次
```

**门禁在充当"便宜的断言"，关掉后 AI 用"昂贵的自检"替代了它。**

## 4. 但这不代表"门禁越多越好"

诚实记录反面证据：

| 证据 | 说明 |
|---|---|
| **历史最好一轮（38%）也是门禁全开的** | 说明门禁开≠一定慢 |
| 19→20 轮的改善（44%→50% 成本降 35%） | 是**注入提示 + 修法 2 收窄 + H-6 只报一次**带来的，不是门禁本身 |
| 20 轮仍比最好一轮差 12 个点 | 说明还有结构问题，**但那不是门禁造成的** |

⇒ **门禁是必要的（它是刹车），但它不是瓶颈。**
瓶颈在**流程结构**：
- 交接与「它引用的索引条目」的循环依赖；
- 计数型证据的自我失效；
- `doc_health` 被当成仪式反复跑。

这三条**关掉门禁也解决不了**（21 轮就是证明）。

## 5. AI 自述里最有价值的一条（本轮）

> 「**验收证据会被『让交接变诚实』的那一步自己弄过期。**」
>
> 为了让 §2 那句「必读清单登记了三份文档」不成为假话，我必须**先**把
> `handover-1` 登记进 `read-order`，**再**写交接。
> 但这一步直接把 `doc_health` 的输出从「4 份受管，**1 份必读**」
> 变成「4 份受管，**2 份必读**」。
> 我写进 §5 的计数证据，在写完的同一刻就已经不是最新的了。

**这是"哈希脆弱"的推广：不只是哈希，连计数型证据都会自我失效。**

三轮不同的模型**独立**收敛到同一个结论：
> 顺序必须是「所有内容文档定稿 → `doc_health` 归零 → 取证据 → **最后**标绿」。

⇒ **这不是模型能力问题，是流程结构问题。** 这是下一步该改的地方。

## 8. 恢复门禁时的意外发现：**三个变异长期是假的**

恢复 `master` 后跑 `verify-anchors.mjs`，报 3 个 BAD-ANCHOR：

```
schema-drops-role            锚点出现 0 次
docnew-promises-direct-mark  锚点出现 0 次
handover-loses-codeblock-warning  锚点出现 0 次
```

### 8.1 排查（按交接 §4.5 的固定顺序）

1. **先查"变异真的施加了吗"** → `String.includes(from)` 为 false；
2. 缩进对过了（10/12/14），**一致**；
3. 最后逐字符比：

```
锚点首行: "          role: { type: 'string', required: true },"
源码首行: "          role: { type: 'string', required: true },\r"
                                                        ↑ CRLF
```

### 8.2 根因：**仓库行尾不统一**

```
ddd-bundle 下 .js/.mjs：CRLF 6 个，LF 86 个
core.autocrlf = true
.gitattributes = 不存在
```

那 6 个 CRLF 文件里正好包含 `doc-new.js`，而三个锚点全在它里面。
锚点是 LF 字符串，源码是 CRLF → `includes()` 永远 false。

### 8.3 为什么一直没被发现

`verify-anchors.mjs` 的输出**不是提交门槛**。交接 §2.3 把它列进"终态判据"，
但没有任何机制强制每次提交都跑它。**它报了 BAD-ANCHOR，只是没人看。**

⇒ **那三条变异的 "CAUGHT" 一直是假的**：它们从来没被施加过，
"测试通过"只说明测试本来就会通过。

### 8.4 修复

1. 新增 `.gitattributes`：`* text=auto eol=lf`（+ 二进制/`.cmd` 例外）；
2. 把磁盘上的 28 个 CRLF 文件真正改成 LF（`_m27/fix-eol.mjs`）；
3. 结果：

```
锚点 106 个：可用 106 / 有问题 0
变异 29 个：CAUGHT 29 / SURVIVED 0 / BAD-ANCHOR 0   ← 修好后的**第一次真实结果**
```

> **这条比实验结论本身更重要**：
> 之前所有"73/73 全 CAUGHT"的结论里，有 3 条是**假通过**。
> 现在才是真的 29/29。
