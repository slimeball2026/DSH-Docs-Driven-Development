## 2. 逐条分析（**只保留仍成立的**）

### F1 · 改文档就作废自己的已读记录（**10 条 / 2 个有效会话 · 唯一高可信**）

**构成**（10 条 = 7 条 `edit` + 3 条 `doc_mark`，两者无重叠）：

| 类型 | 条数 | 一句话 |
|---|---|---|
| `edit` 类（文案「**要先重读**」） | **7** | 改正文前，指纹已变 |
| `doc_mark` 类（文案「**你读过的是旧版**」） | **3** | 改状态也走同一条门禁 |

**现象**（逐字原文，`10f26ffe` seq 86）：

```
Error: 改 `read-order` 之前要先重读：你读过的是 vb95bfa，磁盘已是 vd0443b。用 read 工具重读它，然后再改。
```

**为什么这条结论可信（尽管版本旧）**：

`core/gate.js` 与 `core/scope.js` 是**冻结判据**，从 M0 到 M2.5 **一行没动**
（每份交接都写着「改 `core/gate.js` / `core/scope.js` 一行没动」）。
所以「改文档 → 指纹变 → 已读失效」这条**行为与版本无关**。

**AI 的反应**（`41db731a`，逐字）：

> 「编辑前先重读了一次（因为上一轮读过之后门禁把 read-order 记成了未读，直接编辑会被拒绝），重读后编辑成功。」

⇒ 熟练之后 AI 会自己学会"先读再改"，但它是**撞出来的**，不是被告知的。

**建议**（唯一一条我可以确定该做的）：

在 `【门禁】` 行末尾补一句**静态文案**：

```
｜ 你改过的文档会立刻变回未读（指纹变了），再改之前要重读
```

> ⚠️ 必须守住 M0-5 红线：**不含时间戳/轮次/百分比**。上面这句是静态的，安全。

### F2 ~ F7：**降级为"待重测"**（M1 时代样本，可能已缓解）

这些在旧版里真实发生过，但**每一轮的修复都可能已经改变它们**：

| F3 | `doc_new` 说「可以直接 doc_mark」但实际不行 | `10f26ffe` seq 222/225 | 文案是否改过**需重新核对** |
| F4 | `doc_handover_check` 在没交接时先报错 | 3 个旧会话 | 文案一直有出路，属"顺序没预告" |
| F5 | AI 试 `write` 绕过 `edit` 的限制 | `c03fc8c8` seq 159/161 | **M1 样本**，门禁的 `write` 分支此后没改，但未在新版复现 |

## 4. 下一步：**必须重测，否则不要改代码**

### 4.1 为什么不能直接按旧台账改文案

| 如果直接改 | 风险 |
|---|---|
| 按 F2 加"交接修订请新建" | **可能已经加了两次**（M2.3 加过），再加就是重复 |
| 按 F3 改 `doc_new` 文案 | 不知道现在是哪一句，可能改错行 |
| 按 F6 改 H4 文案 | H4 已改过一轮，现在的报错形态可能不同 |

⇒ **先花 10 分钟核对当前源码里到底有没有这些文案**，再决定改什么。

### 4.2 重测方案（最小可判定）

| 测试 | 目的 | 判据 | 成本 | 前提 |
|---|---|---|---|---|
| **T0** | **核对当前文案**（不用跑会话） | 逐条确认 F2–F7 的文案今天在不在 | **10 分钟** | 无 |
| **T1** | 验 F1 是否仍频发 + 测修复效果 | 同一份全流程演练提示词**在新版上重跑** | 1 个会话 | **必须重启宿主**（改注入要重启才生效） |
| **T2** | 补"接手"场景 | 新会话 + 已有交接 + 一句"接着做" | 1 个会话 | 同上 |
| **T3** | 长会话曲线 | 同一会话连做 3 件事 | 1 个长会话 | 可选 |

**顺序**：`T0 → 改文案 → 重启宿主 → T1 → 对比`

> ⚠️ 不重启宿主就重测，会得到"修复没用"的**假结论**（`M2-施工记录-宿主重载真相.md` 记着这件事）。

### 4.3 T0 已做完：**逐条核对当前源码**

我不等重测，先把"文案今天在不在"查清楚了（搜当前源码，约 10 分钟）：

| 摩擦 | 当前源码状态 | 结论 |
|---|---|---|
| **F1** 改文档即作废已读 | `core/gate.js` **冻结未动**（每份交接都写着"一行没动"） | ❌ **必然仍在 → 要加预告** |
| **F2** 交接修订请新建 | `doc-new.js:381` 已有 `**交接是一次性文档**：之后要修订，请**再建一份新的**` | ✅ **M2.3 已修，不用再动** |
| **F3** `doc_new` 说「可以直接 doc_mark」 | `doc-new.js:363` 仍是 `'已记入本会话的已读集合，可以直接 doc_mark。'` | ❌ **完全没修，仍是误导 → 要改** |
| **F4** 无交接时先报错 | `doc-handover-check.js:89` 文案有出路，但没预告顺序 | ⚠️ **可加一行顺序说明** |
| **F5** 试 `write` 绕过 `edit` | `core/roles.js:131` 的 `denyMessage` 对 `write`/`edit` **共用同一条文案** | ✅ **门禁是对的**；只是文案没主动说"两者同等"，属可选优化 |
| **F6** H4 把代码块表格行算作条目 | `core/handover.js` **没有任何提到"代码块"的注释或文案** | ⚠️ 大概率仍在，但**要改 H4 需授权** |
| **F7** 入口索引 id 撞车 | 初始化会自动建 `read-order` | ⚠️ 行为没变，可加一句预告 |

**这一步的价值**：它把「6 类待重测」直接收敛了——

| 结论 | 条目 |
|---|---|
| **确定要改** | F1（加预告）、F3（改文案） |
| **可选加一行** | F4（顺序）、F7（别重建入口索引） |
| **已经修好，不要动** | F2 |
| **门禁本身是对的** | F5 |
| **要动判据，需授权** | F6 |

⇒ **不需要为了这份台账再跑任何实机测试。** 现在就可以改那 2~4 处文案。
只有 F6 需要你拍板（它要改冻结判据 H4）。
