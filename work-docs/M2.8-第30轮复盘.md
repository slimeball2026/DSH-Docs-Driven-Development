## 1. 真 bug ①：`doc_new` 从中文标题派生出 id `30`

### 现场

```
seq 129  doc_new  role=handover, title="交接：全流程测试30", **没传 id**
         → deriveId 把中文全丢掉，只剩数字 → id = "30"
         → ID_RE（^[a-z0-9]+...$）**接受纯数字** → 建出 docs/30.md
seq 135  AI 发现不对，又建 handover-1
seq 152  把 30 标 void
seq 157  再修 read-order
```

**代价**：1 次白建的 79 行交接 + `read` + `doc_mark` + 两次 `edit` ≈ 5 次调用。
**更糟的副作用**：那个 `void` 的 `30` 永久留在索引与坟场里，是本轮唯一的污染。

### 为什么纯数字 id 必须当派生失败

1. 它一定是"从中文标题里捡到的数字"（年份 / 轮次 / 序号），**不表达语义**；
2. **YAML 会把 `30` 解析成数字**而不是字符串（M2.7 已为手写 `id: 1` 加过 V1 校验，
   但那只管**手写**的，管不到**派生**出来的）；
3. `handover-1` 一看就知道是什么，`30` 谁也不知道。

### 修法

新增 `isDerivedIdUsable(derived)`：派生结果**必须含至少一个字母**。
只在**派生**这条路上收紧；显式传 `id: "30"` 仍然允许（那是明确要求，不是猜的）。

## 2. 真 bug ②：`doc_mark` 的成功回执自相矛盾

### 现场

```
已更新 `handover-1` 的 frontmatter：status、basis。
⚠️ **它的 `basis` 还是「未验证」** —— doc_health 的 H-5 下一步就会报。
```

**同一段话里前后矛盾**：既说改了 basis，又说 basis 还是未验证。

### 根因

`basisPending` 读的是 `entry.meta.basis` —— **写盘前**的注册表缓存。
而这次调用可能刚把 basis 改成「实测」（`basis` 参数），于是判据按旧值报。

### AI 的评价（它说得很准）

> 不管哪句是真的，这直接摧毁了「读工具输出即可确认」的前提，
> 逼我对每次标绿都回读验证。

它为此多读了 2 次文档（`seq 87` / `seq 103`）。

### 修法

`effectiveBasis = basis !== undefined ? basis : entry?.meta?.basis` ——
按**这次调用之后**的实际状态判断。

## 3. 真 bug ③：`supersede` 反填后又写了一次文件，却没重记账

### 现场

```
seq 135  doc_new 建 handover-1 ✅（回执说"已记入本会话的已读集合"）
seq 152  doc_mark 把 30 标 void ✅
seq 168  doc_mark handover-1 ❌ **「你读过的是旧版（v24b7de），磁盘已是 va60b3e」**
```

而 `seq 135 → 168` 之间**没有任何工具碰过 `handover-1`**。

### 根因

`doc_new` 的记账顺序是：

```
① markRead(写文件时的 text)      ← 指纹 A
② rescan
③ markRead(fresh.text)           ← 指纹 B（此时对）
④ supersedeOldHandovers()        ← **它会把 supersedes 反填进这份新交接**
```

④ 的反填**又写了一次 `handover-1`**（写进 `supersedes: ["30"]`），指纹从 B 变 C。
而 ③ 记的是 B → 门禁认为"你读过的是旧版"。

**所以 `doc_new` 那句「已记入本会话的已读集合」在当时就是假话**，
它把代价转嫁给了下一次 `doc_mark`。

### 修法

④ 之后如果**真的取代过旧交接**（`supersededOld.length > 0`），重新 `markRead` 一次。

## 4. 我写的提示词有歧义（不是 bug，是我的错）

第 29 轮我加了这句话：

> ⚠️ **手写 `## 必读清单` 时，别给交接留位置**：不要写「最新交接（role: handover）」这种泛指条目

**第 30 轮 AI 把它读成"清单里根本不要出现交接"**，于是它 `edit` 时把工具自动登记的
那一行 `handover-1` **一起删掉了**，改成一句「交接由工具自动登记在清单第一条」。

结果 `doc_health` 的 **H-3** 如实报：

> `handover-1` 是 authoritative，但没有任何 role: index 的文档提到它

AI 只好再读一遍 `read-order`、再改一遍（2 次调用），**而它以为自己是在遵守我的指示**。

它的原话：

> 工具说「必读清单已自动登记本份交接（不用你再改 read-order 加自己）」，
> 然后 doc_health H-3 说「没有任何 role: index 的文档提到它」。
> 所以自动登记 apparently 不算 "mention"。**工具承诺和健康检查不一致**。这花了我 2 次调用。

**它判断错了原因**（不是工具不一致），但**现象是真的** —— 而根因是我那句话有歧义。

### 修法

补一句：**工具插的那一条具体条目（带本份 id 的那行）必须留着**，
H-3 靠它判断"这份权威交接有没有人提到"。

## 5. 一条测试自己抓到了自己的 bug

补测试时，`m28-fixes.test.js` 里那条「H4 词表必须写在描述里」**红了一次**，
但代码明明是对的。查下去发现是我的**切片边界**写错了：

```js
const descEnd = source.indexOf("].join('')", descStart)   // ← 错
```

DESCRIPTION 数组内部现在有注释，`].join('')` 会提前命中，切片被截断，
`符合` 落在切片外 → 误报"描述里没有"。

改成 `'\n].join(\'\')'`（顶格）作边界才准。

> **教训**：用字符串定位代码块时，边界必须**足够独特**。
> 这也解释了为什么之前几次跑测试时红的是**不同**的测试 —— 顺序不同，切片位置就不同。
