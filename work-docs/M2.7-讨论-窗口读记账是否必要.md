# 讨论：缺陷 #1「窗口读记账」的必要性 —— 如果直接停用会怎么样？

> **日期**：2026-11-15 ｜ **作者**：M2.7
> **用户问题**：「我想先讨论它本身的必要性，如果直接把它停用会怎么样？」
> **状态**：讨论稿，**未实施任何修改**。
> **证据**：`node _m27/m27-experiment-disable-window.mjs`、`_m27/minExp.mjs`（最小复现）

---

## 0. 直接回答

> **停用它，会比现在更严格、也更诚实 —— 但不是没有代价。**
>
> 而更要紧的是：**现在的实现有一个比"记错指纹"更坏的后果，
> 它是"用片段读就能把门禁推开"的一扇小门。**

---

## 1. 先把机制说准（我上一轮的描述是不完整的）

我之前说：「窗口读记下片段指纹 → 之后写被拒 → 报错误导」。

**实测发现它还有另一面，而且那一面更重要。**

最小复现（`_m27/minExp.mjs`，67 行 authoritative 文档）：

```
1 没读过                    → 拒绝（必须先读）
2 完整读后                  → 放行
   （自己 edit 成功一次）
3 自写后 + pre-step（未重读） → 拒绝：你读过的是 vf6fecf，磁盘已是 v5ecdee
   （read(offset=53, limit=15)，读到文件末尾）
4 窗口读之后                → **放行** ← 窗口读"治好"了那次拒绝
```

### 为什么会放行

`markRead` 的 A 分支（`freshText` 是字符串）做的是：

```js
entry.text = freshText                    // ← 把注册表缓存也改成片段
entry.fingerprint = fingerprintOf(freshText)   // ← 注册表指纹 = 片段指纹
readSetSet({ fingerprint: entry.fingerprint }) // ← readSet 也是片段指纹
```

**两边都被改成同一个片段指纹** → 门禁比对时**相等** → 放行。

⇒ 这不只是"记错指纹"，而是：**一次窗口读可以把「你改完后没重读」这个正确拒绝消掉。**

### 那为什么本轮还是被拒了 3 次？

因为本轮那两次窗口读（`seq 162 offset=19`、`seq 182 offset=55`）之后，
**中间还有别的东西让注册表重算成了磁盘全文**（pre-step / rescan）。

所以它是**一个不确定的开关**：有时放行（危险），有时拒绝（报错还误导）。
**两边都不是好结果。**

---

## 2. 如果直接停用（窗口读完全不记账）

### 会变成什么样

| 场景 | 现在 | 停用后 |
|---|---|---|
| 完整读过 → 窗口读 → 写 | **放行**（片段指纹把两边一起改了） | **仍按完整读的记录判**：改过就拒、没改就放 |
| 自己改完 → 窗口读 → 写 | **放行**（推开了门禁） | **拒绝**：「你改过它，先重读」 |
| 从没读过 → 窗口读 → 写 | 记空/片段 → 拒绝（文案误导） | **拒绝**：「必须先读它」（文案准确） |
| 大文件分两段读（1~50 + 51~100） | 第二段读到末尾时算"读完了" | **不算读完** → 要多读一次整份 |

### 收益

1. **没有"用小窗口推开"的小门** —— 这是最重要的一条；
2. **报错文案变准**：不再说"你读过的是旧版"（它没读过全文，说"旧版"是误导）；
3. **行为变确定**：不再依赖"注册表有没有被重算"这种时序运气；
4. 代码更简单：`windowReadOf` / `markRead` 的 window 分支可以整段删掉。

### 代价

1. **分段读完大文件不再算读过** → 多 1 次整份 read。
   实测本项目文档最大 **67 行**，分段读主要出现在"想省 token 看几行"，
   那些本来也不该算读完。**实际受害面很小。**
2. **窗口读彻底没有记账意义** —— 但这正是它应有的语义：
   片段不构成"看过当前版本"的证据。
3. 如果将来有真的大文档（几千行）必须分段读完，AI 会多花一次读。
   可以用"分段读完所有片段后拼起来"来优化，但那要新机制，**不建议现在做**。

## 3. 与"修法 2"（现在已实现的那套）的关系

| | 修法 2（C） | 停用（B） |
|---|---|---|
| 窗口读进 `markRead`？ | 进（走 `window` 分支） | **不进** |
| 保留已有指纹 | ✅ | 不需要（什么都不动） |
| 没有记录时记空指纹 | ✅（→ 报「你读过的是旧版」） | ❌（→ 报「必须先读它」，**更准**） |
| 能推开"自写后未重读"吗 | ❌ 不能 | ❌ 不能 |
| 代码量 | 多一个分支 + `windowReadOf()` | **删掉这些** |

⇒ **B 是 C 的真子集，且更准确、更简单。**
修法 2 当初是为了"既严格又保留自我写的便利"，但从实测看：
- "自我写的便利"根本不工作（`doc_mark` 不看 `selfWritten`）；
- "严格"在 A 分支存在时也不可靠（片段指纹会把两边一起改）。

**两个目的都没达到。**

---

## 4. 我的建议

**直接停用，比修 #1 更干净。**

理由：
1. 修 #1 要同时改 `textFromReadResult` + `windowReadOf`，**漏一处就从误拒变误放行**；
2. 修 #1 只能消掉 3 次报错里的 2 次（`doc_mark` 不看 `selfWritten`）；
3. 停用只需在 `observe.js` 里**跳过窗口读的 markRead 调用**，
   改动面小、无歧义、且**连 `windowReadOf` 一起可以删**。

### 具体改法（三步，都很小）

```
1. observe.js：窗口读（首行行号 > 1 或 footer 是 Showing/Output capped）**不进 markRead**
2. registry.js：删掉 markRead 的 opts.window 分支（没有调用方了）
3. observe.js：删掉 windowReadOf()（或保留但标注"仅诊断用"）
```

### 一个必须一起处理的前提

「首行行号 > 1」这个判据**必须复用同一处实现**。
现在 `textFromReadResult` 和 `windowReadOf` 各算一遍，两边都只看 footer ——
**这正是缺陷的来源**（两处都判错了同一件事）。

停用方案里它们可以合并成一个函数：`isPartialRead(result)`，
判据是「**信封首行的行号 > 1**」或「footer 是 Showing/Output capped」。
一处实现、一处判据，不会再分叉。

## 5. 还没验证的一件事（诚实标注）

**停用之后，本轮那 3 次报错会变成什么？** 我**没有**跑出来，因为：
- 那 3 次的历史时序依赖"注册表有没有被重算"，模拟不准；
- 要真实验证只能等你重启后跑一轮。

**我的预期**：
- `seq 157`（自己改完后紧接着改）→ **仍会拒**（这是铁律 7 的固有代价，不该消）；
- `seq 167`（窗口读后）→ **仍会拒**（但文案变成"你必须先完整读过"）；
- `seq 192`（doc_mark 前）→ **仍会拒**（`doc_mark` 不看 `selfWritten`）。

⇒ **步数不会明显下降**，但**报错会变准、行为会变确定、小门会关上。**

如果目标是"减少步数"，停用 #1 **不解决问题**；
如果目标是"别让 AI 得出错误结论、别让片段读推开写门禁"，**停用是对的**。

---

## 6. 一句话

> **#1 不是"记错指纹"那么简单 —— 它是"一次片段读就能把门禁推开"的一扇小门，
> 而且开合取决于时序运气。**
> **停用比修它更干净：改动更小、语义更准、还能删掉两处重复判据。**
> **但它不会让步数明显下降 —— 那要靠别的改动（比如 `doc_mark` 认 `selfWritten`）。**
