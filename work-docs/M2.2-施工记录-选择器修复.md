## 1. 问题一：下拉框选值后不更新（**我的 bug**）

### 现象（用户原话）

> 「它默认显示为当前会话，哪怕在菜单里选择其它会话，菜单里的文件路径不会变，
> 但下方的内容会变，同时如果再选回原会话，内容就不会再发生变化了」

### 真因

`<select value={chosenCwd}>` 是**受控组件**，值来自 `controller.getChosenCwd()`。
`selectProject()` 改了闭包里的 `chosenCwd`，然后调 `load()` —— 而 `notify()` 只在
`load()` **内部**、且在 `await fetchSnapshot(...)` **之后**才调用。

于是这中间 React 读到的是**旧快照**：`getChosenCwd()` 已是新值，但订阅者拿到的
props 集合与上次相同 → **判定无需重渲染** → 下拉框停在原值。

```ts
// 旧实现（错）
const selectProject = (cwd) => {
  chosenCwd = cwd
  snapshot = undefined
  error = undefined
  if (chosenCwd === '') { notify(); return }
  void load()          // ← notify 在 load 内部，异步且滞后
}

// 新实现
const selectProject = (cwd) => {
  chosenCwd = cwd
  snapshot = undefined
  error = undefined
  notify()             // ← 先通知，UI 立刻反映新选中值
  if (chosenCwd === '') return
  void load()
}
```

> **教训**：受控组件的值变了，**必须在同一次同步流程里**通知订阅者。
> 把 `notify()` 埋在异步函数里，等于赌"React 会自己发现"——它不会。

## 2. 问题二：刷新按钮无效（**我的 bug**）

### 现象（用户原话）

> 「我尝试把 `DDDUI测试/` 当作新的 ddd 工作区，在里面建了一个 docs 并粘贴一个
> 从以前测试来的 agent.md 文档，结果刷新不起作用，点了浏览倒是起了作用」

### 真因

`refresh()` 只是**重取快照**。而 host 侧的探测有 TTL 缓存：

```js
// adapters/probe.js
const cached = cache.get(cwd)
if (cached !== undefined && Date.now() - cached.at < PROBE_TTL_MS) return cached
```

用户刚建的 `docs/` **在缓存有效期内不会被重新读到** → 面板继续说"这不是 DDD 项目"。

而"点浏览反而好了"恰好印证了这一点：`pickDirectory` 换了一个 cwd，
**绕过了那个坏缓存**。

### 修法

1. `probe.js` 加 `forget(cwd)`：让**单个**目录的探测失效；
2. 新路由 `POST /api/ddd/recheck`：`forget(cwd)` → `ensure(cwd)` → 必要时建注册表；
3. client 的 ⟳ 改走 `recheckOf`（先清缓存再取数），**顺序不能反**。

> **教训**：带 TTL 的缓存 + 一个"刷新"按钮，两者必须**显式打通**。
> 否则用户会得到一个"点了没反应"的按钮，而它看起来像插件坏了。

## 3. 问题三：需要一键初始化（**功能缺失**）

### 现象（用户原话）

> 「要我手动建 ddd 工作区太麻烦了，我需要一个能把指定工作区一键建成 ddd 工作区的功能」

手动流程是：建 `docs/` → 手写带合法 frontmatter 的 `.md` → 刷新。
**每一步都可能写错**，而写错的症状是"面板说这不是 DDD 项目"——
用户完全看不出是 frontmatter 少了字段。

### 实现

- 新文件 `server/init-workspace.ts`：生成入口索引 + 幂等写入；
- 新文件 `server/mkdir-bridge.ts`：建 `docs/`（见下面的破纪律说明）；
- 新路由 `POST /api/ddd/init`；
- client 加「初始化为 DDD 工作区」按钮（未选目录时禁用）。

**三条纪律**：

1. **绝不覆盖已有文件**：目标存在就跳过并在 `skipped` 里说清；
2. **失败形状与成功同形**（都带 `created` / `skipped` / `failed`）；
3. 生成的 frontmatter **必须**能被 `looksLikeDddDoc` 认出来 ——
   这条有专门的测试钉着（`**生成的入口索引必须构成激活标记**`）。

## 4. 破了一条纪律：插件开始建目录

### 为什么必须破

`ctx.fs` **没有 `mkdir`**（只有 resolve / stat / read / write / move / delete）。
而本项目的既有纪律是「**插件从不创建目录**」——
M2.1 选"归档元数据写进文件自己"而不是 `_artifacts/graveyard.json`，
理由之一就是后者会逼插件建目录。

但"一键初始化"本质上要建 `docs/`。让用户先手建一个空目录、
再让插件写文件，是把同一件事拆成两步且**中间没有任何收益**。

### 怎么破（用户 2026-11-13 拍板允许）

1. **收在一个文件里**：`server/mkdir-bridge.ts`，别处仍严格禁止 `node:`；
2. **白名单 + 白名单自身的约束**：`test/decoupling.test.js` 里
   `NODE_IMPORT_ALLOWLIST = new Set(['server/mkdir-bridge.ts'])`，
   并且额外钉两条：
   - 白名单文件**必须存在**且**仍然 import node:**（否则白名单该删）；
   - 只允许 `node:fs/promises` 与 `node:path`，多一个就红；
   - 必须含 `realpath` + `isInside` + 越界拒绝分支。
3. **只在用户显式点"初始化"时调用**，不在任何自动路径上。

### 越界检查踩的两个坑（都是 Windows 特有）

`realpath` 会把长名折成 **8.3 短名**（`SLIMEB~1`），而调用方给的路径是长名。
于是"在 `%TEMP%` 里建 `docs/`"被误判为**越界**，错误信息还说"在项目根之外"——
**完全误导**。

最终做法：**逐级向上找最近一个存在的祖先**，`realpath` 它，再把剩下的相对段拼回去。
（第一版只 realpath 父目录，于是"两层深的新目录"仍然误判。）

> **教训**：Windows 上任何"按字符串比较路径"的越界检查都不可靠。
> 要么全 realpath，要么**逐级找到存在的祖先**再比。

## 7. 我这一轮做错了什么（诚实记账）

| # | 错 | 代价 |
|---|---|---|
| 1 | 把 `notify()` 埋在异步 `load()` 里 | 受控组件不重渲染，用户看到"选了没反应" |
| 2 | 加了"刷新"按钮却没打通 host 的探测缓存 | 用户建了 `docs/` 后刷新无效，以为插件坏了 |
| 3 | 候选只从会话推导，漏了"首次指定" | 用户必须先把目录在 DSH 里打开一次 |
| 4 | 越界检查按字符串比较 | Windows 短名下误判，正常操作被拒且错误信息误导 |

**共同点**：这四条**都不是逻辑复杂**，是"没在真界面上点一遍"。
测试全绿不代表功能可用 —— 与 M1.5/M2 反复栽的那条是同一个。
