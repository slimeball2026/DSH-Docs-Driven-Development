# M2 待办：client 半侧已实现但未启用

> **一句话**：client 半侧**代码写完、构建通过、单测守着**，但**一旦声明 `dsh.client` 宿主就起不来**，
> 而宿主自己说的两类失败原因**我都反证掉了**。所以它现在是**已实现、未启用**的状态。

## 一、为什么封版在这里（不是偷懒，是风险判断）

| 层 | 状态 | 说明 |
|---|---|---|
| **host 侧** | ✅ **已验通** | 门禁数据源、HTTP 路由、预算优先级、交付/坟场真源。这是 M2 价值的绝大部分 |
| **client 侧** | ⚠️ **已实现、未启用** | 面板渲染层。卡在一个我解释不了的组合失败上 |

SPEC §11 **R-11** 的处置建议原文是「**分两轮上**」。现在就是把第一轮封版、第二轮挂起。

## 三、未解之谜（**这是本文档最重要的部分**）

### 3.1 现象

声明 `dsh.client` 后重启，宿主起不来：

```
Error: web boot: 1 entry did not activate
@local/ddd: failed
```

卸载/去掉 `dsh.client` 后正常。**可复现。**

### 3.2 宿主自己说失败只有两类原因

`app.asar` 里 `ClientModuleRegistry` 的注释原文：

> Construction runs the activation scan synchronously — **a malformed declaration or missing bundle**
> among the already-loaded entries aggregates into one loud throw (FAILED fiber; the boot activation audit reports it).

### 3.3 两类原因**我都反证掉了**

| 宿主说的原因 | 我的实测 | 结论 |
|---|---|---|
| declaration malformed | 用宿主的 `parseDshClient` 复刻校验：`platform` 是字符串、`inject` 是字符串数组 → **通过** | **排除** |
| bundle missing | `createRequire(profile).resolve('@local/ddd/client')` → `…\lib\client.js`；`statSync` = 32 050 B；内容可读 | **排除** |

**两类都不成立，它却失败了。这是本切片唯一的未解之谜。**

### 3.4 曾经错误怀疑过、已反证的点（**别照着改**）

| 一度怀疑 | 反证 |
|---|---|
| `inject` 里的 `@deepseek-ai/dsh-client-ui-sidebar` 不存在 | `@deepseek-ai` 在 profile 里是**空目录**，官方包都在 `app.asar` 内。真实范例 `dsh-context` 注入 `…ui-sidebar-right`、`dsh-cuigengji-plugin` 注入 `…ui-sidebar` + `…ui-sidebar-right`，同宿主下正常 |
| bundle 外壳形态不对 | 与 `dsh-cuigengji-plugin`、`dsh-client-locale` **逐字同形**（`window.__ModuleLoader__.load({id,factory:(require)=>{var module={exports:{}};…return module.exports}})`） |
| `ddd-bundle/node_modules` 干扰 | 它现在**仍存在**，宿主启动正常 |
| `files` / `devDependencies` 干扰 | host-only 版**同样有**这两项，能启动 |

> **教训**：这四个怀疑如果按"看起来可疑"去改，会**掩盖真因**并引入新的不确定性。
> 真实可运行的范例（用户提示的 cuigengji）比直觉可靠得多。

### 3.5 下一步该怎么查（**给接手的人**）

我建议按这个顺序，**每次都只改一个变量**：

1. **换 bundle 内容**：把 `lib/client.js` 换成**一行最小内容**（只 `window.__ModuleLoader__.load({id:'@local/ddd',factory:()=>({})})`），
   声明不变。
   - 若仍失败 → 问题**不在 bundle 内容**，在声明/路径层；
   - 若成功 → 问题在**我的 bundle**（那就要查 32 KB 产物里的某处）。
2. **换声明形态**：照 `dsh-context` 抄一个**完整**的 `inject`（列出 `ui-sidebar`、`ui-layout`、`locale`、`ui-conversation`）。
   - 若成功 → 是**激活顺序**问题（缺 `inject` 导致我的 bundle 先于 shell 激活）。
3. **换 exports 形态**：用 `dsh-cost-meter` 的对象形式 `{default: './lib/client.js'}`。

**每次试验前先跑 `rollback-ddd.ps1` 确认能回滚。**

## 六、验证 client 侧时**必须先做的事**

`_rv/probe-activate.mjs` 只能证明 `apply()` 不抛，**证明不了宿主能启动**。
所以 client 侧的验证顺序必须是：

1. `_ref/smoke-ddd.mjs` 全绿（39 项）；
2. **激活探针**通过；
3. **重启** —— 这一步无法在本地替代，因为 `clientModules` 是宿主服务；
4. 起来之后才谈 M2-1 / M2-3 / M2-4 / M2-8 / M2-9。

**第 3 步失败时**：`rollback-ddd.ps1` + 重启。
