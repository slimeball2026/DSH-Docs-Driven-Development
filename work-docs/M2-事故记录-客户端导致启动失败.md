# M2 事故记录：client 半侧导致宿主启动失败

> **结论先行**：2026-11-13 18:48 的一次重启，DSH 起不来，用户被迫卸载插件。
> **原因是我把 host 侧与 client 侧一次性上线，违反了 SPEC R-11 自己写的处置建议。**
> 现已回退到 host-only（`dsh.client` 不再声明），并留下一条命令的回滚通道。

## 一、现象

`~\.dsh\profiles\desktop\logs\crash-2026-11-13T10-48-26-520Z-web-boot.log`：

```
phase: running
--- error ---
Error: web boot: 1 entry did not activate
@local/ddd: failed
    at file:///D:/deepseek%20harness/resources/app.asar/lib/main.js:20648:15
```

**只有 `failed`，没有具体异常。** 宿主不会把这个细节写进 crash 日志。

## 二、定位过程（**排除法，每一步都实测**）

| 假设 | 验证方式 | 结论 |
|---|---|---|
| `index.js` 语法/导出坏 | 按宿主方式 `import()` | **排除**：`name`/`inject`/`apply` 都正常 |
| `apply()` 抛异常 | `_rv/probe-activate.mjs` 用假 ctx 跑 | **排除**：4 工具 + 4 路由全部注册，零 warn |
| `server/*.ts` 加载不了 | 6 个模块逐个 `import` | **排除**：全部 OK（Node 24 原生剥类型） |
| `lib/client.js` 不存在 | `statSync` + 读取 | **排除**：32 050 B，可读 |
| `dsh.client` 字段格式错 | 按宿主 `parseDshClient` 校验 | **排除**：`platform` 是字符串，`inject` 是字符串数组 |
| 探针写盘在沙箱里失败 | 实测 `tmpdir` 与 cwd | **排除**：都能写，且在 try/catch 内 |

排除完这些，嫌疑集中到 **client 组合**这一层。

## 三、根因（`app.asar` 反编译所得）

宿主 `clientModules` 服务的构造：

```js
constructor(ctx) {
  super(ctx, "clientModules");
  …
  const failures = [];
  this.flush((err) => failures.push(err));
  if (failures.length > 0) throw new ClientPackageCompositionError(failures);
  const registerWebCarrier = (webCtx) => { … };
}
```

**任何一个带 `dsh.client` 的包组合失败 → `clientModules` 这个服务整体构造失败 → 依赖它的 entry 全部 `failed`。**

这与 SPEC §11 **R-11** 逐字预言的是同一件事：

> 「宿主对 `dsh.client` 声明的处理是：**缺 `lib/client.js` 时 loudly fails activation**，
> 不是"面板静默消失"。**所以"忘了 build"会把局部故障升级成插件整体哑火**——
> 那时连 host 的门禁也不工作了。」
>
> **处置**：把 `build` 写进 `test` 脚本前置，**或在 `cordis.patch.yml` 里先不声明 `dsh.client`（分两轮上）**。

**我两条都没做。** 这是这次事故的**唯一直接原因**，不是运气问题。

## 四、两个"看似可疑其实无关"的发现（**不要照它们改**）

我在排查过程中一度怀疑下面两点，**实测都不是原因**：

| 一度怀疑 | 反证 |
|---|---|
| `dsh.client.inject` 里的 `@deepseek-ai/dsh-client-ui-sidebar` 不存在于 profile | `@deepseek-ai` 目录是空的，官方包都在 `app.asar` 内。**真实范例 `dsh-cuigengji-plugin` 注入的就是 `...ui-sidebar` 与 `...ui-sidebar-right`**，所以注入 sidebar 包合法 |
| 我的 bundle 外壳形态不对 | 与 `dsh-cuigengji-plugin/lib/client.js` 的头尾**逐字同形**（`window.__ModuleLoader__.load({id,factory:(require)=>{var module={exports:{}};…return module.exports}})`） |

> **教训**：这两点如果按"看起来可疑"去改，会**掩盖真因**并引入新的不确定性。
> 真实范例（cuigengji 是侧边栏直接显示、UI 量大的插件）比"看起来对不对"可靠。

## 八、下一个人要注意的

1. **`dsh.client` 是"全有或全无"的开关**：它在 `clientModules` 的构造里，失败一次就带塌整个服务。
   所以**先不声明它**，把 host 侧验稳，再单独上 client（这正是 R-11 的原话）。
2. **宿主不给你 `apply()` 的异常**。`web boot: … failed` 是终点，不是线索。
   要查就得用 `_rv/probe-activate.mjs` 那种"本地给假 ctx 跑一遍"的办法。
3. **别用"看起来可疑"替代反证**。§四 的那两点如果按直觉改了，会盖住真因。
4. **改 profile 的 `package.json` 前先备份**，且**用 JSON 往返时核对列表长度**——
   我这次备份里已经是 7 项，如果不核对就会误以为是自己的编辑弄丢的（或者反过来，真弄丢了却没发现）。
