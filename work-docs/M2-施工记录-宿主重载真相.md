# M2 施工：宿主重载机制的真相（**订正版**）

> ⚠️ **这份文档取代了 `M2-施工记录-H4修复与宿主重载.md` 的第一节。**
> 那一节我写的是「`plugin_manager` 停用/启用会重新加载插件模块」——
> **那是错的**，我把**测试进程**写的探针误读成了宿主写的。
> 错误怎么发生的、怎么被发现的，见下面 §三。**保留这段经过，因为它比结论更有用。**

## 一、结论（实测）

| 你做的动作 | 会发生什么 | 证据 |
|---|---|---|
| 改 `core/*.js` / `adapters/*.js` / `docs/*.js` 等**被 import 的模块** | **新代码立即生效** | 实机：改完 `core/handover.js` 的 H4 正则后，`doc_handover_check` 当场认了 `722/722 全绿` |
| 改 `index.js` 里的 **`apply()` 函数体**（含 `inject` 声明） | **不生效** | 实机：删掉探针文件 → 停用 → 启用 → **探针没有被重新创建** |
| `plugin_manager` 停用 / 启用 bundle | **不重跑 `apply()`** | 同上；且探针里记录的 `ctx` 是 `Object.prototype` 形状（测试进程的假 ctx） |
| 完全重启 DSH | 全部生效 | 这是唯一可靠的"重来一遍" |

**机制**：`include:hmr` 存在且 active，它做的是 **Cordis 模块级热替换** ——
被 import 的模块换了新的，但**插件实例（fiber）没有重建**，所以 `apply()` 不会重跑，
`inject` 声明的服务注入也就不会重新解析。

> **交接 §0.6 的原话「改 JS/TS 必须重启 DSH —— 模块不会热替换」需要拆成两半看**：
> 「模块不会热替换」**不准确**（模块确实会热替换）；
> 但「改 `index.js` 的 `apply()` 必须重启」**是对的**。

## 二、这对 M2 意味着什么（**一个真实的阻塞**）

`webServer` 只能通过**插件级 `inject`** 拿到：

- `ctx.get('webServer')` 在这个 ctx 上**不存在**（探针记录 `viaGet: "no-ctx.get"`）；
- 没声明 `inject` 时 `ctx.webServer` 是 `undefined`（探针记录 `hasWebServer: false`）。

而 `inject` **只在 `apply()` 执行时生效一次**。所以：

> **R-1（`ctx.webServer.register` 真的能注册）必须真正重启 DSH 才能验证。**
> 改 `inject` 而不重启，运行中的插件永远拿不到 `webServer` —— 而且**没有任何报错**，
> 只有一条 warn（"拿不到 webServer 服务"）。

### 2.1 为什么不能靠外部 HTTP 验证（三条都试过）

| 方法 | 结果 |
|---|---|
| 直接 `fetch` `/api/ddd/ping` | **401**（宿主的认证在**路由匹配之前**，所以 401 无法区分"路由在"与"路由不在"） |
| `GET /?token=...` 换 cookie | **401**（我拿不到真实启动 token；进程命令行不可读） |
| 桌面日志 | 只有 `crash-*.log`，**没有运行日志** |

### 2.2 所以需要一个**插件自证**的探针

`index.js` 里写 `_m2-route-probe.json` 到**临时目录**（不污染工作区），内容：

```jsonc
{
  "at": 1794549622388,        // 时间戳：判断是不是这次加载写的
  "pid": 12345,               // 进程号：区分"宿主写的"与"测试进程写的"（这条就是 §三 的教训）
  "inject": ["tools","systemPrompt","fs","webServer"],
  "registered": true,          // ← 重启后应当变成 true
  "routes": ["exact /api/ddd/ping", ...],
  "hasWebServer": true,        // ← 重启后应当变成 true
  "viaGet": "...", "protoKeys": [...], "inOperator": true
}
```

**重启后判据**：`hasWebServer: true` 且 `registered: true` → R-1 通过。
仍是 `false` → 说明 `inject` 这条路在 desktop 组合里也不通，那时才需要考虑备选方案（SPEC §11 R-1 的"快照写文件"）。

## 三、错误是怎么发生的（**这一段是给下一个人的**）

我上一轮写下「停用/启用能重载」时，依据是：

1. 探针文件出现在临时目录，内容看着像宿主写的；
2. 停用后索引块消失、启用后回来（**这个观察是真的**，但它只证明"插件开关生效"，不证明"`apply()` 重跑"）。

**我漏掉的三件事**：

| 漏掉的检查 | 后果 |
|---|---|
| 探针里**没有 `pid`** | 无法区分是宿主（3 个 `DeepSeek-Harness.exe`）还是测试进程（`node --test`）写的 |
| 探针里**没有 `inject` 声明** | 无法判断"加载的是新代码还是旧代码" |
| 没做**反向实验**（删掉文件看它会不会被重新创建） | 一个"文件存在"的观察，被当成了"这次运行写的" |

第 3 条是根因：**「文件存在」不等于「这次写的」**。加上反向实验（删除 → 重载 → 看是否重建）
之后，结论立刻反转。

> 这和 H4 那次「测试假绿」是**同一个病**：都是**把"看起来对"当成"验证过"**。
> 只不过那次发生在测试里，这次发生在**证据判读**里。
