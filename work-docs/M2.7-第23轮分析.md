## 2. 【主要问题】那 3 次报错，根子是同一个

### 2.1 现场

```
seq 152 edit  handover-1  ✅ 成功
seq 157 edit  handover-1  ❌ 你读过的是 vf790f9，磁盘已是 vf627ea
seq 162 read  handover-1  [offset=19 limit=50]   ← 窗口读
seq 167 edit  handover-1  ❌ 你读过的是 v10e2f0，磁盘已是 vf627ea
seq 172 read  handover-1  （整份）
seq 177 edit  handover-1  ✅ 成功
seq 182 read  handover-1  [offset=55 limit=15]   ← 窗口读
seq 187 doc_handover_check handover-1  ✅（不写任何文件）
seq 192 doc_mark handover-1  ❌ 你读过的是 v3231b5，磁盘已是 v5f6780
seq 197 read  handover-1  （整份）
seq 202 doc_mark handover-1  ✅ 成功
```

### 2.2 缺陷一：**窗口读记下的是「片段指纹」，不是「没读过」**

`seq 182` 是 `offset=55 limit=15`，**读到文件末尾**（footer 有 `End of file - total 67 lines`）。

但 `textFromReadResult()` 的实现是：**只剥行号、从第 55 行开始还原**，
于是算出的是"第 55~67 行"的指纹 `v3231b5`。

```
磁盘全文指纹   8455ec7a（259 字符）        ← 真实值
还原出的正文   196 字符
★ 算出的指纹   013385ec                    ← 记录值
两者相等？     false
```

⇒ **它没有记成"没读过"，而是记成了"读过一个片段"的错误指纹。**
之后每一次写都会被拒，直到整份重读。

**这比"没记录"更坏**：没记录时门禁会直接说"你还没读过"（清楚）；
记错指纹时门禁说"你读过的是旧版"（**误导**——它其实读了，只是读的是片段）。

### 2.3 缺陷二：这是**我上一轮引入的**

`20cf9da`（修法 2）当初的设计是：「窗口读不更新指纹，也不覆盖已读」。
但实际代码里，**当 `freshText` 不是 `undefined` 时会走"完整读"分支**——
而 `seq 182` 因为 footer 是 `End of file`，`textFromReadResult()` **返回了正文**
（片段正文），于是被当成完整读处理。

⇒ 修法 2 的守卫**没生效**，因为判定点错了：
它判的是"还原成功没有"，而应该判"**还原出来的是不是全文**"。

### 2.4 缺陷三：AI 自述里那条「只读工具也会让指纹失效」是**误判**

AI 说：「连 `doc_handover_check` 这种"只读"的工具，跑完都会让指纹变」。

**核实结果：`doc_handover_check` 一个文件都没写**（`writeText`/`setFrontmatterFields`/
`rescan`/`markRead` 全部 0 次）。

真实原因就是 2.2：`seq 182` 的窗口读已经记了错误指纹，
`seq 192` 的拒绝跟 check **无关**。

⇒ AI 观察到了正确的现象（"check 之后被拒"），但**归因错了**。
这条如果被当成事实写进交接，下一位会去找一个不存在的 bug。

## 3. 【问题不止一个】另一处：`doc_health` 说「0 条 warn」却列了 1 条

```
seq 209: 文档健康度：0 条 warn（4 份受管文档）。
         ...
         - [H-6] `instruction-1`：标成 authoritative 之后这些文档改过…
```

**自相矛盾**：标题说 0 条，正文列了 1 条。

### 根因

`tools/doc-health.js` 里：

```js
stats: { warnings: result.stats.warnings }   // ← 只统计 5 项检查（H-1~H-5）
```

而 H-6 是**后追加**的 `driftIssues`，**没有计入 `stats.warnings`**。

⇒ 只要 H-6 报了，计数就一定是错的。
这是我在 `752eec1` 加 H-6 时留下的（当时没把计数接上）。

**影响**：AI 会以为"健康度是干净的"，从而跳过处理 —— 而实际上有一条 warn。
`seq 212` 的 AI 自述印证了这一点：

> 「H-6 is a warning about instruction-1 — it doesn't reference read-order content,
> so it's fine. But it says "0 条 warn" in header yet lists one. Let me check whether
> it's benign.」

它**注意到了矛盾**，然后**自己判断成"良性"跳过了**。这一轮是运气好（确实良性），
换一份真引用了 read-order 的交接就会漏掉。
