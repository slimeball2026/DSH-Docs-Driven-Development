## 1. D1：H4 哈希判据被反引号挡住（**真缺陷，用户未发现**）

### 1.1 事实链（全部来自会话日志）

| seq | 事件 |
|---|---|
| 138 | `doc_new` 建 `handover-001`，§5 写 `sha256 = \`B8E89AC6…354C\``（**hex 包在反引号里**） |
| 143 | `doc_handover_check` → **被拒** |
| 144 | 返回：`[H4] §5 验收：有 1/3 条没有证据形式…第一条缺证据的是：- **边界**：\`input.log\` 的 sha256 = \`B8E89AC6…` |
| 211 | 重建 `handover-002`，把 hex 的反引号**去掉** |
| 217 | `doc_handover_check` → **通过** |

### 1.2 根因（源码级，已复现）

`core/handover.js` 的 H4 哈希判据：

```js
re: /\bv[0-9a-f]{6,}\b|指纹\s*[=:：]?\s*[0-9a-f]{6,}|(?:sha256|md5|sha1)\s*[=:：]\s*[0-9a-f]{8,}/i
```

关键是 `[=:：]\s*[0-9a-f]{8,}`：`=` 之后只允许**空白**，然后是 hex。
而 `sha256 = \`B8E8…\`` 里 `=` 后面紧跟的是**反引号**，`\s*` 吃不到它 →

| 写法 | 结果 |
|---|---|
| ``sha256 = `B8E89AC6…354C` `` | **MISS** ❌ |
| `sha256 = B8E89AC6…354C` | **OK** ✅ |
| ``sha256 =  `B8E89AC6…354C` ``（多空格） | **MISS** ❌ |

我用 `checkAcceptanceEvidence()` 对 `handover-001` 的 §5 原文逐字复现，
返回 `{ok:false, missing:["- **边界**：…"]}` —— 与 seq=144 的返回**完全一致**。

### 1.3 为什么这是**判据缺陷**而不是"用户写错了"

三条理由：

1. **反引号是 Markdown 里"这是个值"的标准写法**。用户/AI 把哈希包在反引号里
   是**更规范**的做法，判据却因此拒绝它。
2. **同一个项目里自相矛盾**：`本次会话 id：\`session-…\``（反引号里的会话 id）**能过**，
   因为 session 判据是 `会话\s*id\s*[=:：]\s*\S+`（`\S+` 能吃反引号）。
   而 hash 判据用 `[0-9a-f]{8,}`（吃不到反引号）→ **两条判据对同一种写法给了不同答案**。
3. **错误信息把责任推给用户**：「每条都要能核对…第一条缺证据的是：…」——
   它没有说"你的反引号挡住了判据"，用户只会以为自己漏写了证据。

### 1.4 这个缺陷的次级伤害（**比 D1 本身更糟**）

AI 在 `handover-002` 的 §4 坑表里写了**错误的归因**：

```
| 3 | H4 的哈希判据是 `sha256\s*[=:：]\s*[0-9a-f]{8,}`，`=` 与 hex 之间**不能有反引号** |
```

这条**碰巧说对了**（我实测确认）。但它同时写了：

```
| 4 | 交接文档建好后不能 `edit`（改历史被禁），校验不过只能重建一份 |
```

这条把 **D2 的设计缺口**当成了"理所当然的规则"记下来 ——
下一个读者会以为"交接不能改"是设计意图，而它实际上是**一个没有替代方案的硬约束**。

### 1.5 建议修法（**待拍板**）

判据放宽一格，让它能吃 Markdown 的三种常见包裹：

```js
// 现在
[=:：]\s*[0-9a-f]{8,}
// 建议：允许 = 之后有 ` * _ 这类 Markdown 标记
[=:：]\s*[`*_]*\s*[0-9a-f]{8,}
```

**代价**：可能放宽过头（`sha256 = 见文件` 之类仍不会被误判，因为还是要 8 位 hex）。
**风险低**，且与 session 判据的宽容度对齐。

> ⚠️ 但这是**改冻结判据**（H1–H7 属 M1 冻结范围）。
> **必须你授权**才能动。所以我先把证据摆出来，不动代码。

## 2. D2：交接只能重建、不能改（用户第 1 点，已确认）

### 2.1 会话日志里发生了什么

| seq | 事件 |
|---|---|
| 138 | 建 `handover-001`（status: draft） |
| 143-144 | 校验被拒（H4，见 D1） |
| **211** | **又建了一份 `handover-002`**，而不是改 001 |
| 212 | 返回：`已把旧的交接自动标为 superseded：handover-001` |

最终磁盘上**两份交接**都在：

```
docs/handover-001.md   status: superseded   supersededBy: ["handover-002"]
docs/handover-002.md   status: authoritative
```

### 2.2 用户的判断（我认同）

> 「ai 不知道写交接文档要新建而不是改原来的，这会增加多余摩擦」

**这不是 AI 的错，是插件的提示不到位。** 证据：

- `doc_new` 的返回只说「已创建…已记入已读集合」，**没有提示交接是"一次性文档"**；
- `doc_handover_check` 拒绝时只说「必须改完再复检」，**但没说"改"的正确方式是新建**；
- 而实际上 `edit` 交接会被门禁拒绝（因为交接是必读文档，改它要先重读，
  重读之后又会被"历史不可改"挡住 —— 具体见 §2.3）。

### 2.3 为什么"改交接"实际上走不通（源码核实）

交接文档是 `role: handover`，通常 `status: authoritative` → **在必读清单里**。
所以 `edit` 它要过门禁，而门禁的规则是「改之前必须读过且指纹一致」。

但交接的语义是**历史记录**：改它等于篡改历史。
README 与 SPEC 都写了「交接不建议原地修改」。

**结果是**：用户被夹在两个约束之间 ——
`edit` 要么被指纹拦（要先重读），要么在语义上不该做。
而插件**没有给出第三条路**（比如 `doc_new` 时自动继承并作废旧版，或提供 `doc_supersede`）。

> 实际上 `doc_new` 建交接时**自动把旧的标 superseded** 了（seq=212）——
> 这说明"新建即替代"是**已经实现的行为**，只是**没有告诉 AI 这是推荐路径**。

### 2.4 建议修法（**改动小、风险低**）

**在文案里说清**，不改判据：

1. `doc_new` 建 `role: handover` 时，返回里加一句：
   > 「交接是**一次性文档**：修订请**再建一份**（会自动把旧的标 superseded），
   > 不要 `edit` 旧的。」
2. `doc_handover_check` 拒绝时，如果被拒的是 `role: handover`，加一句：
   > 「修法：用 `doc_new` 建一份新的交接（旧版会自动 superseded），**不要 edit**。」

**这条不需要你授权**（只改文案，不动判据）。我可以直接做。

## 3. D3：看板不随操作刷新（用户第 3 点，已确认）

### 3.1 现象（用户原话）

> 「右侧看板不会随时更新，必须点到别的窗口再切回来才会更新。」

### 3.2 根因（源码级）

`src/client/index.tsx` 的 `createController`：

```js
if ((options.refreshMs ?? 0) > 0) {
  const timer = setInterval(() => { void load() }, options.refreshMs)
  ...
}
```

而 `config.js` 的默认值是：

```js
uiRefreshMs: 0,   // 0 = 不轮询，只在用户操作时刷新
```

**所以默认完全没有轮询。** 而 controller 的取数只发生在：

| 触发点 | 代码位置 |
|---|---|
| 创建时一次 | `void load()` |
| 用户点「⟳」 | `recheck()` → `load()` |
| 用户选项目根 | `selectProject()` → `load()` |
| 用户点「初始化」 | `initializeProject()` → `recheck()` |

**没有任何"窗口重新可见 / 页面 focus"时刷新的订阅。**
所以"切到别的窗口再切回来"能更新，是因为**React 子树被重建**（重新挂载 = 重新 `load()`），
不是因为有什么可见性监听。

### 3.3 这算不算缺陷

**算，但要看怎么定义"应该更新"。**

原来的设计意图（`createController` 的注释）是：

> ⚠️ **不做轮询**：轮询会让 host 每秒被叫一次，而这个面板大部分时间没人看。

这个理由**成立**。但用户的实际期待是：

> 「**AI 改完文档后，我看板上的数字应该跟着变**」——

这不需要轮询，需要的是**在"可能变化"的时机刷新**。合理的三个时机：

| 时机 | 怎么实现 | 成本 |
|---|---|---|
| **窗口重新可见**（`visibilitychange`） | 加一个事件监听 | 极低 |
| **右栏页签被激活**（`tab.visible` 变 true） | 用 `useTabInfo()` 的 `visible` | 低 |
| **AI 每轮结束**（有 `turn/end` 事件） | 需要 host 侧推送或 SSE | **高** |

**建议先做前两条**（低成本、覆盖面大）：
窗口切回来会刷新、页签切回来会刷新。
第三条（实时跟 AI 变动）需要推送通道，是另一个量级的工程。

### 3.4 一个更根本的观察

**看板显示的 `gate N/M` 是会话级的已读状态**，
而它变化的主要原因是「AI 读了文档」—— 那是**另一个进程在写**。

所以真正的"实时"需要 host → client 的推送。
现在的架构（HTTP 拉取）决定了它**本质上不是实时的**。

**诚实的做法**：在 UI 上**明说**"这个数字是快照，不自动刷新"，
而不是让用户以为它该跟着动。这与本项目一贯的"宁可留白也不假装"一致。

## 4. D4：阅读顺序在工作途中变动（用户第 2 点，**设计争议**）

### 4.1 用户的两问

> 「文档被编辑后它就不计入『阅读顺序清单』了，我认为阅读顺序应该是个适用于
> 被交接者初次接手项目的显示指标，它不应该在工作中发生变动。
> 另外，假如工作者在工作中途加了新文档，到底应该算不算他读过？」

### 4.2 先核实事实：**"编辑后不计入"这个说法需要修正**

我查了实际数据（`GET /api/ddd/index`，工作区 `DDD全流程测试`）：

```
gate=0/3
required 条数=3
  id=handover-002  status=authoritative  read=False
  id=read-order    status=authoritative  read=False
  id=spec-report   status=authoritative  read=False
```

`spec-report` 被 edit 过**三次**，但它**仍然在 `required` 里**，
`status` 仍然是 `authoritative`。

**所以"编辑后不计入阅读顺序"并没有发生** —— 发生的是另一件事：

> **编辑后 `read` 变回 `false`**（指纹变了 → 已读失效），
> 所以它在条上从 `✓` 变回空心圆。

这**正是** `core/gate.js` 的设计：改之前必须重读，指纹不一致 = 未读。

### 4.3 但用户的**设计质疑**是成立的

用户说的是：**「阅读顺序」这个词不该随工作变动**。这个直觉有道理：

| 语义 | 应该是什么 | 现在的行为 |
|---|---|---|
| **「接手时该读什么」**（一次性、稳定） | 新会话初次接手时的清单 | ❌ 会随工作变动（新文档加入、指纹失效） |
| **「现在能不能改」**（实时门禁） | 每次都重算 | ✅ 正确 |

**这两个语义被同一个 `required` 数组承担了**，所以用户觉得"它不该动"。

### 4.4 我的判断（供你拍板）

用户说得对**一半**：

- ✅ **UI 的「AI 阅读顺序」条确实应该表达"接手时的清单"** ——
  它是给人看的"该读什么"，不是"现在能不能动手"。
- ❌ **但门禁不能跟着改**。门禁必须实时：改了文档就得重读，这是**不变量**。

**建议（三选一，需要你拍板）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 只改文案** | 条上标注「这是接手清单，✓ 会因文档修改而失效」 | 最小，但没解决"变动" |
| **B. 加"接手快照"** | 新会话首次取数时冻结一份 `required`，条显示冻结版 | 要引入新状态与存储 |
| **C. 拆成两条** | 「接手清单」（冻结）+「当前门禁」（实时） | 信息最清，但 UI 变复杂 |

我倾向 **A → 视反馈再考虑 B**。因为：
**C 会让条上出现两套数字，而本项目最怕的就是"两个不一致的真源"。**

### 4.5 关于「中途加的新文档算不算读过」

现在的行为：`doc_new` 会**自动把它记进本会话已读**（源码 `doc_new.js` 有 `markRead`）。

**这是对的**，理由是：**写它的人当然读过它**（是他写的）。

但用户的问题更深一层：**「接手者」看到的是哪一份？**
如果工作者中途加了 `spec-v2`，接手者拿到的「接手清单」应该是
**工作者最终留下的那一份**，而不是"工作者开始时的那一份"。

> 这一条支持方案 **B**：**快照的时机应该是"交接时"，不是"接管时"**。
> 即：交接文档落定时，冻结一份清单存进交接（或 `_artifacts/`）。
> 但这会把"清单"变成**第二份真源**，与索引漂移 —— 那是本项目极力避免的。

**所以我的最终建议：方案 A（只改文案），并在交接文档的 §2 里
由 AI 自己写清"接手者该读哪几份"。** 这不需要改任何机制。

## 6. 汇总：可做 / 需授权 / 需拍板

### 6.00 第三轮（2026-11-14 用户看过 UI 后）

#### ① 会话间勾泄漏（**我引入的真缺陷，已修**）

用户给截图指出：

> 「阅读顺序的勾应该在换一个会话（也就是下一个交接会话）时被清空，因为 ai 还没读过它们。」

截图证据：API 返回 `gate=0/3`（三份全未读），但条上 3 个 chip **全打了勾**。

| 项 | 内容 |
|---|---|
| 根因 | `localStorage` 键是全局的 `ddd.readOrder.everRead`，没带会话标识 |
| 修法 | 键改成 `ddd.readOrder.everRead.<sessionId>`；root 面板（无 sessionId）用 `__root__` 独立命名空间 |
| 附加 | **三处调用点都必须真的传 `sessionId`** —— 只改键不够（实测过：页签漏传就退化回全局） |
| 验证 | 测试 4 条 + 变异 2 条 |

#### ② 「下一步没变化」——**那是正确的**

用户看到截图里「下一步」仍是 `让用户确认 report.md 的表格格式…`，以为没生效。

核实后：`nextStep` **本来就不该变**（它是交接 §3 第一条）；
变的是「依据文档」——`basisDoc` 现在返回 `null`，那一行**已经消失**。
用户看到的"没什么变化"，实际是"该变的变了、不该变的没变"。

#### ③ 会话 1 的勾全空了 —— **不是缺陷，是宿主重启**

用户说「图一是会话 1，它现在没有勾了」。

我查了三件事：

| 证据 | 值 |
|---|---|
| 宿主进程启动时间 | **09:13:54** |
| GUI 端口 | 51176 → **52731**（重启会换端口） |
| 会话 1 最后写入 | 09:14:04 |
| API（带 session 1 的 id） | `gate=0/3`，三份全 `read=False` |

**根因在服务端**：`adapters/registry.js` 的 `readSetsBySession` 是
**`WeakMap`，以 session 对象为键**（注释原文：key 用 session 对象本身，
会话释放即可回收）。宿主重启后会话对象是**新的**，readSet 归零。

> **这是设计使然，不是 bug**：readSet 是"**这个会话**读过什么"的内存事实。
> 重启 = 新会话 = 确实没读过。
>
> 但它暴露了一个**真实的可用性问题**：重启后所有会话的阅读进度都丢了，
> 而且**没有任何提示**告诉用户"这是重启导致的"。
> 建议：`_artifacts/` 落盘一份 readSet（按 sessionId），或者在索引块里
> 明说「本会话已读为空（宿主重启会清空）」。
>
> **本轮没做**（会引入"第二份真源"，需要你拍板）。

#### ④ 轮询：阅读顺序条不实时（**已修，但有边界**）

用户原话：

> 「图 3 里右侧栏的阅读顺序的勾没有实时刷新，但就在截完图之后它很快就变成 2/3 了。」

**"截完图就变了"恰是证据**：截图让窗口失焦再回来 → 触发了 `visibilitychange`
（上一轮加的）。也就是说，`visibilitychange` 只能覆盖"切走再切回"，
**覆盖不了"一直盯着看"**。

而 `gate.read` 变化的主要原因是 **AI 在另一个进程里读了文档** ——
纯 HTTP 拉取架构下客户端**无从知道**。所以加了 `watchPolling`：

| 设计点 | 值 | 为什么 |
|---|---|---|
| 间隔 | **5 秒** | 不是每秒；`createController` 原注释"轮询会让 host 每秒被叫一次"的理由仍成立 |
| 后台标签页 | **一次都不请求** | `document.hidden` 时直接 return |
| 单次开销 | 一个 GET，几百字节 | — |

> ⚠️ **仍然不是实时**，最坏延迟 = 一个间隔。所以 UI 文案不该暗示"实时"。

#### ⑤ 本轮又踩一次"变异存活"的坑（**这次是断言恒真**）

`polling-runs-when-hidden` 第一次**存活**。我按上轮的教训先查"测试有没有跑到"——
跑到了。真因是**我的断言恒真**：

```js
assert.doesNotThrow(() => tick())   // ← watchPolling 内部 try/catch 把抛吞了，永远不抛
```

改成**数调用次数**，并配一条"可见时确实会刷新"的反向测试（证明前一条不是恒真）。

> 上一轮是"测试没跑到"，这一轮是"断言恒真"。

| 通道 | 语义 | 变不变 |

- AI 自己新建的文档 `read=true`（`doc_new` 会记已读）→ **自动画勾**。
