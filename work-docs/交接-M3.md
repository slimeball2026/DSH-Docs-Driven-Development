## §0 这个项目是什么（**先读这节**）

### 0.1 一句话

> **让 AI 在动手改项目文档之前，必须先读过该读的文档；「读没读」由插件记账并强制，不是靠提示词嘱咐。**

### 0.2 它解决的问题

AI 做长任务时上下文会衰减。传统做法是"让 AI 自己记住"，但会忘。
本项目的办法：**把工程状态外置成文档，每轮只注入一个索引块，并用代码强制 AI 先读后改。**

上一代纯提示词方案（教练模式，同为文档驱动开发）的实测：

> 第二轮共 5 个会话，工具调用总计 **5 次**，其中**真正核查用户机器的只有 1 次**。

⇒ 铁律①：**门禁必须是代码里的 `if`。**

### 0.3 四个环节

```
① adapters/probe.js            判断这个目录是不是 DDD 项目（找激活标记）
② docs/scan.js + registry.js   扫描 docs/，建注册表（内存缓存）
③ adapters/inject.js           每轮往系统提示词注入一个「索引块」
④ adapters/guard.js → ctx.tools.guard()   真正拦 write/edit 的 if
```

「读没读」记在 `readSet`（**会话级、内存 WeakMap**），不落盘。
`edit` 成功 → 指纹变 → 该文档立刻变回"未读"。
**例外**：本会话自己刚写过的文档不再要求重读（`selfWritten`，M2.8 起）。

### 0.4 三条铁律

| # | 铁律 | 为什么 |
|---|---|---|
| **1** | 门禁必须是代码里的 `if`，不是提示词嘱咐 | 教练模式已证明提示词约束会失效 |
| **2** | 插件全局挂载，但作用域是项目 | 装了插件不该让所有项目都被管 |
| **3** | 冻结决策要用户授权才能动 | 见 `docs/架构评审与补充设计-v1.md` §6（Q1–Q13 / R1–R5 / S1–S2） |

### 0.5 术语

| 术语 | 意思 |
|---|---|
| **DDD** | **文档驱动开发**，不是 domain-driven design |
| **受管文档** | `docs/` 下有合法 frontmatter 的 `.md` |
| **门禁** | `core/gate.js` 的 `decideGate()`，拦"没读过就改" |
| **标绿** | `doc_mark` 把 `status` 改成 `authoritative` |
| **指纹** | 文档正文的 sha256 前 8 位 |
| **坟场** | `docs/_graveyard/`，被 `void` 的文档 |
| **引擎步** | `read` + `doc_health` + `doc_handover_check`，**不产出任何文档内容**的调用 |

## §3 下一刀

### 3.1 【第一优先】M3 的核心任务：`read-order` 必读清单半自动渲染

**用户已明确：这件事归 M3，M2.9 只记录方案、不动手。**

#### 3.1.1 现状：两个用途被混在一起

`read-order` 正文里那个 `## 必读清单` 小节，**同时承担两个职责**：

| 职责 | 谁在读 | 数据源 | 需要人手写吗 |
|---|---|---|---|
| **① 门禁判定**：哪些文档必须读完才能改 `docs/` | **机器**（`core/gate.js`） | **frontmatter**（`core/index.js` 的 `buildIndex()`） | **完全不需要** |
| **② 给人看的导航**：先读谁、为什么读、有什么坑 | **人 + AI** | **`read-order` 正文** | 需要 |

**关键事实（已核实）**：门禁的 `required` 清单来自 `buildIndex(entries)`，**只读每份文档的 frontmatter**：

```
status 是 authoritative / partial 且没有 error → 自动进必读清单
status 是 draft / void / superseded / sealed → 不进
```

**它完全不看 `read-order` 正文里写了什么。**

⇒ **手写的那份清单对门禁没有任何作用，它纯粹是给人看的说明。**

#### 3.1.2 那为什么还要手写

因为**"为什么读它"这件事 frontmatter 里没有**：

```markdown
1. `handover-1`（order -10）—— **先读这份**。当前进度、下一刀、坑、验收证据全在里面，
   接手会话照它做就行。
```

`order -10` 这个数字 frontmatter 里有，但「**先读这份**」「**照它做就行**」这种**判断**没有。

#### 3.1.3 "由 frontmatter 渲染"指什么

指那个 `## 必读清单` 小节不再由人手写，而由插件自动生成：

```markdown
## 必读清单

- `handover-1` · order -10 · authoritative · 交接：当前现场…（summary 字段）
- `spec-1` · order 10 · draft · 测试用的规格文档（summary 字段）
```

数据全部来自 frontmatter（`id` / `order` / `status` / `summary`），
**顺序自动按 order 排**，**增删自动跟着变**。

#### 3.1.4 收益

1. **消除一整类过期**：文档删了 / 归档了，清单自动少一条，不会留下指向空文档的条目；
2. **消除 `order` 死锁**（M2.9 花了不少力气修的那个）：不用再手写 `-10`，因为自动排；
3. **少一次"改完 `read-order` 就变回未读"**：如果这一节是生成的，AI 改其他小节时不会因为清单变动而反复失效；
4. **H-3 更准**：现在 H-3 靠"正文有没有提到这个 id"，自动渲染后一定提到。

#### 3.1.5 代价（这就是 M2.8 拍板"先不做"的原因）

1. **"为什么读它"会丢** —— frontmatter 的 `summary` 是"这份文档讲什么"，不是"你为什么要先读它"。
   这两者不同：`summary` 说"交接七段"，而人手写的是"**先读这份**，照它做就行"。
2. **可编辑边界要定** —— 人手写的补充（比如"⚠️ 这份虽然标绿但 §5 有争议"）要不要保留？
   插件生成时覆盖还是追加？这需要一套规则。
3. **`read-order` 自己也在必读清单里** —— 递归问题：渲染 `read-order` 正文时要读它自己的 frontmatter。
4. **它是 `role: index` 文档的正文** —— 生成会改动用户可能已经精心写过的文字。

#### 3.1.6 推荐方案：**半自动**（不是全自动）

```markdown
## 必读清单

<!-- ddd:auto:begin -->
- `handover-1` · order -10 · authoritative · 交接：当前现场…
- `spec-1` · order 10 · draft · 测试用规格
<!-- ddd:auto:end -->

**为什么读**（人手写，插件不动）：
- `handover-1`：**先读这份**，照它做就行。
- `spec-1`：只是占位内容，别补全。
```

**理由**：清单的**成员与顺序**是机械的（该自动），但**"为什么"是判断**（该手写）。
用标记块把两者分开，各管各的 —— 既消掉过期和 order 死锁，又保住人手写的价值。

**工作量估计（M3 量级）**：

| 子任务 | 说明 |
|---|---|
| 标记块语法 | `<!-- ddd:auto:begin/end -->`，要处理"AI 改标记块内内容"的冲突 |
| 渲染函数 | 纯函数：`entries → 清单文本`（放 `core/`，零 IO） |
| 写入时机 | `doc_new` / `doc_mark` / `archive` 之后？还是只由 `doc_health` 检查并提示？**要定** |
| 冲突策略 | 人手改了标记块内 → 覆盖 / 报 warn / 拒绝？**要定** |
| 测试 + 变异 | 至少 8 条测试 + 3 条变异 |

⚠️ **M3 开工前先问用户**：写入时机与冲突策略这两条，是产品决策不是技术决策。

### 3.2 【第二优先】证据台账（结构性天花板）

### 4.3 flex 的根因可能是 `flex-basis`，不是 `maxWidth`

用户给了决定性观察：**"只有当第三列只占一行时，第二列才能变宽"**。

| 写法 | 含义 | 后果 |
|---|---|---|
| `flex: 1 1 auto` | basis = **内容宽度** | 先按内容占位 |
| `flex: 0 0 auto` | **不收缩** | 有多长占多长（**真病根**） |
| `flex: 1 1 0%` | basis = **0** | 拿剩余空间 ✅ |
| `flex: 0 1 34ch` | 封顶**且可收缩** ✅ |

⇒ 只加 `maxWidth` 治不了；必须同时改 `basis` 和 `shrink`。

### 4.4 窄容器里中文会"一字一行"

`whiteSpace: nowrap` 缺了，中文与 `｜` 之间处处可断行，每压窄一档就多折一行。
处方与 4.3 相同：`flex: 1 1 0%` + `minWidth: 0` + `nowrap` + `ellipsis`。

### 4.5 变异脚本的测试白名单会漏（**第四次**）

`mutate-drill-fixes.mjs` 的 `runTests()` 有文件白名单。漏一个 → 对应变异**必然 SURVIVED**，
而"存活"会被误读成"断言太弱"。

**已加自检**：每次跑之前扫 `test/m29-*.test.js`，没登记就 ABORT。
这条自检当场抓出两个一直漏跑的文件（`m15-misc` / `m27-window-read`）。

### 4.6 变异在跑的时候**不能改 `ddd-bundle`**

变异会 `writeFileSync` 临时改源码、跑完 `finally` 还原。
我一边跑变异一边改 `doc-new.js` → **修改被还原步骤覆盖，悄悄消失**。

⇒ 跑变异期间只改 `_m28/` 或文档，别碰被测源码。

### 4.7 改文案后立刻跑 `verify-anchors.mjs`

我删掉「§5 不要放代码块」提示后，一条变异的锚点**静默失效**（出现 0 次），
而它此前一直显示 CAUGHT —— **那个 CAUGHT 是假的**。
检查器如实报了：`锚点出现 0 次 —— 它的 CAUGHT 是假的`。

### 4.8 注释里写 `**/*.md` 会终止块注释

我在 `markSnapshot.js` 的 `/** */` 注释里写了 `docs/**/*.md`，
其中的 `*/` **提前终止了块注释** → 整个文件语法错误。
⇒ 注释里提到 glob 时，避免 `*/` 相邻。

### 4.9 环境坑

| 坑 | 解法 |
|---|---|
| `Start-Process -PassThru` 拿不到 `ExitCode`（沙箱下是 `$null`） | 用**哨兵行**：子进程把退出码写进日志最后一行（`_m27/run-one.ps1`） |
| `git` / `node` 通过管道捕获输出 → `\\.\pipe\LOCAL\... denied` | 用 `Start-Process -RedirectStandardOutput` |
| `robocopy` 同样被沙箱拦 | 用 `Copy-Item -Recurse` |
| 会话日志是 `.zstd` | `node _m23/decode-session.mjs <x.zstd> <out.jsonl>` |
| 动态 `import()` 绝对路径 | Windows 必须转 `pathToFileURL()` |

### 4.10 写「别做 X」必须同时说清「但 Y 要做」

M2.8 写「别给交接留位置」，第 30 轮 AI 把工具自动插的那行**也删了** → H-3 报错。
⇒ AI 会按字面执行提示词。

### 4.11 H11 分不清「引用」和「断言」（**我写交接时自己撞上的**）

我写完这份交接、拿 `checkHandover` 自检，**H11 报了我自己**：

```
- 「坟场为空」—— 坟场内容随时会被用户改变
```

但那一行其实是**引用**（"AI 自曝写了那句「坟场里现在是空的」"），
**不是断言**"现在坟场是空的"。

**H11 做不到这个区分** —— 它只按句式匹配，不判断语境。

⇒ 这正是它**只能是 warn 的原因**：宁可多报一条让人自己判断，
也不能因为"引用了错误写法"就阻断交接。

**给 M3**：如果你要改这条判据，加"引用语境"识别（前后有「写了」「原文」「例如」
等词就跳过）是可以的 —— 但先想清楚：**引用的那句话本身也可能被下一位读者
当成事实**。所以"不跳过"也是一种合理的严格。
