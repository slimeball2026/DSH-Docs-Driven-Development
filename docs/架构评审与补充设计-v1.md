## 1. 结论

### 1.1 一句话判断

**设想的"形态"是对的，"骨架"缺了三根承重梁。**

对的部分：把工程状态外置成文档、让 AI 按文档施工、用会话交接对抗上下文衰减——这三条都被你的教练模式项目实证有效（档 0→2.6，5 次交接，0.4.2 已验收）。
缺的部分：**上下文契约**、**元数据真源**、**信任链**。这三样不补，插件会退化成"给 AI 看的一堆 Markdown + 一个好看但会漂移的图"。

### 1.2 六个结构性缺口

| # | 缺口 | 具体表现 | 后果 |
|---|---|---|---|
| **G1** | **上下文契约缺失** | 设想只说"文档不植入上下文"，没说什么进、多大、何时刷新 | 字面执行 → AI 不读文档；实际执行 → 缓存论断失效。两头都错 |
| **G2** | **元数据真源缺失** | 置信度、阅读顺序、给谁看，全写在"树状图文档"的散文里 | 可视化要靠解析 Markdown；置信度无法推导、无法自检、必然漂移 |
| **G3** | **信任链缺失** | 没有"读了哪些文档""文档写到哪个版本""交接合不合格"的记录与判据 | 退化为提示词约束。而示例已证明提示词约束会失效（F6：5 个会话只有 1 次真核查） |
| **G4** | **边界与状态缺失** | 与 AGENTS.md / skill / todo / goal / present / projections / compact 七个既有机制的关系未定义；流程是线性四步而非状态机；坟场无硬隔离；多会话并发无保护 | 重复造轮子 + 机制打架；模型卡在"问完了没规划"的中间态；坟场误判不可逆；fork 会话互相覆盖 |
| **G5** | **工具面设计缺失** | 只说"文档编辑走工具"，没说**加什么工具、跟既有 `write`/`edit` 怎么共存** | 新增工具 = 新增歧义；模型在两个都能干同一件事的工具之间按习惯选，检查形同虚设（§2.5） |
| **G6** | **目录布局缺失** | 只定义了三个**可视化分区**，没说磁盘上怎么落地 | 路径判定、guard 规则、索引扫描范围、git 范围全部无处安放；"过程产物"无家可归（§2.6） |

### 1.3 三条最该从示例里吸收的做法

1. **决策台账 + "不要重开"**（示例的 D1–D11 / R1–R16 / Q1–Q7）。这是跨会话一致性的真正保障，设想里完全没有。
2. **"陷阱"的显式标注 + "不要执行"**（09/10/11 的 🔴）。负向知识的价值高于正向知识，且必须**原地保留 + 显式禁止**，不能只是扔进坟场。
3. **"验收以日志为准，附会话 id + seq，不接受应该可以"**。可证伪的验收，是整个体系里唯一真正"物理"的东西。

### 1.4 一个必须先做的决策（**已拍板：Q1 = B，施工约束器**）

**这个插件到底是"文档管理器"还是"施工约束器"？**

- 若是**文档管理器**：重心在 UI、检索、版本、健康度。成本主要在 client 端（React + 构建链），AI 侧只加一个索引块。
- 若是**施工约束器**：重心在状态机、门禁、证据落盘。成本主要在 host 端，UI 只是看板。

**拍板 B**：先做约束器。理由：教练模式证明了这条路有真实价值且能验收；纯管理器路线很容易变成"又一个文件树"。UI 只做"当前步骤 + 必读清单 + 交付物"三块。

> 这意味着 **M0/M1 完全不做 UI**（见 §5），client 半侧的工程量推迟到 M2。

### 1.5 与教练模式的结构性对照

这两件事看起来完全不同，但**失败模式是同一个**。对照一下，能省掉一次试错：

| | 教练模式 | 文档驱动插件 |
|---|---|---|
| 核心状态 | 学习者的进度（11 个相位） | 项目的施工进度（建议 6 个相位） |
| 唯一真源 | 会话日志折叠 | 文档 frontmatter + 会话日志折叠 |
| 强制手段 | 工具前置条件（四条 + 新证据规则） | 工具前置条件（必读已读、文档校验通过） |
| 注入形态 | 每轮状态块（`systemPrompt.context`） | 每轮索引块（同机制） |
| **最贵的教训** | 状态机把路堵死 → 模型卡在 `INIT` 干聊 | **会一模一样地发生**：卡在"问完了没规划" |
| 验收方式 | 会话 id + `seq` | 同 |
| 最难的部分 | 让"强制"真的落在代码里而不是提示词里 | 同 |

**结论**：教练模式的**方法论**（状态机 + 工具门禁 + 每轮状态块 + 日志折叠 + 证据验收）可以整套搬过来。**不要重新发明**。

反过来，教练模式**没有**而文档驱动**需要**的，只有三样：文档元数据模型、文档健康度、UI。这三样才是这个插件的真正新增工作量。

## 2. 必须先改的六处

### 2.1 "文档不植入上下文"——这个论断字面执行会自毁

设想的原文（第 4 行）：

> 优势：文档本身不植入ai上下文,任意更改也不会破坏缓存前缀,且易于跨会话转接工作

**问题**：文档驱动开发的定义就是"AI 按文档施工"。如果文档真的不进上下文，AI 就不知道文档说了什么，整个机制失效。

**但你的直觉是对的，只是表述需要精确化。** 真正成立的命题是：

> **上下文里只常驻"索引"（小、稳定、可推导）；正文按需加载（append-only，不碰前缀）。**

拆开看，三个子命题，成立程度不同：

| 子命题 | 成立吗 | 真正的机制原因 |
|---|---|---|
| 改文档正文不破坏缓存前缀 | ✅ 成立 | **不是**因为"不在上下文"，而是因为读取是**追加**进历史的。任何追加都不动前缀 |
| 改文档正文不影响 AI | ⚠️ 不成立 | 如果 AI 已经读过 v1，而磁盘上是 v2，上下文里会**同时存在两个版本**——这是比缓存破坏严重得多的问题（矛盾依据） |
| 跨会话转接容易 | ✅ 成立 | 但瓶颈是**交接质量**，不是文档位置 |

**三个必须补的机制**：

**(a) 版本一致性**。文档被改后，AI 手里的是旧版。要么显式标"你读的是 v1，磁盘是 v2，请重读"，要么在工具层拒绝基于旧版的操作。DSH 已有先例 `[实测]`：

> `@deepseek-ai/dsh-fs-observation-policy`：`edit` 要求先 `read`；文件自读取后变化 → `FS_STALE_VERSION` 拒绝，提示 "re-read the file, then retry"。
> 已知限制：「会话恢复后不携带任何已观察状态，因此必须重新读取」。

这条策略在本机是**默认关闭**的（`dsh-base` 里 `disabled: true`）。文档驱动插件应该**显式开启它，或实现等价逻辑**——因为文档就是这个插件的"代码"，改错版本等于改错代码。

**(b) 指纹可见**。不需要文件 watcher。DSH 的 AGENTS.md 机制用的是"成功的 read/write/edit 触发刷新"`[实测]`。同样的低成本方案：在每轮状态块里渲染每份必读文档的**指纹**（`mtime` + `size`，或 hash 前 8 位）。AI 发现指纹变了就知道要重读，不需要任何监听器。

**(c) 分层**。明确三层，缺一不可：

```
L0 索引块   systemPrompt.context()   每轮重算、不累积    ≤ 800 tokens
   └ 当前切片 / 当前阶段 / 必读清单(id + 一句话 + 置信度 + 指纹) / 禁止清单(sealed 的 id + 原因)

L1 正文     read 工具                 按需、append-only   单份 ≤ 8k tokens
   └ 读完写 tool/result.data.meta，留下"读过哪份、哪个指纹"的记录

L2 摘要     文档顶部 TL;DR            按需、极短           ≤ 200 字
   └ 用于"要不要读全文"的快速判断
```

L0 用 `systemPrompt.context()` 而不是 `section()`，理由在教练模式 SPEC D9 已经论证过 `[实测]`：context 是**每请求重新装配的快照**，"本快照取代上一份快照"，天然满足"每轮都有、不累积"，且不动系统提示词前缀。

**代价**：L0 每轮都进请求，即使内容不变也要付固定 token。所以 L0 必须小（≤800 tokens）且**尽量稳定**（变化只在"必读清单变了"时发生，而不是每轮都变）。

**要写进设计的一条硬约束**：

> 索引块里**不得**出现随每轮变化的内容（时间戳、当前步骤编号、进度数字）。这些属于"状态"，应该走独立的注入通道（教练模式的做法），否则每轮都在破坏缓存——这恰恰是设想想避免的事。

### 2.2 用一份"树状图文档"同时当导航和布局——会重演 00 索引的失败

设想第 16 行：

> 阅读顺序：位于树状图样式文档中,用于提示ai初次工作时应该先按照哪些顺序阅读文档,同时也是树状图可视化的依据.

**这句话里塞了两个职责**：AI 的导航依据 + UI 的布局依据。你的示例文档恰好演示了这个模式的结局。

看 `00. 阅读顺序.md` 实际长什么样：它同时是导航表、开工检查清单、三条禁忌、路径表、"另一半文档在哪"、历史事故说明。**一份文档承担了 6 个职责**，结果就是它自己说的：

- 标题写"共 11 份"，实际目录里有 **15 个文件**，而索引表列了 **13 项**——三个数字互不相等
- 表格第 5 行 `05` 的状态是 `🟠 部分过期`，但这一行本身又写着"仅 §9 的 A7 12 条清单…仍不可替代"——**状态和用途在同一格里打架**
- 每加一份文档就要**重编号**（00 第 14–17 行自述：曾经靠生成脚本重编号，而脚本会**覆盖**手工修改，最后只能把脚本删掉）

这不是写得不好，是**结构决定的**：手写的、散文的、单一真源的索引，一定会漂移。

**替代方案：元数据是真源，图是渲染。**

每份文档的 frontmatter 承载机器可读的元数据，树状图文档和 UI 布局都从元数据渲染：

```yaml
---
id: spec-tier2                    # 全局唯一，稳定，永不变
title: 档 2 施工图
role: spec                        # index|spec|decision|evidence|log|handover|instruction
order: 20                         # 数值，可插值（10/20/30），插入不必重编号
status: authoritative             # 见 §附录B 的封闭枚举
scope: [tier2]
supersedes: [spec-tier1]
sections:                         # 段落级状态——解决"只有 §4 还活着"的问题
  - anchor: "#7"
    status: authoritative
  - anchor: "#2"
    status: superseded
    supersededBy: spec-tier1#13
summary: 档 2 的全部功能切片与验收记录，含 Q1–Q7 决策
tokens: 12400
verifiedAgainst: { dsh: 0.2.1-rc.1, bundle: 0.4.2 }   # 机器可查的锚点，不靠时间
basis: 实测                        # 这条结论是怎么来的
---
```

**收益**：

| 问题 | 手写树状图文档 | frontmatter 元数据 |
|---|---|---|
| 插入一份文档 | 重编号全部 + 改表 | 加一行 `order: 25` |
| 判断"哪份失效" | 读完整份散文 | 读 8 行 frontmatter |
| 段落级失效 | 只能写在正文里 | `sections[].status` |
| UI 渲染 | 解析 Markdown 表格，格式一变就崩 | 直接读 JSON |
| 一致性校验 | 人工 | 可自动 |

**额外收益**：DSH 的文档预览**原生渲染 frontmatter 为键值列表** `[实测]`（`dsh-client-ui-sidebar-documentpreview`：「文档开头的 YAML frontmatter 在 Markdown 正文上方显示为键值列表」）。也就是说，**点开文档就能看到它的元数据卡片，零成本**。

**代价**：写文档的人要记得填 frontmatter。缓解办法：插件提供一个 `doc_new` 工具生成模板，或者交接时自动补全。

### 2.3 没有"信任链"：读没读、写没写、接没接得住

这是三个**可校验但设想里完全没有**的问题。

#### (a) 读没读

教练模式的档 1 最重要的一课（交底 §8.0 / F6）：

> 五个会话的工具调用总计 5 次，其中**真正核查用户机器的只有 1 次**，且发生在用户显式提供文件路径之后。

同理：**如果文档驱动依赖模型自觉去 `read`，它一定会退化。** 5 个会话里可能只有 1 个真的读了必读清单。

**必须做的**：

1. **不要新增 `doc_read` 工具**——让模型在 `read` 和 `doc_read` 之间选，等于自造歧义（详见 §2.5）。改为**监听 `tools/result`**：当一次 `read` 的目标路径是"已登记文档"时，由插件记录 `{ id, fingerprint, at }`。模型不需要知道插件存在。
2. **进阶段门禁**：从"规划"进入"施工"前，检查 L0 索引里的所有 `authoritative` 文档是否都有本次会话的读取记录。没有 → 施工工具拒绝，并列出缺哪几份。
3. 折叠会话日志得到"已读集合"，渲染进 L0 索引块（像教练模式的【核查证据】行）。

这是**把软约束变成代码里的 if**——正是教练模式档 1 的核心方法论。注意"变成 if"指的是**判据**，不是**换工具**。

#### (b) 写没写

设想第 25 行："它会自己对相关文档进行编辑，编辑行为可能包括'编写日志,勾选完成任务,更新文档任务状态,记录决策等'"。

**问题**：AI 会**声称**自己改了文档但实际没改。你的示例里已经有这个教训（交底 §7 F4）：

> 实证：档 0 日志中教练说「我保留的状态：目标 Photoshop，进度在板块 1 第 1 步」——但档 0 原型**没有任何持久化**，这是不实陈述。
> 建议：不得声称已保存进度 / 已记录跳过原因 / 已写入会话状态，除非确实写入了持久化存储。

**必须做的**：

1. **不替换 `write`/`edit`，而是给它们"记账"**：用 `tools/post-execute` 或 `tools/result` 观测成功的写入，自动更新文档的 `lastWriter` 与 fingerprint。**同一套工具，只是插件在旁边记了一笔。**
2. **元数据由插件自动维护，不靠模型填**：`lastWriter` / `fingerprint` / `updatedAt` 都是机器写的字段（见 §附录 B1 的标注）。
3. 每轮 L0 索引块渲染【文档写入状态】："本次会话已更新 3 份（spec-tier2、handover-2.6、decision-log）；decision-log 已 5 轮未更新"。没写的会显示"未更新"，模型看到就会补。

**只有一种情况需要新工具**：写入动作本身需要"校验 + 拒绝"的语义（比如"改了 `sealed` 文档"或"改了别人的文档"）。这时候用 `tools/pre-execute` **拦**，而不是提供另一个工具让模型选（§2.5）。

#### (c) 接没接得住

设想第 23 行说交接时"ai 会写一份交接文档,同时对树状图样式文档进行编辑"。**没有任何验收判据**。

而你的示例证明了交接质量方差极大：12 和 13 都是交接文档，但 13 里还写着"我上一轮问过但用户去交接了，没有明确回答"——**这种"未决问题"恰恰是最容易在交接中丢失的信息**。

**必须做的**：交接不是"写了文档"就算完成，而是**可机器校验 + 可演练**的：

| 判据 | 校验方式 |
|---|---|
| handover 文档存在，§1–§6 非空 | 解析 frontmatter + 章节标题 |
| 索引已更新（handover 排第一） | `order` 排序 |
| 每份 `authoritative` 文档本次交接内被复核过 | `verifiedAt` |
| `sealed`/`void` 不在必读清单 | 集合差 |
| "下一刀"含 ≥1 个可执行动作（具体工具/路径） | 正则 + 人工兜底 |
| **冷启动演练**：新会话第一轮能复述"目标 + 下一步 + 依据文档 id" | 人工，但可脚本化评分 |

最后一条是**最硬的**，也最有价值。它把"交接质量"从主观变成可观测。

### 2.4 流程只有"顺序"，没有"状态与门禁"

设想第 6 行：

> 用户使用插件时,agent不会直接开工,而是先询问用户获取更多信息,做工程规划,然后产出这些文件…随后才按照这些文档进行开发

这是一条**线性流程**（问 → 规划 → 写文档 → 开发），不是**状态机**。区别在哪：

| | 线性流程 | 状态机 |
|---|---|---|
| 谁保证顺序 | 提示词（模型自觉） | 工具的**前置条件**（代码里的 if） |
| 模型跳步怎么办 | 无手段 | 调用被拒 + 明确理由 |
| 能不能回退 | 不能 | 可以（显式转移） |
| 卡住了有没有出口 | 没有 | 每个状态必须有出口 |

**这正是你教练模式档 1 最贵的一课**，原话（01 §四 坑 6）：

> v2.1 时有 5 个会话卡在 `INIT` 再也不调 `coach_plan`，于是所有工具被拒。现在靠 INIT 状态块的命令式文案 + 人设的"最高优先级提醒"兜住。**如果你加新状态，注意别再造出"只能干聊"的死角。**

以及档 2 的总结（12 §8）：

> 这个项目最容易犯的错，不是"功能没做完"，而是**为了把清单打勾，造出一个模型走不出去的状态**。

**文档驱动插件会以完全一样的方式失败**：模型"询问用户获取更多信息"之后，可能再也不产出规划文档，于是永远停在"问完了但没规划"的中间态。**而这个中间态在设想里根本不存在**——它只有四个顺序步骤，没有"卡住了"这个概念。

**必须做的**：

1. 把流程定义成**显式状态**，每个状态有：进入条件（哪个工具调用）、出口（哪几个）、驻留还是过渡。
2. **每个状态的每个工具调用，都要有明确的允许/拒绝集合**（不是"应该"，是代码里的 `if`）。
3. **每个状态必须有出口**。规划阶段写不出文档怎么办？验收不通过怎么办？用户中途换需求怎么办？
4. 用**命令式状态块**告诉模型"现在只能做这几件事"（教练模式 R14 的教训：命令式文案把 5 个卡死会话全部救回来了）。

**建议的最小状态集**（6 个，比教练模式的 11 个少很多，因为文档驱动的分支本来就少）：

```
IDLE ──doc_start──▶ CLARIFY ──doc_plan──▶ PLAN_REVIEW ──用户确认──▶ BUILD
                        ▲                                              │
                        │                                              │
                        └────────── replan ──────────────────────────┤
                                                                       │
BUILD ──用户确认交接──▶ HANDOVER ──校验通过──▶ DONE（本切片）
BUILD ──完成全部任务──▶ REVIEW ──验收通过──▶ DONE
```

**关键**：`CLARIFY → PLAN_REVIEW` 之间的门禁是"规划文档存在且通过 frontmatter 校验"；`BUILD` 的入口门禁是"必读文档已全部读过"。这两条就是 §2.3 的信任链落到状态机上的形态。

### 2.5 新增工具 vs 拦截既有工具：模型怎么知道该选哪个

> 这一节回答一个具体的反对意见：**"你让我用 `doc_update` 替代 `write`/`edit`，但 AI 知道该选哪个吗？总不能把原工具删了。"**

这个反对意见是对的。上一版把"用新工具替代 `write`/`edit`"写得太粗糙，它同时犯了三个错：**新增歧义、重复实现、把风险从"写错"降级成"选错"**。

#### 先说结论

> **能用"拦截 + 记账"解决的，就不要"新增工具"。**
> 新工具只应该出现在**既有工具表达不了的能力**上，而不是"我想在旁边加个检查"。

判断标准只有一条：

| 问题 | 结论 |
|---|---|
| 这件事**模型已经知道要做**，只是我担心它不做 / 做错？ | → **拦截既有工具**（`guard` / `pre-execute`），**不要新工具** |
| 这件事**既有工具根本做不到**（模型连"可以做这件事"都不知道）？ | → **必须新工具**，且要在状态块里点名 |

#### 为什么"新工具 + 保留旧工具"是最差的组合

三个具体代价：

**(a) 歧义必然产生，而且**吃亏的总是新工具**。** 两个工具都"能改文件"，描述再清楚模型也会按习惯选。你的示例里已经有一例：`fcaf00c2` 会话中用户问一个工具问题，模型选了 `web_search` 而不是 `coach_research`——尽管后者才是这个模式的专用检索工具。**专用工具存在 ≠ 模型会用。**

这条的杀伤力在于：如果你把**门禁**建在 `doc_update` 上，而模型习惯性地用 `write`，那么**门禁是被静默绕过的**——你不会收到任何错误，只会发现"文档没更新"。这比没有门禁更糟，因为它给了你虚假的安全感。

**(b) 重复实现。** `doc_update` 要实现定位、替换、编码、原子写、diff、沙箱提权……这些 `write`/`edit` 全都做好了（`[实测]`：`write`/`edit` 会派生可回放的 diff 卡片元数据；有 `fs-sandbox` 时还会公开 `sandbox_permissions` / `justification` 走审批）。重写一遍只会更差。

**(c) 把风险降级了。** 你担心的是"文档被乱改"，新工具解决的是"用哪个工具改"。**只要 `write` 还在，风险一点没少**——模型完全可能"正确地"用 `write` 绕过去。这是**换了问题，不是解决了问题**。

#### 那"删掉旧工具"行不行？

技术上可以（`[实测]`）：`tool-fs` 的配置里 `write` / `edit` 默认 `true`，设为 `false` 就**同时省略工具及其指导文本**（"将开关设为 `false` 可省略对应工具及其指导文本"）。所以隐藏是干净的，不会留下"教模型用 write"的孤儿提示词。

但**不应该这么做**，三个理由：

1. **`read` 不能关。** `read` 是通用能力（看代码、看日志、看交付物），关掉它整个插件就没法工作了。而 `read` 在、`write` 不在，模型会转向 `pwsh` 写文件——`guard` 当然能拦 `pwsh` 这个**工具**，但拦不住"这条 shell 命令到底会不会写文件"（`pwsh` 的参数是任意字符串，要判断副作用等于写一个 shell 解析器）。教练模式就是因为这个原因，明确决定 `pwsh`/`bash` **本阶段不加守卫**。
2. **通用文件编辑能力被剥夺。** 文档驱动项目里，模型还要改代码、改配置、改测试。全都塞进 `doc_update` 是灾难。
3. **`write`/`edit` 自己已经在做一半的事了。** `[实测]`：`write`/`edit`/`apply_patch` 成功后会发出 `fs/observed`（含版本），并派生 diff 元数据；`dsh-workspace-changes` 更是已经在做"每轮改了哪些文件、每个文件前后对比"的记录。**你要的"记账"，宿主已经做了一大半。**

#### 正确做法：三层，从"零新工具"到"必须新工具"

**第一层：让路径自己说话（零新工具，零歧义）**

不给文档单独的读写工具，让文档就是普通文件，靠**路径约定**区分。目录布局见 §2.6：

```
<workspace>/<项目>/
  docs/            ← 受管（有 frontmatter，进索引，guard 生效）
  _graveyard/      ← 只读坟场
  deliverables/    ← 交付成品
  _artifacts/      ← 过程产物（不受管）
```

插件注册一个"项目根"配置（`projectRoot`），所有路径判定都是相对于它的一次前缀比较。**模型完全不需要知道插件存在**。

这一层能解决：读没读（监听 `read` 的 `tools/result`）、写没写（监听 `write`/`edit` 的 `tools/result`）、版本一致性（比较 fingerprint）、坟场隔离（路径前缀判断）。

**第二层：拦（`guard` / `tools/pre-execute`，仍然零新工具）**

需要"拒绝"的场合，**拦**比"换个工具"有效得多，因为拦是**不可绕过**的：

```js
ctx.tools.guard((exec) => {
  const path = exec.arguments?.file_path
  if (!isDocPath(path)) return                    // 非文档，放行
  if (isSealed(path)) return '这是 sealed 文档，禁止修改；如需变更请先解除封存'
  if (isGraveyard(path)) return '坟场文档只读'
  if (isStale(path)) return `文档已被 ${writer} 修改（seq ${seq}），请先重读`
  // 放行
})
```

`[实测]` `ctx.tools.guard()` 是**同步、单调、分层**的：返回字符串即拒绝，**后续监听器无法把拒绝重新变为允许**，没有插件能强制放行。这正是"文档是这个插件的代码"所需要的强度。

关键点：**模型看到的仍然只有 `write` 和 `edit`**。它不需要选工具，只需要接受"有时候会被拒绝，且拒绝理由告诉它该干什么"。

**第三层：只在既有工具表达不了时才新增（并且要"点名"）**

确实需要新工具的情况只有几类：

| 场景 | 为什么既有工具不行 | 新工具 |
|---|---|---|
| 让文档"进入/退出受管状态" | `write` 表达不了"我要新建一份符合 schema 的文档" | `doc_new(role, title, ...)` → 生成带 frontmatter 的模板 |
| 段落级状态变更 | 改 `sections[].status` 需要结构化输入，`edit` 只能做字面替换 | `doc_mark(id, anchor, status, reason)` |
| 交接的整体校验 | 不是文件操作，是一次"检查 + 报告" | `doc_handover_check()` |
| 健康度自检 | 同上，跨多份文档的只读分析 | `doc_health()` |

这四类的共同点：**它们都不是"另一种写文件"，而是"文件操作表达不了的动作"**。而且数量很少（4 个以内），不会造成工具目录膨胀。

#### 新工具必须"点名"，不能靠模型自己发现

新工具一旦存在，就必须在**每轮状态块**里点名，否则等于不存在（`coach_research` 被 `web_search` 抢活就是先例）。做法：

```
【文档操作】
- 新建文档 → doc_new（不要手写 frontmatter，校验会失败）
- 改段落状态 → doc_mark
- 改正文 → 直接用 edit（受管文档会被校验；sealed 会被拒绝）
- 交接前 → doc_handover_check（不通过不许交接）
```

这段每轮都在，且**明确说了"改正文用 `edit`"**——把默认路径指回既有工具，新工具只出现在它真正不可替代的位置。

#### 一条可直接用的判据

设计任何一个新工具之前，问三个问题：

1. **模型不用这个工具，能不能完成这件事？** 能 → 不要新工具，用拦截。
2. **这个工具是不是"另一个 `write`"？** 是 → 不要，用 `pre-execute` / `guard` 拦 `write`。
3. **如果我把这个工具删了，模型会不会卡住？** 不会 → 它不必要；会 → 它必要，但要写进状态块点名。

补一条第 4 问，专门防"新工具被冷落"：

4. **模型会不会已经有一个更熟的工具能干这件事？** 会 → **不要新工具**，除非你能把那个旧路径堵死（而堵死通常有代价，见上一节）。

#### 一个真实的对照：`coach_check` 为什么成功，`doc_update` 为什么会失败

教练模式的 `coach_check` 是个"新工具替代旧能力"的**成功**案例，值得对照：

| | `coach_check` | 假设的 `doc_update` |
|---|---|---|
| 旧能力 | 没有。`pwsh` 能跑命令，但**没有"只读核查"这个受限通道** | `write`/`edit` 已经能做，且做得更全 |
| 模型不用的后果 | 没法核查（`coach_verify` 直接失败），**被前置条件逼着用** | 用 `write` 照样改成功，**没人知道** |
| 是否唯一通道 | ✅ 是（`pwsh` 被白名单收窄，且 `coach_check` 是唯一会写 `checks` 的） | ❌ 不是 |
| 结果 | 实机验证有效（A1/A2/A5 都有 `coach_check` 调用） | 会被静默绕过 |

**结论**：新工具能成功的唯一条件是——**它是完成这件事的唯一通道**。`coach_check` 是（因为 `coach_verify` 只认它写的证据）；`doc_update` 不是（因为 `write` 一样能改，而插件无法区分）。

想让 `doc_update` 变成唯一通道，就必须**堵死 `write` 对文档路径的写入**（`guard` 拒绝）。但那样一来——**为什么不干脆让 `write` 自己通过 `guard`？** 回到 §2.5 第二层。

#### 顺带修正：`doc_read` 也不该有

同理，**不要新增 `doc_read`**。`read` 已经能读，新增一个"专用读文档工具"只会让模型在两者之间犹豫。用 `tools/result` 观测 `read` 的调用就够了：

```js
ctx.on('tools/result', (event) => {
  if (event.name !== 'read') return
  const id = docIdOf(event.arguments?.file_path)
  if (id) recordRead(id, fingerprintOf(id), event.seq)
})
```

模型视角：**只有 `read`，没有别的选择。** 插件在背后记账。这就是"把软约束变成代码里的 if"的正确形态——**if 在插件里，不在模型的选项里**。

### 2.6 项目目录布局：一个项目根，四个子目录

设想只说了"工作区 / 交付成品 / 坟场"三个可视化分区，没说它们在磁盘上怎么落地。这个决定影响**路径判定、guard 规则、索引扫描范围、git 范围**，必须先定。

**方案：工作区里一个项目根文件夹，里面四个子目录。**

```
<workspace>/
  <项目>/                     ← 项目根（一个项目一个，多个会话共用）
    docs/                     ← 工作文档：受管、有 frontmatter、进索引
      _graveyard/             ← 坟场：只读（同目录，见 §3.3）
    deliverables/             ← 交付成品（present 声明）
    _artifacts/               ← 过程产物：备份、验收证据、构建中间物（不受管）
```

**为什么是四个不是三个**：设想的三分区漏掉了"过程产物"。看你的教练模式项目，它实际上有五类目录：

| 实际目录 | 归属 |
|---|---|
| `coach-mode-bundle/` | 代码本体 → 就是 `<项目>/` 本身或其中一部分 |
| `教练模式-文档-档2阅读版/` | → `docs/` |
| `_dist/*.tgz` | → `deliverables/` |
| `_backup-0.3.4-*/` | → `_artifacts/` |
| `_verify-20261017/` | → `_artifacts/`（验收证据，但**不是**受管文档） |

备份和验收证据**塞进哪都不合适**：放进 `docs/` 会被当成受管文档（frontmatter 校验会失败，且会污染必读清单），放进 `deliverables/` 会污染交付清单。所以必须有第四个落点。

**每个目录的规则**：

| 目录 | 受管 | 进索引 | guard | 可被 AI 写 | git |
|---|---|---|---|---|---|
| `docs/` | ✅ frontmatter 校验 | ✅ | 按 role 查表（§3.1） | ✅ | ✅ |
| `docs/_graveyard/` | ❌ | ❌ | **读也拒** | ❌ | ✅（Q4 选 A 的理由） |
| `deliverables/` | ❌ | ❌ | 放行 | ✅ **直接产出** | ⚠️ 排除 `.tgz` 等二进制 |
| `_artifacts/` | ❌ | ❌ | 放行 | ✅ | ⚠️ 建议排除 |

**关键约定：成品直接产出到 `deliverables/`，不要先产出再移动。**

原因见附录 A13 `[实测]`：`present` 记录的是**绝对路径**，文件移动后声明失效（"源文件删除或移动后，无法通过原声明打开"）。所以"先在 `_artifacts/` 打包、验收通过后再移进 `deliverables/`"这个看起来很自然的流程会**让交付卡片失效**。

**交付物视图以谁为准**：

| 选法 | 问题 |
|---|---|
| 只认文件夹（在里面就算交付） | 没有"这是最终版"的语义，中间产物混进去也显示 |
| 只认 `present` | 与视觉上的三区不一致，文件夹会空着 |
| **文件夹是约定位置，`present` 是声明**（推荐） | 两者不冲突 |

推荐第三种：AI 把成品产出到 `deliverables/` 并调 `present`。UI 从文件夹里扫到但**未被 `present`** 的，标成"未声明"并提示补一下。这样既不破坏既有工具，文件夹也不是空的。

**`deliverables/` 守住一条**：只放**通过验收**的产物。否则它会退化成杂物间——这正是示例里 `_dist/` 和 `_backup/` 混在一起时发生过的事。

**为什么叫"项目"不叫"会话"**：**按会话分文件夹会让跨会话共享失效**——第二个会话看不到第一个会话的文档，而文档驱动的全部价值就是"多个会话共用同一份文档集"。项目根是**项目级**的，会话只是执行单位（与 §4.4 的切片命名讨论一致）。

**配置项**：`projectRoot`（相对于工作区）。所有路径判定都是相对它的一次前缀比较，不出现绝对路径。

## 3. 补充清单（按优先级）

### P0 · 不做就不能开工

#### 3.1 文档角色（role）——把"文档"拆开

设想里"文档"是一个词，但示例里至少有 7 种完全不同的东西。它们的**更新规则、失效速度、读者、是否进上下文**全都不一样：

| role | 是什么 | 可改写 | 进 L0 | 衰减驱动 | 时间可靠吗 |
|---|---|---|---|---|---|
| `index` | 导航（阅读顺序、必读清单） | 只由元数据生成，不手写 | ✅ 就是 L0 | 随成员变化 | — |
| `spec` | 规格：要做什么 | 版本化改写，旧版 superseded | 按需 | 被 supersede / 外部条件变（DSH 升级） | ❌ 一年不改也可能全对 |
| `decision` | 决策台账：为什么这么做、不要重开 | **只追加** | ✅ 摘要 | 被新决策取代 | ❌ |
| `evidence` | 证据：验收报告、日志、哈希 | **不可改写** | ❌ | **永不衰减** | ❌ 旧不等于错 |
| `log` | 过程日志：今天做了什么 | 只追加 | ❌ | **永不衰减** | ❌ |
| `handover` | 交接快照：给下一个会话 | **不可改写**（新的另起一份） | ✅ 排第一 | 下一份 handover 出现 | ❌ 与时间无关 |
| `instruction` | 一次性流程指令（阶段 1~6） | **不可改写** | ❌ | 执行完成 | ❌ 与时间无关 |

> **注意最后一列**：**七个 role 里没有一个靠时间衰减。** 所以 `confidence` 不能做成"TTL 自动降级"——衰减驱动是**事件**，不是时间。详见 §6 的 Q5 说明。

**为什么重要**：示例里 09/10/11 变成"陷阱"，**不是它们写错了，而是它们被放错了位置**——一次性流程指令和持续有效的规格混在同一编号序列里，读者无法从形式上区分。有了 `role`，UI 可以分栏渲染，AI 可以按 role 决定读不读。

**`role` 还顺带解决了工具面问题**（§2.5）：不同 role 的**写入规则**不同，而这些规则全部可以由 `guard` 按"路径 → role"查表实现，**不需要为每种 role 造一个工具**：

| role | `write` | `edit` | 说明 |
|---|---|---|---|
| `spec` | 允许（覆盖需先读） | 允许 | 版本化改写 |
| `decision` | ❌ 拒绝 | 允许**仅追加**（`new_string` 非空、`old_string` 匹配末尾锚点） | 台账不许删改 |
| `evidence` | ❌ 拒绝 | ❌ 拒绝 | 证据不可改写 |
| `handover` | ❌ 拒绝 | ❌ 拒绝 | 用 `doc_new` 另起一份 |
| `log` | 允许 | 允许追加 | — |

**注意最后两行**：`handover` 的"另起一份"是既有工具表达不了的（要生成带新 id、`order: 0`、七段骨架的文件），这才是 `doc_new` 存在的理由。

#### 3.2 状态枚举——必须是封闭集合

示例里的状态标记是**自由文本 + emoji**，后果是**一个 emoji 表达多个语义**：

- `🟡 权威（只覆盖档 1）` — 权威但范围窄
- `🟡 半过期` — 不权威
- `🟠 部分过期 · 只当背景`

同一个 🟡，两种完全不同的含义。AI 读到 🟡 无法判断该不该信。

**建议的封闭枚举**（6 个，互斥）：

| status | 含义 | 能否执行 | 默认位置 |
|---|---|---|---|
| `authoritative` 🟢 | 当前有效，按它做 | ✅ | 工作区 |
| `partial` 🟡 | **只在 `scope` 内有效**（必须给 scope + sections） | ✅（限 scope） | 工作区 |
| `superseded` ⚪ | 有明确取代者（必须给 `supersededBy`） | ❌ | 工作区（灰显） |
| `sealed` 🔴 | **原地封存**：内容有诱惑力但已被推翻，没有取代者 | ❌ | **原地不动** |
| `void` ⚫ | 明确作废（判据写错等），无追溯价值 | ❌ | 坟场 |
| `draft` 🔵 | 未定稿，不作为依据 | ❌ | 工作区 |

**关键区分：`superseded` vs `sealed`**。
- `superseded` 有替代品 → 读者可以直接跳过去。
- `sealed` **没有**替代品 → 读者必须知道"这里有个坑，别照做"。

09/10/11 是 `sealed`，不是 `superseded`。如果把它们扔进坟场，反而可能被"翻出来"当成有效文档；留在原地 + 🔴 + "不要执行"才是对的。

**这直接修正设想里"坟场"的设计**：坟场只处理 `void`，不处理 `sealed`。

#### 3.3 坟场：同目录独立文件夹 + 前缀拦截

设想第 13 行：

> 坟场：在工作区上方散落的窗口,这部分是因为时效性等原因被弃置的文档,一般情况下不会被ai读取.

**"一般情况下不会"= 软约束**。而示例已经证明软约束会失效：00 文档之所以要写"别按原始文件名顺序读"，就是因为模型会按字母序扫到 09/10/11。

**决策：坟场是项目根下的独立文件夹**（`<项目>/docs/_graveyard/`，布局见 §2.6），不搬到工作区之外。理由：

| 理由 | 说明 |
|---|---|
| 单点管理 | 用户不用在两个位置之间来回找 |
| git 一起管 | 归档跟着仓库走，历史可追溯，不用另建一套 |
| 路径稳定 | 跨会话、跨工具引用不会失效 |

**为什么嵌在 `docs/` 里面而不是项目根下**：坟场里放的是**文档**，与 `docs/` 同级放会让"受管文档根"和"坟场"变成两个并列概念；嵌进去之后，`docs/` 就是"所有文档"的根，`_graveyard/` 只是其中"不扫描、不可读"的一个子目录——**guard 和索引都只需要排除一个前缀**。

代价很小，因为**"全部在一个文件夹"这个前提让过滤变成一次前缀比较**。

**两个挂钩点，缺一不可**：

| 挂钩 | 拦什么 | 为什么必须 |
|---|---|---|
| **`guard`** | `write` / `edit` / `read` 的参数命中 `docs/_graveyard/` 前缀 | 直接读写 |
| **`tools/post-execute`** | 从 `glob` / `grep` / 目录列表的**返回值**里剔除该前缀 | **guard 拦不住枚举**——`glob docs/**/*.md` 的参数里没有坟场路径，但结果里有 |

**只做 guard 是漏的**，这一点在示例里有直接证据：模型扫整个目录、按字母序读到 09/10/11，就是这么发生的。`post-execute` 允许替换结果（`[实测]`），所以这条路可行。

**两个配套细节**：

1. **`doc_health()` 必须显式排除该文件夹**，否则会把它全报成"孤儿文档"（存在但不在索引里）。
2. **索引扫描（L0 必读清单）本身就要跳过它**——它不是"状态为 void 的文档"，而是"不参与索引的目录"。

**关于 `pwsh`**：`guard` 能拦 `pwsh` 这个**工具**，但拦不住"这条 shell 命令会不会写文件"——`pwsh` 的参数是任意字符串，判定副作用等于写一个 shell 解析器（教练模式因此明确决定 `pwsh`/`bash` 本阶段不加守卫）。同目录方案下，这一点用**命名约定 + 用户可见**来兜，而不是靠工具拦截。

**另外：坟场必须可回收，而且归档动作不该由 AI 触发**（详见 §6 的 Q12 说明）：

| 谁 | 能做什么 |
|---|---|
| AI | 标 `status: void` + 写理由。**永远不能移动文件** |
| UI | 列出"待归档"清单 |
| 用户 | 勾选 → 点"归档" |
| 插件 | 执行物理移动（走 `ctx.fs`，不是模型调工具），从 `docs/` 移到 `docs/_graveyard/` 并保留原路径元数据；提供"还原" |

这样误判天然可逆：AI 标错了，用户不勾就不会动。**"进坟场是移动不是删除""有回收站""AI 必须给理由"这三条要求，靠这个分工一次性满足**，不需要再额外加约束。

**顺带一个简化**：因为模型**没有任何工具能往坟场里写**，§上文 guard 里那条规则只需要**防读**，不需要防写。

#### 3.4 明确与既有 7 个机制的关系

这是最大的架构风险：设想可能重复造 5 个轮子。以下全部是我在本机核实过的既有机制 `[实测]`：

| 既有机制 | 已解决的问题 | 与设想的重叠 | 建议 |
|---|---|---|---|
| `dsh-agent-instructions`（AGENTS.md） | 工作区文档**自动进上下文**、按需刷新、字节预算、去重、KV 安全 | 与"文档驱动"几乎同构 | **不要重造**。要么用它承载 L0 索引（写 `AGENTS.md`），要么明确说明为什么它不够（它只支持固定文件名、无元数据、无置信度） |
| `dsh-tool-skill` + `dsh-skill` | **目录常驻 + 正文按需加载 + digest 变化才追加替换** | 与"索引 + 正文"架构完全同构 | **这是最像的既有机制**。文档驱动 ≈ "项目级 skill 目录"。可以借鉴它的 digest 方案，甚至复用 `ctx.skills.register()` |
| `dsh-tool-todo` | 结构化任务列表 + 投影 + UI | 与"勾选完成任务"重叠 | 复用它的投影，不要自建任务模型 |
| `dsh-goal` | 跨会话持久的长期目标 + 4 个 phase + 阻塞原因 | 与"总体规划路线图"重叠 | 路线图 = 一系列 goal？还是独立模型？**必须选一个** |
| `dsh-tool-present` + `dsh-client-ui-deliverables` | 交付物声明 + 卡片 + 侧栏预览 | 与"交付成品区"完全重叠 | **直接复用事件源**（`deliverables/presented`），不要自建交付物模型 |
| `dsh-session-projection` | 从日志派生状态、快照、检查点；摘要键里已有 `contextPressure` / `contextBreakdown` | 与"文档状态"重叠 | 文档状态如果可从日志派生，用投影；否则用 frontmatter。**`contextPressure` 只给 UI 用，不要注入模型上下文**（§6 Q6） |
| `dsh-command-compact`（`/compact`） | 按需压缩历史，报告"压缩了多少项、省了多少 token" | 与"会话交接"解决同一问题 | 明确分工：`/compact` 解决"同一会话太长"，交接解决"换会话"。**先试 `/compact` 再考虑交接**——交接的成本高一个数量级 |

**最尖锐的一条**：`dsh-agent-instructions` 的 README 里写着它的设计原则 `[实测]`：

> 工作区指令是**持久的对话内容**，按 agent 与会话分别归属。基线消息与刷新消息都是普通的带来源 `user/message` 事件，因此与其他历史一样**可回放、可压缩、可恢复**，模型可见状态总能从会话日志重建。

这段话几乎就是"文档驱动"应该有的设计原则。**如果设想的方案与它冲突（比如用 `systemPrompt.section()` 注入文档），那是设想错了，不是它错了。**

#### 3.5 并发与多会话保护

设想没有考虑：

- **fork / 分支会话**：两个会话基于同一份文档，各自改 → 互相覆盖
- **subagent**：子代理改了文档，主代理不知道
- **UI 编辑 vs AI 编辑**：设想里"点击展开可以查看完整内容"，如果可编辑，就与 AI 的写入冲突

**必须做的**：每份文档记录 `lastWriter: { sessionId, seq, at }`。写入前检查：如果 `lastWriter.sessionId !== 当前会话` 且 `lastWriter.seq > 我上次读的 seq` → 拒绝，要求重读。

这正是 `fs-observation-policy` 的语义，只是把"版本"换成"会话 + seq"。

**示例里的惨痛教训**（00 文档第 14–17 行）：

> 历史教训：之前一度是反过来做的——在桌面改、再把整个文件夹**生成**到工作区。那样每改一次都要审批一次，而且生成脚本会**覆盖**这里的手工修改。

**同一份文档绝不能有两个可写副本。** 这条要写进设计约束。

### P1 · 决定成败

#### 3.6 文档健康度自检

设想完全没有。但这是这个插件**最有价值、也最容易做**的功能——因为它把"文档体系"从"人肉维护的散文"变成"可校验的数据结构"。

| 1 | **索引里的文件是否存在** | 05 的阅读顺序列了 `冒烟测试脚本-第二轮.md`，**该文件不存在** |
| 2 | **有没有孤儿文档（存在但不在索引里）** | 目录 15 个文件，索引横幅说"共 11 份" |
| 3 | **同一份文档内部数字是否一致** | 01 的 line 5 说"六个坑"，line 41/197 说"七个" |
| 4 | **有没有循环 supersedes** | 需检查 |
| 5 | **frontmatter 是否完整/合法** | 示例文档**完全没有** frontmatter |
| 6 | **状态与 supersedes 是否自洽** | `superseded` 但没有 `supersededBy` |
| 7 | **`verifiedAgainst` 与当前环境不符的 `authoritative` 文档** | 03 冻结于 DSH 0.2.1，仍标权威 |
| 8 | **关键数字是否多处不一致** | 单测 63→149 分散在 6 份文档的 36 处 |
| 9 | **冷启动预算是否超限** | 主干"约 45 分钟"阅读量 |

**输出**：一个 `doc_health()` 工具 + UI 上的红点。每次交接前必须跑一次，有 error 级问题就拒绝交接。

#### 3.7 冷启动预算

示例里最触目惊心的一句（00 文档第 85 行）：

> **01 → 02 → 03 是主干**（约 45 分钟）

45 分钟是**人的**阅读时间。模型的成本更高——而且**每次新会话都要付一次**。

**必须做的**：
- 每份文档估算 `tokens`（字数 × 1.5，或实际 count）
- L0 索引里显示"必读总计 ≈ 28k tokens"
- 设一个**冷启动预算**（建议 30k），超了就报警，提示"文档体系需要合并/加摘要"
- 提供"TL;DR 模式"：每份文档顶部 ≤200 字摘要，先读摘要决定要不要读全文

#### 3.8 版本、快照与回滚

示例里的 `_backup-0.2.4-20261017\`、`_backup-0.3.4-20261018\` 等手工备份目录，**说明需求真实存在且当前靠人肉解决**。

**建议**：不自己造版本系统，而是**依赖 git**（如果项目根在 git 里），或提供"文档快照"（每次交接时打包一份 `<项目>/_artifacts/_snapshots/<timestamp>/`，放在 §2.6 的过程产物目录里，不进索引）。后者简单但会膨胀，前者需要用户接受 git。

**最低要求**：任何 AI 的文档编辑都能被撤销。至少记录"改动前内容"到日志或旁路文件。

#### 3.9 段落级状态

示例里最痛的一点（01 的表格）：

> **04** 🟡 半过期 → **只有 §4 建议 C / D 还活着**
> **05** 🟠 部分过期 → **仅 §9 的 A7 12 条清单、§10 决策、§12 术语、§13 协作约定** 仍不可替代

**置信度是文件级的，但失效是段落级的。** 这是示例文档体系里最大的信息损耗——读者必须读完 451 行才知道"只有 §4 有用"。

设想沿用了文件级置信度，等于继承了这个缺陷。

**方案**：frontmatter 的 `sections[]`（见 §2.2），或正文内嵌标记（`<!-- ddd:status superseded by spec#13 -->`）。前者更适合机器读，后者更适合人写。建议前者为主。

#### 3.10 决策台账作为一等公民

设想里有"总体规划路线图（也许是 spec）"和"工程记录文档"，**没有决策台账**。

但示例证明决策台账是最有价值的一类文档：

- `D1`–`D11`（设计决策）
- `R1`–`R16`（实测后的修订）
- `Q1`–`Q7`（用户拍板）
- 每条都带**理由**，且明确"不要重开"

**为什么重要**：没有它，每个新会话都会重新讨论已定的事。示例里 05 §十 专门写了一张表说"这 5 个问题已经有答案了，不要再问一遍"——**这张表的存在本身就说明问题有多严重**。

**建议**：`decision` role，只追加，每条有 `id` / `decision` / `reason` / `decidedAt` / `decidedBy` / `status(open|closed|superseded)`。L0 索引里只放"当前有效的决策 id 列表"，正文按需读。

### P2 · 体验

#### 3.11 右栏的现实约束（重要，会影响整个 UI 设计）

设想第 2 行："位置：位于dsh右侧窗口栏中"。

我在本机核实了右栏的实际能力 `[实测]`（`dsh-client-ui-sidebar-right`）：

| 事实 | 影响 |
|---|---|
| **每会话一个停靠面**，状态按 sessionId 键控 | **没有会话就没有面板**（README：「hero 画面右侧什么都不显示」） |
| 最多 **2 个分栏**，分隔条 20%~80% | 三区布局（工作区/交付/坟场）**塞不进 2 格** || 窗口 < 768px 打开右栏**自动全屏** | 窄屏下"三区并排"不可行 |
| 布局存 localStorage，按 sessionId 键控 | 换会话布局不共享 |
| 面板**没有标题行**，tab 条就是上边 | 顶部空间很紧 |

**"从左往右的树状图"在右栏里基本不可用**：默认宽度约 400px，横向树需要滚动，且每层节点宽度受限。

**建议的布局替代**（注意：**磁盘上的四目录 ≠ 右栏的四格**，UI 分区可以合并）：

| 设想 | 建议 | 磁盘对应（§2.6） |
|---|---|---|
| 工作区：从左往右的树 | **主栏（main slot）全屏页放图谱**，右栏只放"当前文档 + 相邻 3 份" | `docs/` |
| 三区并列 | 主栏里用 tab 切区；右栏只放"当前上下文" | — |
| 交付成品：90 度网格 | 复用 `dsh-client-ui-deliverables` 的卡片样式，或主栏网格 | `deliverables/` |
| 坟场：上方散落 | 主栏的"归档"tab，时间线列表（散落布局在窄栏里不可用且难检索） | `docs/_graveyard/` |

> **`_artifacts/` 在 UI 里可以不给独立入口**——它不是给人读的东西，用文件树能翻到就够了。**四个磁盘目录不需要四个 UI 分区**，这是两件事。

**关键先例** `[实测]`：`@linxin666/dsh-client-ui-skill-explorer` 就是**双注册**——`sidebar.panellist` 一个入口行 + `main` 一个整页。文档驱动插件应该照抄这个模式。

#### 3.12 直接复用文档预览

右栏已有 `dsh-client-ui-sidebar-documentpreview` `[实测]`：
- 支持 Markdown / 代码 / 图片 / PDF / Office / HTML
- **渲染 frontmatter 为键值列表**
- 有目录树、行号、自动刷新

**"点击节点看全文"几乎零成本**：调用 `ctx.sidebarRight.openResource('dsh-resource://file/<path>')` 即可在右栏打开 `[实测]`（`dsh-client-ui-deliverables` 与 `dsh-client-ui-sidebar-files` 都是这么用的；文档预览在 `builtin` 档认领 `.md` 后缀）。

**这意味着**：设想里"点击展开可以查看完整内容"不需要自己实现编辑器/渲染器。**代价降到接近零**，但前提是路径能被 `dsh-resource://file/` 认领（工作区内的文件可以，工作区外需要确认）。

#### 3.13 当前文档聚焦视图

设想的三区布局里**没有**这个。但文档驱动开发时，用户最常做的是：

> 看当前这一步依据的是哪份文档、写到哪了、下一步是什么。

建议加一个"施工看板"视图（右栏第一格）：
```
当前切片: 0.4.2 成本控制
当前阶段: 验收
当前任务: A15-b 状态块预算
依据文档: spec-tier2 §14.5 (指纹 a3f2c1)
          handover-2.6 §10.5
下一步: 跑 A15-b，留会话 id + seq
交付物: _dist/local-coach-mode-0.4.2.tgz
```

这一块的信息密度远高于树状图，且**每轮都要用**。

#### 3.14 搜索与跳转

文档一多（示例 15 份 1 万行），找不到就是致命问题。DSH 有 `dsh-session-query` 的全文搜索 `[实测]`，但那是搜会话历史，不是搜文档。文档搜索需要自己做，或用 `grep` 工具。

**最低要求**：按 id / role / status / 关键词过滤；点搜索结果直接打开预览。

### P3 · 成本与度量

#### 3.15 成本模型（设想的"优势"需要算账）

设想声称省 token。但文档驱动有**五项成本**，设想一项都没提：

| 成本项 | 说明 | 估算 |
|---|---|---|
| 冷启动读取 | 新会话读必读文档 | 示例 ≈ 30k–45k tokens/次 |
| 索引常驻 | L0 每轮都进请求 | 800 tokens × 轮数 |
| 文档维护 | AI 写日志、更新状态、写交接 | 示例的 12/13 各 25k 字符 |
| UI 渲染 | 不进上下文，但占开发成本 | — |
| 返工 | 读到过期文档导致的错误 | 难估，但示例里 09/10/11 就是 |

**省下的是什么**：不重复注入大文档（如果不用文档，就得每轮带规格）。
**关键问题**：一份文档在一个长会话里被读 5 次，还不如一开始就注入（缓存命中的话更便宜）。

**建议给出明确的适用边界**：

| 场景 | 文档驱动更省？ |
|---|---|
| 一次性小任务（<10 轮） | ❌ 更贵 |
| 长项目、多次交接（示例就是） | ✅ 明显更省 |
| 多会话并行 | ✅ 省（共享文档而非共享上下文） |
| 单会话长跑 | ⚠️ 取决于读几次；读 >2 次就该考虑注入 |

#### 3.16 度量指标

没有度量就没有改进。建议内建：

- **冷启动 tokens**：新会话到"能开始施工"为止消耗的输入 token
- **交接质量分**：冷启动演练通过率
- **文档漂移率**：`verifiedAgainst` 与当前环境不符的 `authoritative` 文档比例
- **索引准确率**：索引与实际文件的一致率
- **读覆盖率**：进入施工前，必读文档的实际读取比例

前四个可以自动算，第五个是核心质量指标。

## 4. 示例文档的实践评估

> 说明：以下评价针对"文档驱动"这个**做法**，不针对具体内容质量。示例文档的内容质量很高——恰恰因为高，才值得逐条拆解。

### 4.1 值得吸收的 12 条

| # | 做法 | 出处 | 为什么好 | 吸收方式 |
|---|---|---|---|---|
| 1 | **按读者视角重新编号**，而不是按时间顺序 | 00 §"为什么不按原来的文件名读" | 把"阅读顺序"从隐性知识变成显性数据。理由写得极清楚："按字母序读，你会在读到权威结论之前先读到已被推翻的要求" | 改为 frontmatter `order`，避免重编号 |

| 9 | **"验收以日志为准，附会话 id + seq"** | 01 §九 6、SPEC §12.3 | 可证伪的验收。整个体系里唯一真正"物理"的东西 | `evidence` role + 必填 `evidenceRef` |
| 10 | **"已实测的机制事实（不要重新论证）"** | 01 §三 | 把探索成本固化下来。这是文档驱动**最高价值的形态**：不是描述要做什么，而是记录已经知道什么 | 独立 role：`fact`（或 decision 的子类） |

### 4.3 一条元观察（很重要）

**示例文档是为"人接手"优化的，不是为"AI 接手"优化的。**

证据：

| 特征 | 为人的设计 | 对 AI 的影响 |
|---|---|---|
| 横幅写"给谁 / 拿什么 / 注意什么" | 帮人建立心理模型 | AI 不需要心理模型，需要结构化字段 |
| "约 45 分钟" | 人的时间预算 | AI 没有时间概念，需要 token 预算 |
| 大量口语化解释（"这段认知是错的"、"我留给你的是…"） | 传递判断和语气 | 占 token 但不增加可执行性 |
| "上面 0–9 节是快照，不改写" | 人的信任建立 | AI 需要的是 `status: snapshot` 字段 |
| 靠编号顺序表达优先级 | 人扫目录就知道 | AI 需要显式 `order` 数值 |

**结论**：直接照搬示例的**形式**会失败。要吸收的是**原则**（阅读顺序显性化、负向知识显式化、决策不重开、验收可证伪），而不是**载体**（散文 + emoji + 编号）。

**推论**：这个插件真正的价值不是"把示例文档的做法自动化"，而是**把示例里靠人肉维持的纪律，变成机器可校验的结构**。

### 4.4 一条补充观察：切片命名

示例用"档 0 / 1 / 2 / 2.5 / 2.6"命名交付切片。**用会话序号命名切片**：

- ✅ 好的一面：承认了"AI 会话是有限资源"这个现实
- ❌ 坏的一面：把**组织方式绑死在了工具的限制上**。上下文变长后这套命名就失去意义
- ❌ 且"2.5 / 2.6"说明**切片粒度在漂移**——2.5 和 2.6 实际是同一批人做同一件事

**建议**：切片按**可验收的功能边界**命名（如 `0.4.0 会话连续性` / `0.4.1 脚手架递减`），会话只是执行单位。示例的 0.4.x 线其实已经是这么做的——**0.4 线比"档 2.5/2.6"健康得多**，这个对比本身值得注意。

## 5. 建议的切片（M0 / M1 / M2）

> 原则：每个切片都要**可独立验收**，且不依赖未完成的下一个切片。这是从教练模式"每次只交付一个可验收的版本"学来的。

### M0 · 索引与门禁（最小可用）

**只做六件事**：

1. **目录布局**（§2.6）：建 `<项目>/{docs,deliverables,_artifacts}` + `docs/_graveyard`，并落地 `projectRoot` 探测（R2）
2. **frontmatter schema + 校验器**（§附录B）：读文档时校验，缺字段/非法枚举 → 报错
3. **L0 索引块**：**慢变量写 `<项目>/AGENTS.md`**（必读清单、禁止清单、术语）+ **快变量走 `systemPrompt.context()`**（当前切片、进度、已读集合、写入状态）——**R3 的拆分表是硬规格**
4. **读取记账**（**零新工具**）：监听 `tools/result`，`read` 命中 `docs/` 即记 `{ id, fingerprint, at }`，折叠成"已读集合"
5. **门禁**（R1）：**按路径拦**——`guard` 只看目标路径，`docs/` 下未读文档的写入一律拒绝；其它目录放行
6. **坟场读取拦截**：`guard`（直接读写）+ `post-execute`（枚举结果过滤），前缀 `docs/_graveyard/`

**验收（编号 `M0-1` 起，R5）**：

| # | 用例 | 判据 |
|---|---|---|
| **M0-1** | 新会话第一轮 | L0 索引里出现正确的必读清单（id + 状态 + 指纹），无快变量污染 `AGENTS.md` |
| **M0-2** | 未读必读文档就改 `docs/` | 被拒绝，理由列出缺哪几份 |
| **M0-3** | 未读必读文档就改 `src/` | **放行**（按路径拦的反向验证，R1） |
| **M0-4** | `glob docs/**/*.md` | 结果里**没有** `_graveyard/` 下的文件（post-execute 生效） |
| **M0-5** | 连续 10 轮对话 | 会话历史里**只有一条**索引消息，不随轮次累积（R3 的核心验收） |
| **M0-6** | `read` 一份 `docs/` 文档 | `tool/result` 里记到 `{ id, fingerprint }`，已读集合 +1 |

**不做**：任何 UI、坟场归档流程（用户勾选/移动/还原）、交接、健康度、交付物视图、任何新增的读写工具。

> 坟场的**读取拦截**在 M0 就要生效（纯 host 逻辑）；**归档动作**属于 M2 的 UI。M0 期可以手工建 `docs/_graveyard/` 并放文件。

**为什么先做这个**：它验证了最核心的假设——"结构化索引 + 强制读取"能不能让 AI 真的按文档施工。如果这条不成立，UI 做得再漂亮也没用。而且这个切片**一个读写工具都不加**，工具目录与标准模式完全一致，零歧义。

> **M0-5 值得单独说**：它是 R3 选"混用"之后唯一能证伪的判据。如果 `AGENTS.md` 里混进了快变量，会话历史会越来越长——**这条用例就是用来抓这个的**。

### M1 · 交接与验收

1. `handover` 模板 + 七段校验（附录 B2）
2. 交接触发 = **用户点了 UI 上的"交接"**（不由阈值自动触发，也不由 AI 发起；占用提醒在 M2，见 §6 Q6）
3. 交接验收判据（§2.3(c) 的 6 条）
4. `doc_health()` 自检
5. 冷启动预算计算

**验收**：走完一次真实交接，新会话能只靠索引 + handover 复现"下一步"，且不需要追问。

**一个容易漏掉的验收项**：M1 必须证明"交接**失败**时会被拒绝"。只测成功路径等于没测门禁——这条教训直接来自示例的 A3/A4/A14-d（验收判据长期"部分闭合"，最后只能靠结构证明兜底）。

### M2 · UI

1. 主栏全屏页：图谱（纵向缩进树，不是横向树）
2. 右栏第一格：施工看板（当前切片/阶段/任务/依据/下一步/交付物）
3. 交付成品视图：从 `deliverables/` 扫 + `deliverables/presented` 声明；**未被 `present` 的标"未声明"**（§2.6）
4. 坟场：待归档清单（用户勾选）+ 归档/还原
5. 复用 documentpreview 做全文预览
6. **上下文占用提醒**（40% / 55% 两档，各一次，之后静默）——**纯客户端，host 零代码**（§6 Q6）

**验收**：完成一次完整的"看板 → 点开文档 → 编辑 → 看到指纹变化"闭环。

**注意 M2 不含 `_artifacts/` 的独立入口**——它不是给人读的，文件树能翻到就够（§3.11）。

**工程量提醒** `[实测]`：M2 之前，插件是**纯 host**（和教练模式同形态，只需 `index.js` + `cordis.patch.yml`，零构建）。
M2 一开始就变成 **host + client 双半侧**：需要 `dsh.client` 声明、`lib/client.js` 构建产物、`PLATFORM_MODULES` 白名单对齐、React 运行时。
**这不是"加个 UI"，是换一个技术栈。** 建议 M2 单独排期，且先用 `@linxin666/dsh-client-ui-skill-explorer` 的源码当模板（它是"双注册 + 无构建依赖"的完整范例，我已读过）。

### 不建议现在做的

- 横向树状图（右栏放不下，主栏也不划算——纵向缩进列表信息密度更高）
- 自动置信度推断（需要先有 supersedes 图和证据，否则是猜）
- 跨项目共享（先证明单项目有用）

**R3 的拆分表**（哪些内容走哪条通道）：

### 6.2 教练模式是怎么做的（R3 的参考实现，**已读源码**）

> 你问的这个：教练模式的现成做法可以直接当 R3 的验证参考。我读了 `coach-mode-pack-v0.4.4` 的源码，结论比预想的更明确。

**结论：教练模式**完全不用** `AGENTS.md`，也**完全不用** `{{...}}` 变量，只用两条通道——静态 `persona.prefix` + 动态 `systemPrompt.context()`。**

| 通道 | 用来放什么 | 实际规模 | 变化频率 |
|---|---|---|---|
| `persona.prefix`（`cordis.patch.yml`） | 全部**不变**的内容：铁律、意图分流、自我说明、输出格式、跳过规则、检索规则 | **约 8,400 字符 / 188 行** | 从不 |
| `systemPrompt.context()`（`inject.js`） | **每一轮都变**的状态块：当前阶段、当前步骤、请执行、合格标准、核查证据、失败次数、进度摘要 | **预算 4,000 字符**（`maxStateBlockChars`，超了按顺序裁剪） | 每轮 |

**`inject.js` 里的原始理由**（源码注释，可以直接引用）：

> 1. 运行时上下文按**每次模型请求重新装配**，语义是"本快照取代上一份快照"，因此天然满足"每轮都有、不随轮次累积"；
> 2. 它**不进入历史消息，也不改系统提示词前缀**，对 KV 缓存最友好；
> 3. `text` 回调拿到的 `AssembleContext` 里有 `agent`，所以能按会话渲染。

**`{{...}}` 变量的处置**（`cordis.patch.yml` 第 28–32 行，`R16` 的现场遗迹）：

> ⚠️ 不要在这个 config 里写 `{{...}}`，除非是宿主明确注册过的变量。
> 宿主提供的提示词变量会随 DSH 版本变化：0.2.0-rc.2 注册过 `cwd`，0.2.1-rc.1 只剩 `provider` / `model`，于是每一轮都 `unknown prompt variable "{{cwd}}"` 直接失败。
> **现在这个 config 里不再使用任何提示词变量**……工作目录不由 persona 提供，改由插件的状态块【位置关系】那行给出。

#### 这对 R3 意味着什么：**我的"混用"建议要改**

| | 教练模式的做法 | 我原来建议的 R3 |
|---|---|---|
| 慢变量（必读清单、禁忌、术语） | `persona.prefix`（**不是** AGENTS.md） | `AGENTS.md` |
| 快变量（当前切片、进度） | `context()` | `context()` |
| 结果 | **两级都稳定**，快变量单独一块 | 慢变量走 AGENTS.md 会被**持久追加** |

**关键区别**：`persona.prefix` 和 `AGENTS.md` **都是静态的**，但行为不同——

| | `persona.prefix` | `AGENTS.md` |
|---|---|---|
| 位置 | **系统提示词内**（真正的前缀） | 一条持久 **user 消息**（在历史里） |
| 变化时 | 改系统提示词前缀 → **缓存全失效** | **追加一条新消息**，旧的留着 |
| 谁维护 | 插件作者（随版本发） | 项目/用户在运行时改 |

教练模式选 `persona.prefix` 是因为**它的慢变量是插件作者写的、随版本发布**，不需要运行时改。
而**文档驱动的慢变量是项目自己的文档清单，必须运行时可变**——这是本质差别，所以不能直接照抄。

#### 修正后的 R3

```
慢变量（必读/禁止/术语）
  ├─ 方案 A：写进 <项目>/AGENTS.md      ← 运行时可变，但变化会追加历史消息
  └─ 方案 B：插件用 persona.prefix 生成  ← 位置更好，但作者改不了
```

**建议保持 R3 的混用不变，但补两条约束**（这是教练模式给我的新认识）：

1. **慢变量必须真的慢**。教练模式的 `persona.prefix` 84 次发版才改一次。如果 `AGENTS.md` 里的必读清单每加一份文档就变一次，那它还是会累积——**所以"必读清单变更频率"要在 M0 用 M0-5 盯住**。
2. **快变量块给个字符预算**。教练模式用了 `maxStateBlockChars: 4000` 并配了裁剪顺序（`BUDGET_STUBS`），且有单测断言 `< 4000`。文档驱动的 `context()` 块也应该有同样的预算，**预算值可以小得多**（索引块本质是清单，不需要 4000）。

**一条可以直接抄的工程细节**：教练模式把"当前步骤/请执行/合格标准/核查结论/错误提示"列为**永不裁剪**，其余按顺序换短提示。文档驱动的对应物是"**必读清单/禁止清单永不裁**，已读集合和历史证据先裁"。

> **顺带解答我上一轮留的待验证项**：`inject.js` 的注释明确说 context **"不进入历史消息，也不改系统提示词前缀"**。所以它在请求尾部区域——**内容变化时废掉的缓存很少**。这条现在有源码依据，不需要再实测了。
>
> （仍值得实测的是**确切位置**——`order: 130` 排在 sandbox(110)/approval(115)/delegation(120) 之后，但这只是注册顺序，不等于装配后的位置。不过既然它不改系统提示词前缀，影响已经很小。）

> **Q2 / R3 的机制依据**：`dsh-agent-instructions` 会**自动发现项目根到会话 cwd 的每一级 `AGENTS.md`** `[实测]`，所以把慢变量索引写进 `<项目>/AGENTS.md` 是**零代码**的。
>
> 但它的注入语义是"**持久 user 消息 + digest 变化才追加替换**"，不是每轮重算的快照——**索引一变就多一条历史消息，旧的在压缩前一直留着**。这正是 R3 把快变量分出去的原因，也是 §2.1 那条硬约束（"索引块里不得放每轮变化的内容"）的由来。
>
> 两条通道的分工已在 **§6.1 的 R3 拆分表**里定死，此处不再重复。

> **Q5 的说明：为什么砍掉 TTL 自动降级**
>
> **谁标**：AI 在交接时标（设想第 17 行），用户否决。但 AI 的自我评价不可验证——它说 0.9，你没有依据反驳。所以 `confidence` **不能是唯一判据**，必须配可核对的东西。
>
> **TTL 为什么错**：`confidence: 0..1` 把三个独立维度挤成一个数字：
>
> | 维度 | 含义 | 由什么驱动 |
> |---|---|---|
> | **真值** | 它说的还对吗 | **事件**（代码改了、DSH 升级），不是时间 |
> | **适用性** | 它管不管我现在这件事 | **切片 / scope 变化**，不是时间 |
> | **权威性** | 我能不能拿它当依据 | 是**决定**，推不出来 |
>
> 而不同 role 的衰减驱动根本不同：
>
> | role | 衰减驱动 | 时间可靠吗 |
> |---|---|---|
> | `spec` | 被 supersede，或外部条件变了 | ❌ 一年没改也可能全对 |
> | `evidence` / `log` | **不衰减**。它记录"当时确实如此" | ❌ 旧不等于错 |
> | `handover` | 下一份 handover 出现 | ❌ 与时间无关 |
> | `instruction` | 执行完成 | ❌ 与时间无关 |
> | `status` | 提交、代码变更 | ⚠️ 时间是粗糙代理 |
>
> **七个 role 里只有一个勉强跟时间相关。** TTL 最多适用于 `status`，做成通用机制是错的——而且它和 §3.1 表格里 `evidence` 的"失效速度：永不"直接矛盾。
>
> **改法**：拆成两个字段——
> - **`status`**：权威性，由人/AI 显式决定，**永不自动改**
> - **`verifiedAgainst`**：机器可查的锚点
>
> ```yaml
> verifiedAgainst:
>   dsh: 0.2.1-rc.1
>   bundle: 0.4.2
>   commit: a3f2c1
> ```
>
> 插件读环境实际值比对，不一致就提示"**这份文档是对 DSH 0.2.1 验证的，当前 0.3.0，其中关于提示词变量的结论可能已失效**"。
>
> **这比 TTL 强得多，你自己的项目就是现成例子**：R16 那条 `{{cwd}}` 被删除——时间没过去多久，但事实已经变了。时间在这里完全没用，**锚点一比对就能发现**。
>
> **每个 role 配不同的锚点**（这正是"不该用同一套逻辑"的落法）：
>
> | role | 锚点 | 漂移时 |
> |---|---|---|
> | `spec` | `dsh` + `bundle` + `commit` | 标"需复核"，不自动降级 |
> | `evidence` / `log` | **无** | 永不检测 |
> | `handover` | 无（靠"是否有更新的一份"判断） | — |
> | `status` | `commit` | 提示"进度可能已过期" |

> **Q6 的说明：交接触发是纯 UI 的事，不进模型上下文**
>
> **判定由插件做，不由 AI 做。** `contextPressure` 是会话投影 `[实测]`（摘要键里就有），插件直接读，模型完全不参与。
>
> **提醒走 UI，一个字都不进上下文。** 这是本节最关键的约束。如果往状态块里写一句"上下文快满了"，模型会回应"好的我记下了"然后接着干活——**这是拿环境观测在干扰 AI 的工作**。用户要看的是自己的会话还剩多少余量，不是让 AI 操心这个。
>
> **两档，各提醒一次，之后彻底静默**：
>
> | 水位 | 提醒 | 之后 |
> |---|---|---|
> | ≥ 40% | 侧栏角标 / toast："上下文已用 42%，可以考虑交接" | 到 55% 前不再提醒 |
> | ≥ 55% | 同上，措辞加重 | **再提醒一次，然后永远静默** |
>
> **用户有权在 80% 占用的会话里继续跑。** 只记"本会话已提醒过 N 次"（客户端本地状态），到 2 就再也不响。插件不该对用户的使用方式有意见。
>
> **技术落点**：`contextPressure` 是**客户端可见投影**，client 半侧自己读、自己算阈值，**host 侧零代码**。也不需要新增事件类型（插件不得 append 自定义事件类型，否则会话无法重开）。
>
> **后果**：Q6 完全属于 M2。M0/M1（无 UI）阶段没有这个功能——可接受，它本来就是舒适性功能。
>
> **一条可提炼的原则**（比 Q6 本身更通用）：
>
> > **门禁改"能不能做"，提醒只给"用户知道"。**
> > 前者是产品功能（必读未读 → 拒绝施工），后者是环境观测（占用高 → 告诉用户）。
> > **后者永远不进模型上下文。**
> >
> > 这两件事容易混。混了就是"插件用环境信息偷偷影响模型行为"。

> **Q12 的说明：AI 只有提议权，移动由用户在 UI 上确认**
>
> **不该让用户去跟 AI 说"把这个归档了"。** 这是用户的文件管理动作，不是给 AI 的指令——和 Q6 一样，属于"人的决定，不是模型的判断"。
>
> **分工**：
>
> | 谁 | 能做什么 | 不能做什么 |
> |---|---|---|
> | AI | 标 `status: void` + 写理由 | **永远不能移动文件** |
> | UI | 列出"待归档"清单 | — |
> | 用户 | 勾选 → 点"归档" | — |
> | 插件 | 执行物理移动（走 `ctx.fs`，不是模型调工具） | 不自行决定归档谁 |
>
> **流程**：
>
> 1. AI 在某份文档上标 `status: void` + `voidReason`
> 2. 坟场视图里出现"待归档（3）"角标，展开是清单
> 3. 用户勾选后点"归档" → 插件把文件移到 `_graveyard/`，保留原路径元数据
> 4. 有"还原"：移回原路径
>
> **这样误判天然可逆**：AI 标错了，用户不勾选就不会动；用户勾错了，还原即可。**AI 永远拿不到移动文件的权限**，也就没有"AI 误判导致不可逆"这种事故。
>
> **技术上顺带一个好处**：guard 里那条"坟场只读"的规则因此**只需要防读，不需要防写**——因为压根没有工具能让模型往里写。

| A10 | **结构化事实落盘** | `output.presentationMeta(args, value)` → `tool/result.data.meta` | 自己注册的工具才需要；观测别人的工具用 `tools/result` 事件 |
| A11 | **会话投影** | `ctx.sessionProjections.register({ key, stateSchema, stateVersion, init, apply, wire })`；摘要键含 `contextPressure`、`contextBreakdown`，**client 可见** | **仅供 UI 提醒**，不注入模型上下文（§6 Q6） |
| A12 | **skill 目录机制** | 目录常驻 + 正文按需 + digest 变化追加替换；`ctx.skills.register()` 可注册内存 skill | 与文档驱动最同构的既有机制（§3.4） |
| A13 | **交付物** | `present` 工具 → `deliverables/presented` 事件 → `dsh-client-ui-deliverables` 卡片；**声明记录绝对路径，文件移动后失效** | 交付成品区直接复用（§3.4、§2.6）；成品必须**直接产出到 `deliverables/`**，不要先产出再移动 |
| A14 | **goal 服务** | 4 个 phase（active/paused/blocked/complete）+ revision 比较设置 + 严格回放 | 路线图可考虑复用（§3.4） |
| A15 | **client 插件成本** | 需要 `dsh.client` 声明 + `lib/client.js` 构建产物 + `PLATFORM_MODULES` 白名单；缺 bundle 会激活失败 | **工程量数量级提示**：设想是双半侧插件，远复杂于纯 host 的教练模式 |
| A16 | **会话日志查询** | `ctx.sessionQuery.readSession/filterEvents/searchEvents/traceSession` | 健康度自检、读覆盖率统计 |
| A17 | **条件注册** | `ctx.tools.register(definition, { when })`：`when` 每步计算一次，返回 false 则**从 schema、PTC 绑定与执行集合中排除**（不只是拒绝执行） | **让工具"按状态出现/消失"**——模型只在需要时看得见它，天然没有歧义（§2.5 第三层） |
| A18 | **工具级开关** | `tool-fs` 的 `read`/`readImage`/`write`/`edit`/`applyPatch` 各有布尔开关，设 `false` **同时省略工具及其指导文本** | 隐藏是干净的（不留孤儿提示词）；但见 §2.5 为何不该隐藏 `write`/`edit` |
| A19 | **执行流水线四段** | `tools/pre-execute`（可扩展的允许/拒绝/询问）→ 已注册单调 guard → `tools/execute` → `tools/post-execute`（可替换结果/附加上下文）→ `tools/result`（**仅观测**，冻结的最终结果） | **"记账"走 `tools/result`，"拦截"走 `guard`，"改写"走 `post-execute`**——不需要新工具（§2.5） |
| A20 | **`pre-execute` 不能改参数** | 有意不允许改写 `exec.arguments`：否则日志与呈现的参数会和实际运行内容失同步（改写仍在 proposed 阶段） | 想"把 write 重定向到 doc_update"是不可行的；只能**拒绝**，不能**改道** |
| A21 | **`write`/`edit` 已自带记账** | 成功后发出 `fs/observed`（含版本）；派生可回放的 diff 卡片元数据；有 `fs-sandbox` 时公开 `sandbox_permissions`/`justification` 走审批 | 你要的"记账"宿主已经做了一大半，不要重写 |
| A22 | **轮次级改动汇总** | `dsh-workspace-changes`：git 快照 + 文件工具编辑前后整文件捕获，每轮宣告一条 `workspace/changes`，提供 `summary(sessionId, seq)` 与 `diff(...)` | **"本次改了哪些文件"已现成**，文档写入统计可以直接读它 |
| A23 | **作用域隔离** | `createScope(ctx, key)` / `agent.ctx` 注册只对该 agent 可见；`ctx.tools.restrict(filter)` 按 agent 收窄可见集合 | 文档工具只在文档驱动模式下出现（若真需要区分） |

**一条必须知道的工程量事实** `[实测]`：教练模式是**纯 host 插件**（只有 `index.js`，零构建）；文档驱动插件如果要 UI，必须是 **host + client 双半侧**，需要 TypeScript/React 构建链、`lib/client.js` 产物、`dsh.client.external` 声明。**这是数量级的复杂度差异**，建议 M0/M1 完全不做 UI，先证明机制。

**另一条与工具面直接相关的事实** `[实测]`：`tools/pre-execute` **不允许改写参数**，只能允许/拒绝/询问。这意味着"让 `write` 自动转成 `doc_update`"这条路是堵死的——**要么拒绝，要么放行**。这也反过来支持 §2.5 的结论：拦截只能做"守门"，做不了"重定向"；想让模型做别的事，只能靠状态块说清楚。

## 附录 B：可直接用的三份模板

### B1 · 文档 frontmatter schema（v1）

```yaml
---
id: string                    # 必填，全局唯一，kebab-case，永不变
title: string                 # 必填
role: index|spec|decision|evidence|log|handover|instruction|fact
                              # 必填，决定更新规则与是否进 L0
order: number                 # 必填，阅读顺序，建议 10/20/30 留插值空间
status: authoritative|partial|superseded|sealed|void|draft
                              # 必填，封闭枚举
scope: [string]               # partial 必填，适用切片/阶段
supersedes: [string]          # 我取代了谁（id 列表）
supersededBy: [string]        # 谁取代了我（status=superseded 时必填）
amends: [string]              # 我局部修订了谁（不改其 status）
sections:                     # 可选，段落级状态
  - anchor: "#7"
    status: authoritative
  - anchor: "#2"
    status: superseded
    supersededBy: spec-tier1#13
summary: string               # 必填，≤80 字，索引渲染用
tokens: number                # 可选，冷启动预算用
basis: 实测|推断|未验证        # 必填：这条结论是怎么来的（可信度的真正来源）
verifiedAgainst:              # 可选但强烈建议：机器可查的锚点，按 role 决定填哪些
  dsh: string                 # 如 0.2.1-rc.1
  bundle: string              # 如 0.4.2
  commit: string              # 如 a3f2c1
verifiedAt: date              # 上次复核日期（人/AI 显式填写，不自动改 status）
lastWriter:                   # 由插件自动维护（tools/result 记账），不要手写
  sessionId: string
  seq: number
  at: datetime
fingerprint: string           # 自动维护：内容 hash 前 8 位，用于判断"读过的是不是这一版"
---
```

> **没有 `ttlDays`，也没有 `confidence: 0..1`。** 权威性只由 `status` 表达（显式决定，永不自动降级）；"会不会过时"由 `verifiedAgainst` 锚点比对得出。理由见 §6 的 Q5 说明。

**哪些字段是人写的、哪些是机器写的**（这个区分很重要，决定了工具面）：

| 字段 | 谁写 | 怎么写入 |
|---|---|---|
| `id` / `title` / `role` / `order` / `summary` / `scope` / `supersedes` / `supersededBy` | 人 / 模型 | `edit`（手改 frontmatter）或 `doc_new`（新建时生成） |
| `status` | 人 / 模型 | `edit`，但 `sealed` ↔ 解封走 `doc_mark`（需要理由） |
| `sections[].status` | 人 / 模型 | `doc_mark`（结构化，`edit` 做字面替换太脆） |
| `basis` / `verifiedAgainst` / `verifiedAt` | 人 / 模型 | `edit`（交接时复核并更新） |
| `lastWriter` / `fingerprint` | **插件** | **不要模型填**，由 `tools/result` 监听自动维护 |

**校验规则**（M0 实现）：
1. 必填字段缺失 → error
2. `role`/`status` 不在枚举内 → error
3. `status: superseded` 但 `supersededBy` 为空 → error
4. `status: partial` 但 `scope` 为空 → error
5. `supersedes` 指向不存在的 id → error
6. `sections[].anchor` 在正文中找不到对应标题 → warn
7. `supersededBy` 未反填 → warn（可自动修）
8. `fingerprint` 与磁盘内容不符 → **由插件自动重算并更新**（不是错误，是记账）
9. `verifiedAgainst` 与当前环境不符 → **warn，不自动改 `status`**（提示"需复核"，把决定权留给人/AI）

### B2 · 交接文档模板（handover role）

```markdown
---
id: handover-<切片>-<序号>
role: handover
status: authoritative
order: 0                      # 交接永远排第一
summary: <一句话：下一刀是什么>
---

#### 1. 我的意图（为什么这样做）
> 上一任为什么按这个顺序做？哪些是刻意的取舍？

#### 2. 现在到哪了（可核实的事实）
| 项 | 值 | 怎么核实的 |
> 版本号、测试数、已验收的用例、证据位置。**每条都要能被下一个会话独立复核**。

#### 3. 下一刀（可执行的第一个动作）
1. <具体到工具/文件/命令>
2. ...

#### 4. 坑（不要重犯）
| # | 现象 | 根因 | 怎么避免 |

#### 5. 验收（怎么算做完）
| 用例 | 判据 | 证据形式（会话 id + seq / 哈希 / 测试输出） |

#### 6. 我刻意没做的事（负向范围）
> 防止下一个会话"顺手补上"。

#### 7. 仍未决（需要用户拍板）
| # | 问题 | 选项 | 我的建议 |
```

**校验规则**：§1–§6 必填非空（§7「仍未决」可为空，但若为空需显式写"无"，避免"忘了写"和"确实没有"无法区分）；§3 至少 1 条含具体路径或工具名；§5 每条必须有证据形式，否则不算验收判据。

> **为什么 §1「意图」排在 §2「现状」前面**：这是示例里最值得抄的一处细节。现状可以从代码和日志重建，**意图不能**——"为什么按这个顺序做""哪些是刻意的取舍"一旦丢失，下一个会话会按自己的偏好重做一遍。

### B3 · 禁忌清单模板（fact / decision role）

```markdown
| # | 规则 | 为什么 | 违反后的现象 | 状态 |
|---|---|---|---|---|
| 1 | 任何 .js 都不许 import '@deepseek-ai/*' | 宿主包在 app.asar，profile 的 bundle 解析不到 | 整行插件加载失败，preset 显示「加载失败」 | sealed |
| 2 | 人设固定格式字段之间必须空行 | DSH 渲染器只认硬换行 | 字段挤成一行 | authoritative |
```

**关键**：前三列（规则 / 为什么 / 违反后的现象）缺一不可。只写规则会被忽略；写清"违反后的现象"才会被当成真约束。`状态` 列让它同时充当坟场判据与门禁数据源。

> **示例里的原话值得抄下来**（01 §四 坑 1）："想加工具时，**不要** `import { defineTool } from '@deepseek-ai/dsh-tools'`——用 `tools/define-tool.js`。"
> 它不是只说"禁止"，而是**同时给出替代路径**。缺了替代路径的禁令，模型会卡在原地。
