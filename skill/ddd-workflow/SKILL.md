# DDD 全工序操作手册

> **这份手册的目的只有一个**：让你知道每个动作**具体等于什么操作**，不要为了搞清"该怎么干"去读插件源码。
>
> 实测教训：一次全流程演练里，13 个回合中有 3 个回合（共 25 次工具调用）在翻
> `app.asar` / `profiles\desktop\node_modules`，**两个回合被用户直接中止**。
> 原因不是模型不会写文档，而是没人告诉它"归档""交付""改阅读顺序"各对应哪个操作。

## 0. 先判断：这是 DDD 工作区吗

- 看上下文里有没有 `【门禁】` / `【未读】` 这样的注入块。**有 = 已激活**。
- 没有 → 这个目录还不是 DDD 工作区。**请用户点面板上的「初始化为 DDD 工作区」按钮**，
  不要自己写 `AGENTS.md` 或 `docs/` 去凑标记（要不要把这个目录变成 DDD 工作区由用户决定）。

## 1. 四个工具（只有这 4 个，别找别的）

| 工具 | 干什么 | 关键约束 |
|---|---|---|
| `doc_new` | 新建受管文档，自动生成 frontmatter | 建完会自动重扫索引，并**按 frontmatter 重渲染 `read-order` 的必读清单**（M3） |
| `doc_mark` | **只改** frontmatter 状态 | 不改 `order`/`role`/`title`/`summary`；**`basis` 可以改**（见 §3.3）；标完也会重渲染必读清单 |
| `doc_handover_check` | 校验交接七段（H1–H7） | 不合格会列具体缺什么 |
| `doc_health` | 5 项健康度检查 | 全是 warn，不阻塞施工 |

**改正文用 `edit` / `write`，不要用 `doc_mark`**（它只碰 frontmatter）。
**改 `order` 也用 `edit`**（`doc_mark` 会直接报错拒绝）。

## 2. 门禁怎么运作（决定你的操作顺序）

- 改 `docs/` 下任何**受管文档**之前，必须先 `read` 过它。没读过 → 被拒。
- **改完它就变回未读**（指纹变了）。要再改一次，得先重读。
  - ⚠️ **但"自己刚改的"是例外**（M2.8 起）：同一次会话里，**你**刚用 `edit` 改成功的文档，
    紧接着再改**不会**要求重读。只有**外部改动**（别人/另一个会话/编辑器）才强制重读。
  - 所以看到「你读过的是旧版」时，先问一句：**这中间是不是我自己动过？** 不是才重读。
- 这不是 bug，是设计。**不要为此去找插件源码**。
- **`read-order` 的「必读清单」是自动块**（M3 起）：成员与顺序由插件按 frontmatter 的
  `status` / `order` 渲染，`doc_new` / `doc_mark` 之后**自动更新**。
  - ⇒ **你不用再手写成员**，也不要去补一行。
  - 工具改写这一节**不会**让你重读 `read-order`（插件已经替你重新记账了）。
  - 只有块**下方**的「为什么读」、以及「下一步 / 陷阱 / 依据文档」需要你写。
  - 若你手改了块内部，插件会**拒绝覆盖、只在回执里 warn** —— 那是有意的（交接时才该改它）。
- `docs/` 下**完全没有 frontmatter** 的文件是 `unmanaged`：可写、不进索引、不报异常。
- `_artifacts/` 与 `deliverables/` **门禁完全不拦**，随便改。

## 3. 各工序怎么做

### 3.1 建文档

```
doc_new(role, title, summary, body, id?)
```

`role` 取 `index` / `spec` / `decision` / `evidence` / `log` / `handover` / `instruction` / `fact`。
`order` 会自动插值（默认取最大值 +10）。**不要自己写 frontmatter 再 `write` 进 `docs/`** —— 那样不保证合规。

#### ⚠️ `id` 与标题是解耦的：**用中文标题就显式传 `id`**

`id` 是**永不变的内部标识**（决定文件名 `docs/<id>.md`）；`title` 是**给人看的**。
不传 `id` 时工具会从标题推导 —— **只保留 ASCII 字母数字**，于是：

| 标题 | 推导结果 | 结果 |
|---|---|---|
| `架构评审与补充设计` | `""` | ❌ **报错**（纯中文，一个 ASCII 都不剩） |
| `测试规格` | `""` | ❌ 报错 |
| `第 3 轮复盘` | `"3"` | ❌ **故意拒**（纯数字不表达语义） |
| `交接：全流程测试30` | `"30"` | ❌ 同上 |
| `交接：DDD全流程测试35` | `"ddd-35"` | ✅ |
| `API 设计 v2` | `"api-v2"` | ✅ |
| `handover 交接` | `"handover"` | ✅ |

⇒ **这条不是"文件名不能有中文"，是"别让工具去猜 id"。**
用中文标题时**直接传 `id`**，一次就过：

```
doc_new({ role: 'spec', title: '架构评审与补充设计', summary: '…', id: 'arch-review' })
```

报错里那句「请显式传 `id`，例如 `id: "handover-m1"`」就是让你补这一步。
**这一步只花 0 次额外调用；不传则必然多一轮 `doc_new` 重试。**

#### ✅ 建完之后：必读清单会自动更新（M3）

`doc_new` / `doc_mark` 之后，插件会按 frontmatter 重渲染 `read-order` 的「必读清单」自动块：
`status` 是 `authoritative` / `partial` 的文档自动进清单（按 `order` 排），
**非终态的交接也会进**（刚建的交接是 `draft`，同样按 order 排在第一）。

⇒ **不要再手写「必读清单」的成员**，也别去补一行。回执里会明说「已自动维护」。

### 3.2 改文档正文

1. `read` 它（否则门禁拒绝）
2. `edit` 改正文
3. 若要改状态，再 `doc_mark`

### 3.3 改状态

```
doc_mark(id, status, basis?, reason?, supersededBy?, anchor?, sectionStatus?)
```

- 标 `sealed` / `void` **必须给 `reason`**（会写进标记块）
- 标 `superseded` **必须给 `supersededBy`**
- **`basis` 可以一起给**（`实测` / `推断` / `未验证`）。它和 `status` 同属"置信度"维度，
  一次调用就能同时改完 —— **推荐这么做**，否则标绿后 H-5 会报"authoritative 却 basis 未验证"，
  再改一轮 `edit` 又会让指纹失效。
- ⚠️ **标 `authoritative` 不会校验交接结构**（M2.7 起，结构只是提示词层）。
  不合格的交接**也能**标绿。要体检请**自己先跑** `doc_handover_check`。

### 3.4 归档进坟场（**这条最容易错**）

**归档 = 用 `doc_mark` 把文档标成 `void`。就这一步。**

```
doc_mark(id: "handover-6", status: "void", reason: "已被 handover-10 取代")
```

- ⚠️ **工具不能搬文件**。标完 `void` 后，文件还在 `docs/` 里；
  真正的搬运由用户在界面「归档」页签点（或 `docs/_graveyard/` 手动移动）。

  #### ⚠️ 别在文档里断言"文件仍在 `docs/`"——**那是会过期的**

  第 35 轮实机（`session-0a4d5b43`）的真实现场：AI 归档后写了

  > `instruction-2` 已 `void`，但文件仍在 `docs/`。要真正搬进 `docs/_graveyard/`，
  > 由用户在界面「归档」页签点。

  **用户随后就在界面上搬了** —— 于是这句话立刻变成假话，而 `handover-1` §7
  还写着「何时由用户实际搬进坟场，**未定**」。

  **搬文件是用户的动作，AI 永远不知道它什么时候发生。**
  ⇒ 写"已 `void`（等待用户搬）"就够，**不要写"文件仍在 `docs/`"这种当前事实**。
  同理别写"坟场里现在是空的"——那是随时会变的快照。

  **这不是免责声明，是刻意的职责分离**（2026-11-16 用户拍板决策 #7 要求补上理由）。
  两条具体原因：

  1. **搬文件会让 `present` 声明失效** —— `present` 记的是**绝对路径**，
     文件移动后"无法通过原声明打开"（M2 架构评审附录 A13 实测）。
     工具擅自搬 = 悄悄弄坏用户已经打开的卡片。
  2. **会让跨文档的 `supersedes` / `supersededBy` 悬空** —— 搬走之后别处的引用
     指向一个不存在的路径，右栏会报「指向不存在的 id」，而工具无法判断
     哪些引用是"该一起改"的、哪些是"用户想保留的历史"。

  ⇒ 所以：**工具只负责把状态标对（`void`），搬不搬、什么时候搬，是用户的决定。**
- ⚠️ **不要**为了"怎么归档"去读插件源码。上面就是全部。
- ⚠️ 标 `void` 会**删掉 `supersededBy` 字段**，历史关系转由正文的 `<!-- ddd:mark -->` 标记块承载。字段消失不是出错。
- ⚠️ 归档前先 `grep` 一遍它的 id：移走后别处引用它的 `supersedes` / `supersededBy` 会悬空，右栏会报「指向不存在的 id」。

### 3.5 交付成品（**这条也最容易错**）

**交付 = 把文件放进 `deliverables/`。就这一步。**

```powershell
Copy-Item docs\spec-1.md deliverables\spec-1.md -Force
```

- ⚠️ **不要**去找"交付工具"——没有这个工具。就是复制文件。
- `deliverables/` 是**交付成品区**，不是工作区根，也不是 `docs/`。
- 想让交付区显示"已声明"，可以调用宿主的 `present` 工具；不调也能用，只是标成「未声明」。

### 3.6 改阅读顺序（**三条载体，只有一条要你手写**）

| 载体 | 谁在读 | 怎么改 |
|---|---|---|
| 各文档 frontmatter 的 `order` | **机器**（索引块与看板按它升序排） | `edit` 改 `order:` 那一行 |
| `## 必读清单` 里的**自动块**（`<!-- ddd:auto:begin -->` 到 `<!-- ddd:auto:end -->`） | **人和 AI** | **不用你改**：M3 起由 `doc_new` / `doc_mark` 按 frontmatter 自动渲染 |
| 入口索引正文的**其它小节**（「为什么读」/ 下一步 / 陷阱 / 依据文档） | **人和 AI** | **手写维护** |

**只改 `order` 不写其它小节 = 只做了一半。** 自动块只负责"该读谁、按什么顺序"；
「先读这份」「别照 §4 写代码」这类**判断**它表达不了 —— 那些必须人手写。

入口索引正文该维护的小节：

- `## 必读清单` —— 自动块由插件维护；**块下方**写「为什么读」
- `## 下一步` —— 接下来该干什么
- `## 陷阱` —— 哪些东西看起来该改但别改，以及为什么
- `## 依据文档` —— 结论建立在哪些文档上

`order` 取值建议留插值（10/20/30），交接永远排第一（最小）。

⚠️ **别手改自动块内部**：交接时或用户明确要求时才改它是合理的；
平时手改会让插件在回执里 warn「被手改过、本轮没覆盖」（它不会悄悄冲掉你的改动）。

## 4. 交接（最复杂的一步，按顺序做）

### 4.1 直接 `doc_new` 一次建好，**不要打草稿**

> **2026-11-15 M2.8 更正**：这一节原来要求「先在 `_artifacts/handover-draft.md` 打草稿」。
> **那条对策已经过时了**，别再照做。

**为什么过时**：打草稿是 `edit` 交接**还被锁死**时的绕法 —— 当时改一行就得整份重写，
所以先去 `_artifacts/` 写、自查、再 `doc_new` 一次定稿。
**M2.6 起 `edit` 交接已经彻底放开**（任何状态都能改，见 4.5 与 `core/roles.js` 的
`handover: { write: DENY, edit: ALLOW }`），所以那个绕法失去了理由：
写错了直接 `edit` 就行，不需要先在外面抄一遍。

**实测它现在只剩成本**（第 24 轮 `session-5b5f5c68`）：
AI 在 seq 61 明确计划「Let me draft in `_artifacts/handover-draft.md` first」，
**最后一次都没写**（全会话 `_artifacts` 写入 0 次），却为这个决定多绕了一步；
它事后自述「交接草稿直接一次成稿，没有反复重建」。
⇒ **一条没人执行、只制造犹豫的提示。**

**现在的做法**：

1. **先把要引用的东西全做完**（见下面 4.1.1）—— 这一步才是真正防返工的
2. **直接 `doc_new` 建交接**，一次写全
3. 校验没过就**原地 `edit`**（见 4.5），**不要**重写整份

⚠️ 唯一还值得先写外部文件的场景：交接**特别长**（比如 >200 行）且你要反复大改。
那时草稿能省门禁重读 —— 但那是"长文档"的通用技巧，**不是交接的必经步骤**。

#### 4.1.1 ⚠️ 落笔之前：**先把要引用的东西全做完**

AI 自述（`session-916967d2`）：

> `doc_new` 建交接的那一刻，我在正文里已经写了「`read-order` 的必读清单与「下一步」
> 已按这两份更新」——**但那时我还没改 `read-order`**。我在陈述一个尚未发生的状态。
> ……**七段结构全合规、健康度全过，但有一句话在说假话**——校验器查不出来，只有我自己知道。

**H1–H7 只查结构，不查内容真实性**（它无法知道 `read-order` 改没改）。
所以这条只能靠你自己守：**交接说"已完成 X"，X 就必须在此刻真的完成了。**

正确顺序：

```
改完所有内容文档（正文 / order / basis）
→ 入口索引的「为什么读 / 下一步 / 陷阱 / 依据文档」定稿（**必读清单成员由插件自动维护**）
→ doc_health 里 **H-1 ~ H-5 清零**（H-6 不用管，见下）
→ 写交接（此时才能诚实地引用它们）
→ doc_mark 标 authoritative
```

#### ⚠️ **H-6 清不掉是正常的，别为它反复改**

**只要项目里有内容文档，H-6 就必然存在。** 原因是一条因果链，绕不开：

```
交接必须写"现在到哪了" → 写完还想补细节 → 补细节就要改别的文档
→ 改了就触发 H-6「标绿后这些文档改过」
```

**所以验收标准是「H-1 ~ H-5 清零」，不是「H-6 也清零」。**

H-6 报的是**事实**（"这些文档在你标绿之后改过"），不是判决（"你写错了"）。
它现在**报一次就会自动重取基线**，所以同一处漂移不会反复报。

**看到 H-6 该怎么办**：看一眼它点名的文档，确认交接正文里没引用它们的
**具体数值/哈希/状态**。确认没有就**收手** —— 不要为了消掉它去改文档，
那会让漂移更多、H-6 更多。

> 这条是 2026-11-16 用户拍板（决策 #4）：原文案「doc_health 不再报 warn」
> 在有任何内容文档的项目里**永远达不到**，会让 AI 陷入无意义的循环。

#### ⚠️ `basis` 默认是「未验证」

`doc_new` 建出来的文档 `basis` 是 `未验证`。**它不属于七段，也不影响 H1–H7**，
所以很容易忘 —— 但 `doc_health` 的 H-5 会在你**标绿之后**才报：
"authoritative 却 basis 未验证"。

那时再去改，两份文档指纹都变了、又变回未读、还要重读。

⇒ **打算标 `authoritative` 的文档，建的时候就把 `basis` 写对**（`实测` / `推断`）。

### 4.2 七段结构（缺一段就不合格）

| 段 | 标题关键词 | 要求 |
|---|---|---|
| §1 | 我的意图 | 非空，不能只写「无」 |
| §2 | 现在到哪了 | 非空 |
| §3 | 下一刀 / 下一步 | **≥1 条含具体路径 / 工具名 / 反引号命令** |
| §4 | 坑 / 不要重犯 | 非空，可逐条枚举 |
| §5 | 验收 | **每一条都要带证据**（见 4.3） |
| §6 | 刻意没做 | 非空，可逐条枚举 |
| §7 | 仍未决 | 可为空，但要显式写「无」 |

### 4.3 §5 的证据怎么写（H4 现在是 **warn**，不再阻断交接）

> **2026-11-14 起 H4 降为 warn**（用户拍板）。理由：它逼的是"人话迁就正则"，
> 不是"把话写清"。一份"我用 PowerShell 逐份比对，两行都输出 OK"的交接
> —— 它确实验过了 —— 原来会被判 2/2 全挂。**现在它能过，但会有一条提醒。**

所以：**写不清证据形状不再卡住你**，但写清楚仍然更好（下一位接手者看得懂）。

每条验收都要能被**核对**。四类写法任选其一：

| 类型 | 写法示例 | 稳定性 |
|---|---|---|
| **测试输出** | `722/722 全绿`、`3/3 通过`、`3/3 命中`、`tests 691 / pass 691`、`ALL GOOD` | ⭐⭐⭐ **最稳，优先用** |
| 事件序号 | `seq=42`、`seq: 2468` | ⭐⭐⭐ 稳 |
| 会话 id | `session-abc123`（`session-` + 至少 6 位十六进制） | ⭐⭐⭐ 稳 |
| 哈希 | `sha256: a1b2c3d4`、`SHA256 ` `0445F64A…` ``、`指纹 8c6246` | ⭐ **脆弱，最后才用** |

**不算证据的写法**（写了会被拒）：

- `3/3`（只有分数、没有结果词）
- `共 12/12 条`、`跑了 3/3 次`、`文件数: 4`（没有“通过/命中”这类结果词）
- `看起来没问题`、`测试也没做`
- `sha256 = 见文件`（没有实际哈希值）

#### ⚠️ 哈希为什么脆弱（实测踩过两轮）

哈希是**文件的当前内容**。你写进 §5 之后，**任何一次对那份文件的改动都会让它作废**：

```
改 read-order → 取哈希 41BC5538 写进 §5
→ 跑 doc_health 发现 basis: 未验证 → 改 basis
→ read-order 哈希变成 3AF143D8 → §5 那条作废 → 再 read、再 edit
```

**AI 自述（`session-3ef1b3b2`）**：

> 我把“取证据”当成了收尾动作，但它其实是**最后一个**动作，
> 前面任何一次改动都会让它作废……我把顺序弄反了，多付出了两轮 read 和 edit。

**所以：能用 `3/3 通过` 就别用哈希。** 非要用哈希，必须按这个顺序：

1. **先**把所有内容文档（`read-order` 等）的正文、`basis`、`status` 全部定稿
2. 跑 `doc_health`，确保它不再报 warn
3. **最后**一次性取完所有哈希，写进交接 §5
4. 最后才 `doc_mark` 标 `authoritative`

**两条重要限制**：

- ✅ **§5 可以放代码块了**（2026-11-16 起）。解析器现在会跳过围栏内的行，
  所以 ```bash 里的命令示例不会再被当成"缺证据的验收条目"。
  （之前这条是"§5 别放代码块"，那是让用户迁就实现，已修。）
- ⚠️ **不要写自我指涉的验收条**（如「本份交接自检通过」）：判据在文本里找不到哈希/命令/测试输出，必然判不合格。
- ⚠️ **比值必须成立**：`0/0 通过` 不算（零项被验证 = 什么都没验），`5/3 通过` 也不算。
  写之前先问自己：这个分母是**我实际验过的项数**吗？

### 4.4 交接后还要做的事

1. **写入口索引的「为什么读 / 下一步 / 陷阱 / 依据文档」**（必读清单成员由插件自动，见 3.6）—— 漏了这一步用户得提醒你
2. 归档被取代的旧交接（`doc_mark` 标 `void`）
3. `doc_health` 复检 —— **只要求 H-1 ~ H-5 清零**；H-6 报的是时序事实，清不掉是正常的（见 4.1 那段）

### 4.5 交接：**可以直接 `edit`，任何状态都行**

| 操作 | 允许 | 说明 |
|---|---|---|
| `edit` 交接正文 | **允许**（draft / authoritative / … 全部） | 校验没过就原地改，**不要重写整份** |
| `write` 新建交接 | **拒绝** | 新建请用 `doc_new`（它生成合法 frontmatter + 处理 superseded 链） |

**校验没过时怎么办**：

1. **直接 `edit` 它**，把列出的问题一次改完，再 `doc_handover_check` 复检。
   **不要**每修一行就重写一份新的（实测有会话因此连建 4 份、44 步、最后被中止）。
2. 想留一份干净的新版再 `doc_new`（旧的自动标 `superseded`），但不是必需的。

> **这张表就是 4.1 那条"不用打草稿"的依据。** 两张表曾经互相矛盾：
> 4.1 说"别一上来就 `doc_new`，先打草稿"，4.5 说"任何状态都能直接 `edit`"。
> 以 4.5 为准 —— 打草稿是为绕开一条**已经不存在的**限制。

⚠️ **别过早标 `authoritative`**：标绿之后如果还要改别的文档（比如 `read-order`），
你交接里写的哈希就会过时。虽然没有硬限制拦你改回来，但会多一轮返工。

⚠️ 为什么这里允许改：真实使用中交接是"照做"的对象，几乎不会被改；
而演练/施工中经常需要改（哈希变了、漏了一条证据）。**锁死的代价远大于放开的风险。**

## 5. 常见卡点与出路（都是实测踩过的）

| 现象 | 真正原因 | 该做什么 |
|---|---|---|
| `no-project-root` | 这个目录还不是 DDD 工作区 | 请用户点「初始化为 DDD 工作区」按钮 |
| 「你读过的是旧版」 | 你改过它（或 `doc_mark` 改过它的 frontmatter），指纹变了 | `read` 重读，再改 / 再标 |
| `read-order` 的必读清单「多了/少了我没写过的条目」 | **正常**（M3 起它是自动块，按 frontmatter 渲染） | 不用动它；要改就改 frontmatter 的 `status` / `order` |
| 回执说「自动块被手改过…本轮没有覆盖」 | 你（或别人）动了自动块内部 | 保留你的改动；想让插件接管就删掉整块，下次工具调用会重建 |
| H4 说"没有证据形式" | §5 那一条没有可核对的形状 | 照 4.3 的表加 `seq=` / 哈希 / `N/N 全绿` |
| H4 说有 N 条缺证据，但你觉得写了 | 用了 `3/3` 这种**没有结果词**的写法，或比值不合理（`0/0`） | 加结果词（`通过`/`命中`/`全绿`/`全过`）并确认分母是真实验过的项数 |
| **H11 说"会过期的当前事实"** | 你写了「坟场为空」「文件仍在 `docs/`」「还没交付」这类**用户一操作就变**的状态 | 改写成**不变量**：把「坟场为空」写成「本轮未归档任何文档」。**确认那句话永远不会变就可以忽略**（它是 warn，不阻断） |
| 交接校验总不过、感觉在原地转 | 可能是你在反复重写整份 | **原地 `edit`**，别重建 |
| `doc_health` 报 **H-6「标绿后这些文档改过」** | 这是**时序事实**，不是你的错。只要项目里有内容文档就必然出现 | 看一眼点名的文档，确认交接没引用它们的具体数值/哈希 → **收手**。别为它改文档（越改越多）。验收标准是 H-1~H-5 清零 |
| `doc_mark` 拒绝改 `order` | 它只改状态，不改结构字段 | 用 `edit` 改 frontmatter 的 `order:` |
| 归档后文件还在 `docs/` | 工具只能标 `void`，不能搬文件 | 让用户在界面「归档」页签点，或手动移动 |
| 交付区没变化 | 交付 = 复制文件到 `deliverables/` | `Copy-Item docs\xxx.md deliverables\xxx.md -Force` |
| 主栏（root 面板）点文件没反应 | root 面板没有会话，预览必抛 | 到**会话页右侧栏**的 DDD 页签里点（那里能开） |

## 6. 绝对不要做的事

1. **不要为了搞清"该怎么做"去读插件源码**（`app.asar`、`@local/ddd`、`profiles\desktop`）。
   那是最贵的错误路径，且上面这张表已经覆盖了所有工序。
2. **不要自己写 `AGENTS.md` 或 `docs/` 去凑激活标记** —— 那是用户的选择。
3. **不要反复重写交接** —— `draft` 状态**原地 `edit`** 就行；只有已定稿的才需要新建。
4. **不要假设"文档变了但门禁没拦"** —— 门禁按路径判，`_artifacts/` 和 `deliverables/` 本来就不拦。
5. **不要手改 `read-order` 的自动块**（`<!-- ddd:auto:begin -->` 到 `<!-- ddd:auto:end -->`）——
   那是插件的投影；交接时或用户明确要求时才改它，且改了要在交接里说清。

## 7. 一句话总结

| 用户说 | 你做 |
|---|---|
| 建一份 spec / 决策 / 指令 | `doc_new` |
| 把它标成权威 / 作废 | `doc_mark` |
| 归档 / 移入坟场 | `doc_mark` 标 `void`（搬运由用户点） |
| 交付 / 放进交付区 | 复制文件到 `deliverables/` |
| 改阅读顺序 | `edit` 改 `order` **+** 写索引的「为什么读 / 下一步 / 陷阱 / 依据」（必读清单成员自动） |
| 交接校验没过 | 还是 `draft` → **原地 `edit`**；已定稿 → `doc_new` 建新的 |
| 交接给下一个会话 | 定稿引用 → **直接 `doc_new`**（不打草稿）→ 写索引其它小节 → 归档旧的 → `doc_health` |
